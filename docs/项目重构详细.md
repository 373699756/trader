# 项目重构详细设计

## 1. 项目评审结论

当前活动仓库仍保留历史 `domain / application / infra / web / entrypoints` 分层，但阶段 9 已将 HTTP 所有者切换为顶层 `http_api/`，`web/` 只保留页面、模板、组件和静态资源；`bootstrap.py` 是唯一组合根。本文件是本轮产品、架构、时间线、API、Web、运维和验收的唯一权威，同时区分当前现状与阶段目标，不把尚未存在的目录写成现状。目标切换必须在同一实施批次同步修改源码、架构契约、消费者、必要测试和 `docs/02_工程设计.md`；在对应阶段门禁通过前，活动系统仍按本文件标明的当前现状运行。

重点结论：
- 数据源，如何保证数据的完整度和新鲜度？避免之前数据的干扰，把实时动态数据和静态数据分开处理，静态数据程序启动一次获取就行，保证荐股链条上的数据是最新的 #TODO 数据源数量超级少
- 业务必须按照“数据源 -> 静态采集 -> 静态清洗 -> 一级稳定过滤 -> 动态采集 -> 动态清洗 -> 二级动态过滤 -> 候选生成 -> 质量评估 -> 评分 -> 风险复核 -> 固定 68/32 融合 -> 下行保护与动作门 -> TopK/集中度/冻结/发布”的 14 层链路推进，不允许模块直接跨层读取别的模块的临时缓存。
- 清洗与格式统一必须尽早落在数据采集之后，保证后续所有过滤、候选生成、评分、风险、Web 监控都在统一 schema 下进行；这是整个推荐流程的前置契约，不属于后期特征工厂的延迟处理。
- 一级稳定过滤和二级动态过滤必须严格区分：前者解决“长期不具备参与资格”的问题，后者解决“当前时点不具备交易/风险条件”的问题；二级过滤对应大纲中定义的动态硬过滤，属于当前时点的硬筛选，不是最终推荐结果。
- 候选生成不是“临时缓存拼接”，而是“在全市场标准化数据上，完成稳定资格过滤、动态时点过滤、必要的特征准备，输出一个可进入评分流程的候选清单”。它只负责生成候选集合，不赋值最终推荐，不直接写 Web 视图，也不做评分和风控结论。
- 质量评估在数据清洗和特征构建完成后，按评分档位合同标注缺失字段的严重度；评分层据此执行显式质量扣分，关键字段缺失固定扣至 0 分并停止模型、DeepSeek 和动作升级，不能通过默认值伪造完整输入。
- 风险复核在评分结果形成后检查可交易前提与结构化风险证据；合法风险在融合前扣分、否决或降级，不能由自由文本直接改变分数。
- `download/`、`training/`、`recommendation/` 是三个独立业务，各自拥有完整责任边界和运行生命周期。`http_api/` 与 `web/` 只为 `recommendation/` 提供对外只读接口和页面展示；二者因功能边界独立而放在最外层，不因目录并列而成为独立业务。
- 每一层都必须输出统一阶段快照；Web 与 `scripts/` 中的诊断脚本必须能看清输入、输出、业务拒绝、待补充、失败、原因聚合、来源状态、耗时和降级状态；Web 只读取公开聚合投影，受限诊断脚本才能按既定边界定位单股。这里面的脚本如何精简优化 #TODO script里面乱七八糟的脚本太多了
- 评分和 Web 必须区分“业务状态”和“诊断状态”：Web 监控是只读观测，不允许参与业务决策。

## 2. 重构总目标

本次重构目标不是简单拆文件，而是把推荐链路建成一个可审计、低耦合、高可观察的分层系统，满足以下要求：

1. 各独立功能不能互相干扰
   - 下载、训练和实时荐股是三个生命周期独立的业务。
   - HTTP 和 Web 是荐股业务的外置交付模块：只展示 `recommendation/` 已发布的结果和诊断投影，不拥有第四条业务链路。
   - 每个模块只负责自己的输入输出，不直接写入其他模块的运行态。
   - 任何共享对象都必须是不可变值对象，禁止跨模块附加临时字段。

2. 荐股链路采用分层设计
   - 层次必须清晰：数据源 -> 静态采集 -> 静态清洗 -> 一级稳定过滤 -> 动态采集 -> 动态清洗 -> 二级动态过滤 -> 候选生成 -> 质量评估 -> 评分 -> 风险复核 -> 固定 68/32 融合 -> 下行保护与动作门 -> TopK/集中度/冻结/发布。
   - 每一层都必须具有独立输入、独立输出、独立错误处理和独立监控状态，确保问题能够在具体层级中定位，不跨层污染其他模块。
   - 其中：
     - 数据源负责统一进入链路的原始输入来源；
     - 静态数据采集负责全市场静态基础信息拉取；
     - 静态数据清洗与特征构建格式统一负责统一字段名、字段类型、时间格式、单位、精度、缺失值编码以及静态特征结构，形成稳定基础对象；#TODO 把这字段一一列举出来
     - 一级稳定过滤负责长期排除缓存，处理证券身份、交易所和板块、上市日龄、退市状态、长期黑名单和发行人资格；
     - 动态数据采集负责当前时点行情与行为信号的获取；
     - 动态数据清洗与特征构建格式统一负责统一动态特征 schema 和时序规范，保证同一评估时刻数据一致；#TODO 把这字段一一列举出来
     - 二级动态过滤负责当前时点硬过滤，处理交易状态、流动性、均线、波动率、异常行情和高风险波动等；
     - 候选生成负责将通过一、二级过滤的股票组织为“可进入评分的候选清单”；
     - 质量评估负责数据缺失与严重程度分级；
     - 评分负责本地和模型评分；
     - 风险复核负责本地风险只扣一次和 DeepSeek 结构化证据校验；
     - 融合负责固定 68/32 公式和 local-first 降级；
     - 下行保护与动作门负责正式、观察或不行动结论；
     - TopK、集中度、冻结与发布负责组内最终选择、不可变正式记录和只读 Web 快照。#TODO 这个需要主动推送到web端，或者web端超时了主动查询

3. Web 需要监控荐股链路完整流水线
   - 每一层必须留下输入、输出、业务拒绝、待补充、失败、原因聚合、耗时和来源健康；只有过滤层计算业务拒绝率。
   - Web 页面只展示“可观测状态”，不能直接发起行情抓取、评分或 DeepSeek 请求。

4. 业务与运维状态分离
   - 业务状态：候选池、正式池、观察池、评分结果、冻结状态。
   - 诊断状态：过滤日志、降级状态、源健康、耗时、水位等。
   - 两类状态必须分别命名和持久化，避免一份状态对象同时承担业务决策和设备诊断。

## 3. 目录结构与模块化设计

本章裁决重构完成后的唯一目标目录。它会把当前分层优先结构迁移为业务线优先结构，因此不是“保持现有顶层目录”。第 3.1 节是唯一目录树；后续章节只能引用该树中的路径，不得创造同义文件、平行目录或临时兼容层。

既定目录结构承载三条明确的设计主线：

1. 业务独立：`download/`、`training/`、`recommendation/` 分别拥有历史归档、模型训练和实时荐股业务；
2. 荐股交付模块外置：`http_api/` 和 `web/` 按独立功能模块放在最外层，但业务所有权始终属于 `recommendation/`；
3. 基础设施分层：时钟、缓存、配置、数据库、DeepSeek、行情适配器等作为公共基础设施。

重要原则：

- 不使用无法表达职责的泛化业务目录；三个业务目录必须直接表达下载、训练和荐股责任；
- 业务链路和功能能力不能混用同一套目录命名；
- 顶层物理位置不改变业务归属；`http_api/` 和 `web/` 不得被解释为与三个业务并列的第四、第五业务；
- 目录设计必须与链路语义一一对应，能直接回答“这一步是哪一层、哪一个能力在做什么”。

- 三个业务内部的依赖方向固定为 `entrypoints / infra -> application -> domain`；`http_api/` 与 `web/` 只能调用 `recommendation/application/` 公开的只读用例，不得调用下载或训练业务；
- `domain/` 只负责定义纯业务对象和值对象，不直接读时钟、文件、数据库、HTTP、配置；

- `infra/` 属于该业务线的基础设施适配和持久化封装，适用于本业务线的外部依赖；
- 顶层 `infra/` 只提供共享的时钟、配置、原子文件、序列化、缓存 primitive、供应商底层客户端和有界执行资源；业务语义、业务缓存、标准化规则和端口适配器留在对应业务线的 `infra/`；
- `entrypoints/cli.py` 与 `entrypoints/server.py` 分别实现 `trader-cli` 和 `trader-server`，两者都只调用 `bootstrap.py`，不得各自形成组合根；离线研究命令由 `training/entrypoints/commands.py` 延迟分派，生产推荐入口不得导入研究依赖；
- 每一层都必须拥有：
  - 独立输入对象；
  - 独立输出对象；
  - 独立错误处理；
  - 独立监控状态；
  - 明确的失败降级策略。
- 下层不允许直接访问上层临时对象，上下层只通过有类型的数据对象和接口交换；
- 阶段名称固定为：数据源 -> 静态采集 -> 静态清洗 -> 一级稳定过滤 -> 动态采集 -> 动态清洗 -> 二级动态过滤 -> 候选生成 -> 质量评估 -> 评分 -> 风险复核 -> 固定 68/32 融合 -> 下行保护与动作门 -> TopK/集中度/冻结/发布。

### 3.2 业务与荐股交付模块边界

能力模块化服从第 3.1 节的唯一目录树。下载、训练和推荐是彼此独立的业务；HTTP 和 Web 是荐股业务之上职责独立的交付模块。本节只说明责任边界，不再重复绘制目录或创造第二套所有权。

固定原则：

- `download/`、`training/`、`recommendation/` 是三个顶层独立业务目录；
- `http_api/` 和 `web/` 在物理目录上与三个业务并列，在业务所有权上共同属于 `recommendation/` 的只读交付边界；
- 顶层 `infra/` 只封装跨业务共享的技术 primitive；具体业务线的端口适配、业务标准化、持久化规则和缓存身份由该业务线的 `infra/` 唯一拥有；
- 三个业务及两个荐股交付模块都有明确输入、输出、错误处理和诊断状态，但只有三个业务目录拥有业务状态与决策；
- 模块之间只传递有类型 DTO、不可变快照、状态对象或事件，不共享可变工作态。

#### 3.2.1 下载与训练能力边界

下载和训练保留在第 3.1 节既定的 `download/` 与 `training/` 目录中，不迁入推荐链，也不直接写推荐运行状态。

- `download/` 只负责历史归档首次建立、增量补齐、校验和快照发布；
- `training/` 只读已发布历史快照，按显式选择的评分档位训练并发布模型工件；
- `training/infra/profile/v2/` 与 `training/infra/profile/v3/` 分别拥有训练特征合同、训练参数和待发布 manifest；
- `training/infra/artifacts/` 是工件 codec、校验和原子发布的唯一代码边界，不在应用层复制 `artifacts/` 目录；实际模型文件固定写入 `data/train/v2/{tomorrow,d25}/` 或 `data/train/v3/{tomorrow,d25}/`；
    #TODO artifacts 这是什么鸡毛命名
- 下载维护锁、训练锁和推荐运行态相互独立，任何一条链失败都不得污染另两条链。

#### 3.2.2 推荐评分档位能力边界

推荐应用层必须通过 `recommendation/application/ports/` 使用外部能力，不得导入 `recommendation/infra/`。职责固定如下：

- `base_scoring.py` 计算统一标尺的原始规则分，再按质量合同扣除 `quality_penalty` 形成 `base_score`；后续风险复核只扣一次本地风险并形成 `local_score`；
- `model_scoring.py` 只调用 `LoadedProfilePort` 读取已由组合根加载的档位能力，输出模型预测、分歧和成本后效用等模型诊断，不加载工件、不保存第三份 profile 实现，也不改写 `local_score`；
- `recommendation/infra/scoring/profile/v2/` 与 `recommendation/infra/scoring/profile/v3/` 是推荐侧模型加载、工件校验和推理适配器；训练侧同名单数 `profile/` 只拥有训练合同，二者不得复制实现或互相导入；
- 本地结果与模型结果只在后续 `score_merge/` 按固定规则汇合，不能在 `local_score/` 内提前融合或形成最终排名；
- `downside_action/` 只在融合完成后执行下行保护与动作门，输出正式、观察或不行动结论；
- 第 10 层只形成分组评分记录；`final_selection/grouped_ranking.py` 在动作门之后按档位 × 策略 × 板块执行最终稳定排序，`concentration_policy.py` 与 `topk_selection.py` 再完成组内集中度、补位和最终 TopK；
- 排序结果随后才能进入 `freeze_publish/freeze_coordinator.py` 与 `freeze_publish/snapshot_publisher.py`，禁止排序、TopK 或集中度逻辑回流到 `local_score/`。

启动配置只允许选择 V2、V3 或同时选择 V2 与 V3。组合根必须在启动推荐运行时前，对所选集合的全部 Tomorrow、D25 模型头、manifest、hash 和输入合同执行一次原子校验；任一所选档位或模型头失败，整个所选集合不启动，不允许部分启用、规则分冒充正常模型档位、静默切换档位或拼接不同档位对象。合法启动后的单次在线推理失败可以保留规则评分并标记该次结果降级，但不能改变已加载档位身份。

Web 只为实际选择并成功加载的档位生成切换按钮：只选 V2 时显示 V2，只选 V3 时显示 V3，同时选择时显示两个按钮。按钮只切换同一档位已经发布的独立结果，不触发模型加载、重新评分或跨档合榜。

#### 3.2.3 荐股 HTTP 与 Web 交付边界

HTTP 与 Web 沿用第 3.1 节中的 `http_api/` 和 `web/` 目录。它们是 `recommendation/` 的外置交付边界，不是独立业务；`http_api/` 是荐股 HTTP/API 的唯一所有者，`web/` 不再建立 `api/` 子树。

- `http_api/` 只通过 `recommendation/application/` 的只读用例读取已发布快照和诊断状态，负责请求处理、schema 与白名单响应投影；
- `http_api/routes/page_routes.py` 统一注册桌面页面路由；`web/` 只提供无 HTTP 副作用的页面渲染、组件、模板和静态资源，不定义路由或 Flask handler；
- 页面需要监控数据时只消费 `http_api/` 已发布的只读端点或注入的只读投影，不在 `web/` 内重复注册路由、handler、schema 或响应序列化；
- `http_api/` 和 `web/` 不定义下载或训练的业务接口、页面状态或组合根；页面中的档位和模型状态只是荐股运行时已加载能力的只读投影；
- 两者都不得抓取行情、执行评分、调用 DeepSeek 或写推荐工作态；
- 内部对象必须经过显式投影后才能成为公开 JSON，不能直接透传。

#### 3.2.4 业务及交付模块与推荐链路的关系

- 推荐链路负责阶段顺序和业务决定；
- 下载和训练各自拥有独立业务链，不属于推荐链路；
- HTTP 和 Web 只为推荐链路提供对外交付，公共基础设施只提供跨业务技术 primitive；
- V2/V3 只表示评分生产档位，不是新的顶层业务线；
- 耦合点固定为有类型协议和不可变数据，不允许通过共享缓存、动态字典或隐藏服务定位器连接。

### 3.3 两条主线的关系

“业务层次模块化”和“功能模块化”不是互斥，而是互补关系：

- 业务层次模块化回答：链路在什么阶段出现问题？
- 功能模块化回答：哪个独立能力负责这件事？
- 业务链路可以调用能力模块；
- 能力模块不应理解业务链路中的中间状态；
- 能力模块的输入输出必须规范化，并且被业务链路按阶段消费。

换句话说：

- 业务层次模块化负责“过程”；
- 功能模块化负责“能力”；
- 两者都必须具备独立输入、独立输出、独立错误处理和独立监控状态。

### 3.4 唯一结构裁决

第 3.1 节的目录树是本章唯一目标结构。当前活动树必须通过可回滚的实施批次迁移到该结构；迁移过程中不得保留两套活动路由、两套模型加载器或两套发布所有者。后续各节只能补充职责、输入输出和失败边界。

本次裁决同时固定：

- 静态采集、静态标准化、一级稳定过滤继续由 `static_market/`、`static_standardize/`、`static_filter/` 分责，不合并为同时抓取、清洗和过滤的粗粒度目录；
- 动态采集、动态标准化、二级动态过滤继续由 `dynamic_market/`、`dynamic_standardize/`、`dynamic_filter/` 分责，避免供应商失败与业务淘汰共用状态；
- 训练工件代码只保留 `training/infra/artifacts/` 一个所有者，模型文件写入 `data/train/`；应用层仅编排发布用例，不复制工件目录；
- `local_score` 是已扣本地风险一次的结果值；模型诊断是独立输出，固定到 `score_merge/` 才与 DeepSeek 结果融合；
- `downside_action/` 固定拥有融合后的下行保护与动作门，`final_selection/` 固定拥有档位 × 策略 × 板块独立组的稳定排序、集中度、补位和最终 TopK；`local_score/` 不再拥有排序；
- `http_api/` 是荐股路由、请求校验、schema 和响应投影的唯一所有者，`web/` 只保留荐股页面、组件、模板和静态资源；
- 目录和机器身份一律使用小写 `v2/`、`v3/`；中文叙述使用评分档位 V2、V3；配置语义使用 `scoring_profile`，目录语义统一使用单数 `profile/`，应用层不建立 profile 实现目录；
- 目标生产策略只有 Tomorrow 与 D25；Long 是不进入评分链的只读当前快照。旧策略和旧档位退出活动配置、训练、推荐、HTTP 与 Web 路由，历史审计数据只按迁移方案离线归档，不形成活动兼容分支。

### 3.5 infra 模块：公共部分提取

顶层 `infra/` 是跨业务共享的技术 primitive 层，不拥有下载、训练或推荐业务端口。它提供供应商底层客户端、时钟、配置、原子文件、规范序列化、有界执行器和锁；每条业务线的 `infra/` 负责把这些 primitive 适配为本线 application ports。业务标准化规则、缓存身份、仓储 schema、DeepSeek 证据校验和行情选择策略只能各有一个业务所有者，不能在顶层与业务 `infra/` 各实现一份。

本节只补充公共技术能力及其边界，不改变第 3.1 节的唯一目录树，也不新建第二套运行时编排结构。涉及应用编排或进程入口的能力仍在本节说明协作合同，但 `infra` 只拥有对应的外部资源适配、执行支撑和有类型状态。

所有权固定如下：

| 能力 | 唯一业务所有者 | 顶层 `infra/` 允许提供的内容 |
| --- | --- | --- |
| 历史归档 | `download/infra/` | 原子文件、SQLite 连接 primitive、底层供应商客户端 |
| 训练样本与工件 | `training/infra/` | 序列化、hash、锁和有界执行器 primitive |
| 实时行情选择与标准化 | `recommendation/infra/market_data/`、`recommendation/infra/normalization/` | 底层供应商客户端和通用失败类型 |
| 模型加载与推理 | `recommendation/infra/scoring/profile/` | 原子读取、hash 和资源 primitive |
| DeepSeek | `recommendation/infra/deepseek/` | HTTP 客户端 primitive；预算、schema 和证据规则不得上移 |
| 推荐持久化 | `recommendation/infra/persistence/` | SQLite/文件 primitive；schema、幂等键和冻结语义不得上移 |

同一外部资源只能有一个底层客户端实例，由 `bootstrap.py` 注入多个业务适配器；业务适配器不得各自隐藏创建客户端、缓存或线程池。

#### 3.5.1 数据库操作
- 顶层 `infra/` 只负责数据库连接与事务 primitive；各业务 `infra/` 分别拥有自己的 Schema 约束、查询封装和迁移责任。
- 只暴露明确接口，不允许 `application` 或 `web` 直接写裸 SQL。
- 需要区分：
  - 运行态数据库：状态、快照、Frozen 结果；
  - 历史归档数据库：历史行情与训练归档；
  - 稳定排除数据库：长期排除名单和证据身份；
- `PipelineStageSnapshot`、来源健康和受控 `recent_errors` 只存在于当前进程内存，由 `http_api/` 将有类型状态投影给 Web 和诊断脚本；重启后重新生成，不新建诊断数据库、文件归档或流水线事件表。
- 数据访问必须遵循职责分离：持久化层只做数据落地，不做业务评分逻辑。
- 项目自有接口、类型、模块、函数和变量必须使用能直接表达业务职责的具体名称，允许按真实语义使用 `Index`、`Cache` 或 `Snapshot`；不得新增 `Store`、`Stored`、`*Store`、`Repository`、`Archive`、`Registry` 等不简洁泛称。
- 每类数据必须明确唯一写入所有者、事务边界、幂等键、冲突语义和损坏恢复策略；读取失败或校验失败不得返回空对象伪装成功。
- 数据库连接、事务和游标必须有界关闭；运行态写入、历史归档维护和只读 Web 查询不得共享隐式全局连接或相互持锁等待。

#### 3.5.2 上海时区时钟与交易日历
- 所有业务时间统一使用带时区的 `Asia/Shanghai` 时钟，并通过组合根注入可测试时钟；任何模块不得自行调用本地系统时间形成第二业务时钟。
- 时长、deadline 和超时判断使用单调时钟，业务日期、审计时刻和对外时间使用上海时区 wall clock；系统时钟回拨、休眠恢复和 wall/monotonic 明显偏差必须形成可观测状态。
- 必须明确区分：
  - 评估时间 `as_of`：本轮数据与决策事实对应的业务时点；
  - 生成时间 `generated_at`：结果对象完成生成的时点；
  - 冻结截止 `freeze_deadline`：策略窗口禁止继续接纳同日新正式结果的边界；
  - 实际冻结时间 `frozen_at`：正式记录实际完成原子封口的时点；
  - 发布时间 `published_at`：结果对只读消费者可见的时点。
- 供应商声明的 `source_time` 只是经校验的数据事实，不得推进本地业务时钟、交易日或冻结窗口。
- 交易日由注入的 A 股生产交易日历判定；交易日历与时钟是两个独立职责，日历输出必须携带来源、版本、有效期和覆盖范围。
- 日历来源失败时只允许使用仍在有效期内且版本、内容哈希和覆盖范围校验通过的本地缓存；没有可靠缓存时失败关闭，禁止按周一至周五猜测交易日。

#### 3.5.3 股票实时获取
- `recommendation/infra/market_data/` 实现推荐应用层的统一行情端口，不允许业务层直接依赖具体 SDK；顶层 `infra/market_data/providers/` 只包装底层供应商协议。
- 当前实时源失败时只允许按显式优先级、deadline 和熔断状态执行有界备用来源切换；切换不能承诺必然可用，也不能无限重试。
- 所有实时来源输出统一收敛到同一标准对象模型，外部无感。
- 需统一处理：
  - 主源失效切换；
  - 实时行情合并；
  - 多源时间戳冲突；
  - 价格字段、成交量字段、板块字段的标准化。
- 对上层只暴露“可用的标准行情快照”，而不是各个 SDK 的原始结构。
- 多源合并必须校验交易日、观察点、证券身份和字段新鲜度，不得静默拼接不同时点或不同身份的数据。
- 全部实时源失败时保留最近有效快照并显式标记来源年龄、失败类别和降级状态；不得用全零、空集合或过期数据伪装为本轮成功结果。
- 实时人口、历史档案就绪人口与业务过滤必须分开计数；历史缺失只能记为待下载/待更新，不能伪装成业务淘汰。

#### 3.5.4 历史数据获取
- `download/infra/` 实现历史下载应用端口并隐藏不同数据源差异；推荐与训练只读取已发布归档，不另建历史供应商客户端。
- `./run.sh download` 与服务启动同步必须调用同一个下载用例、配置、维护锁、checkpoint 和活动快照发布协议；启动同步每个进程只执行一次且不得阻塞只读 Web。
- 推荐从 `data/history/baostock` 的同一活动快照构造派生内存视图，只在活动快照 hash 改变时原子替换；读取或同步失败保留最近有效视图并显式降级，不得回退到腾讯、东方财富或 Tushare 历史请求。
- 对外提供的数据必须是统一的历史窗口、统一的字段标准和统一的时间轴。
- 历史数据获取失败时，不应阻断已有本地推荐和只读 Web；只能回退到来源身份、Schema、内容哈希、交易日覆盖和有效期校验通过的最近快照。
- 历史数据加载与训练模块之间仅通过明确的数据接口通信，不允许反向写入实时候选状态。
- 下载游标只能表示增量位置，不能代替实际交易日历、历史事实和活动快照身份；失败不得推进游标或覆盖旧活动快照。

#### 3.5.5 数据清洗与格式转换
- 推荐实时数据由 `recommendation/infra/normalization/` 唯一清洗；历史归档标准化由 `download/infra/` 唯一拥有。两者共享字段语义合同，但不共享可变实现或互相写入。所有股票信息在进入业务层之前必须形成“统一基础语义 + 阶段专用不可变类型”；禁止把静态资格、动态行情、历史归档、评分和风险结果堆叠成一个全能对象。
- 这一层的目标不是“简单修正字段”，而是让各阶段对象共享一致的证券身份和字段语义，同时分别遵守自己的 schema：
  - 字段名统一；
  - 字段类型统一；
  - 时间格式统一；
  - 单位和精度统一；
  - 缺失值统一编码；
  - 板块、交易状态、交易所、价格限制统一规范；
  - 主板/创业板/科创板的同类字段必须有一致封装方式。
- 任何数据源、任何模块产出的股票对象都不能继续保留“原始字段名 + 原始类型 + 原始格式”的不同实现；内存中同一语义只能存在一种定义，但不同阶段只能携带本阶段需要的字段。
- 目标是：所有上层逻辑都只处理标准对象，不再处理“不同来源字段名和不同数据格式”，从而让一、二级过滤、候选生成、评分、风险、Web 监控都在同一数据契约之下进行。
- 这一层是候选筛选、评分、风险、Web 展示的基础，也是保证过滤漏斗可观测的关键前置环节。

- 标准对象必须使用简洁且唯一的业务字段名：证券代码统一为 `code`，最新价统一为 `price`；同一语义不得存在第二字段名。各阶段字段与含义固定如下。

  1. 静态资格事实 `StaticSnapshot`
     - `code: str`：证券代码，所有阶段共用的唯一证券身份；
     - `name: str`：证券简称；
     - `exchange: Exchange`：交易所枚举，只允许上交所或深交所；
     - `board: Board`：板块枚举，只允许主板、创业板或科创板；

     - `source: SourceIdentity`：来源、批次和内容身份。

     停牌、交易状态和涨跌停都是当前交易日事实，只能进入动态清洗与二级动态过滤。

  4. 质量评估 `QualityAssessment`

- 上述字段必须经过统一的转换规则处理：
  - 所有时间统一转为 `Asia/Shanghai` 时区的 `datetime`；
  - 所有数值统一为 `Decimal` 或标准整数，禁止混用 `float` 与字符串；
  - 可选数值缺失统一使用 `None`，缺失原因和严重度统一写入 `MissingField`；禁止用 `0`、空字符串或临时哨兵伪装缺失；
  - 所有板块、交易状态、交易所、缺失严重度、阶段状态和涨跌停约束必须使用有类型枚举，不允许以任意字符串表达；
  - 主板、创业板、科创板的字段结构必须保留一致，并通过 `board` 维度区分具体市场；
  - 任何来源模块产出的原始对象都必须在标准化入口被转换成统一 schema；
  - 静态过滤字段、动态过滤字段、历史下载字段不能混写到同一对象中，而是按阶段分别使用各自标准契约，保证一阶段只读取自己需要的字段，并保留可观测的过滤证据。

- 这意味着：一、二级过滤、候选生成、质量评估、评分、风险复核、融合与 Web 监控都不再处理“不同来源字段名 + 不同数据格式”，但也不共享一个可被任意阶段改写的大对象。静态过滤对象依赖长期资格字段，动态过滤对象依赖时点行情和因子字段，历史下载对象只用于归档与训练，评分与风险结果由对应输出类型表达。这样才能保证每层输入/输出明确、字段语义稳定、漏斗统计可追踪，并让 Web 只读取最终诊断投影。

#### 3.5.6 失败处理与降级
- `infra` 必须把第三方异常收敛为稳定、有类型的失败分类，至少覆盖：
  - `timeout`：单次外部调用超时；
  - `transport_error`：DNS、连接、TLS 或网络传输失败；
  - `protocol_error`：HTTP、SDK 或供应商协议不符合合同；
  - `schema_invalid`：载荷字段、类型、单位或枚举校验失败；
  - `stale_data`：来源数据超过允许年龄；
  - `insufficient_coverage`：证券、日期或必要字段覆盖不足；
  - `identity_conflict`：交易日、观察点、来源身份或内容哈希冲突；
  - `budget_exhausted`：对应资源预算已耗尽；
  - `circuit_open`：健康门或熔断器拒绝继续调用；
  - `resource_rejected`：有界执行资源或队列拒绝接纳；
  - `deadline_exceeded`：本轮总 deadline 已耗尽；
  - `cancelled` / `superseded`：任务被关停或尚未开始的旧 pending 被更新输入替换；
  - `persistence_error` / `corrupt_snapshot`：持久化失败或快照完整性校验失败。
- retry、fallback 和 source switch 必须由失败类别、剩余 deadline、调用幂等性和健康门共同决定；禁止对 schema、身份冲突、预算耗尽或已过 deadline 的请求盲目重试。
- 任何外部源失败都必须记录有界且脱敏的来源、发生时间、稳定失败码、尝试次数、是否启用 fallback、最近有效快照年龄和当前可用性；不得记录密钥、完整载荷或完整第三方异常文本。
- 失败不得直接以异常或 JSON 字典穿透到评分逻辑，必须投影为不可变的有类型状态；上层按 `available`、`degraded`、`unavailable` 等明确状态决定保留最近有效结果、跳过可选增强或返回 `not_ready`。
- 预算和健康门由具体资源所有者持有，不能建立一个模糊的全局预算中心：DeepSeek 共享适配器拥有每日物理请求总账以及预热、emergency 独立原子预算桶，行情来源分别拥有自己的熔断与健康状态。
- 负缓存的身份、有效期和清除规则统一见 3.5.9，本节不重复定义缓存实现。

#### 3.5.7 受限执行资源与工作池
- 所有线程池、工作池和提交队列必须显式有界，并公开固定 worker 数、普通/urgent 队列容量、在途数、已提交数、完成数、拒绝数和关停状态。
- `BoundedExecutor` 作为运行时执行 primitive 提供普通车道和可选 urgent 车道；urgent 只服务冻结、检查点、结算等短控制任务，不得被普通长耗时任务占满，也不得无限抢占导致普通车道饥饿。
- 实时采集、历史下载、研究端点、DeepSeek 和持久化写入按资源特征分池，禁止使用无界全局执行器或在适配器内部隐藏创建线程。
- 队列已满、执行器未启动或正在关停时必须立即返回稳定的 `resource_rejected` 结果并计数，不得阻塞调用线程等待无限空间，也不得悄悄转为同步执行。
- 组合根显式创建并注入执行资源，`infra/runtime_resources` 只组合、暴露状态和协助停止，不成为全局服务定位器。
- 任务优先级、策略节拍、是否进入 urgent 车道及拒绝后的业务动作由应用运行时拥有；`infra` 只消费注入的执行能力并报告资源结果。

#### 3.5.8 源车道执行支撑
- 本节描述来源请求的执行合同，不把调度所有权移入 `infra`；来源 lane 的生命周期、latest-wins、deadline、取消和发布资格由现有运行时编排拥有。
- 每个物理来源必须拥有独立的有界并发、单个 latest-wins pending 槽、稳定来源身份和状态计数，避免一个慢来源耗尽全部执行资源。
- latest-wins 的唯一替换语义是：尚未开始的旧 pending 可以被更晚且身份兼容的输入替换；已经在途的请求允许有界完成，不通过强制取消破坏第三方客户端状态。
- 被替换任务必须形成 `superseded` 终态并完成等待者通知；旧在途结果返回后仍须通过交易日、sequence、输入身份和 CAS 校验，禁止覆盖新结果。
- 请求合并或 single-flight 只允许复用完全相同的来源、数据集、证券范围、观察点、Schema、配置身份和 deadline 语义；不得合并仅“看起来相似”但时间窗口或发布权限不同的请求。
- 同一调度观察点可共享一次全市场读取，但各策略继续独立执行候选、评分、冻结与发布判断；来源层不得根据策略排名裁剪基础行情。

#### 3.5.9 缓存
- 缓存按职责拆分为行情、历史、参考数据、DeepSeek、研究和只读投影等明确类型，不建立无所有者的通用业务缓存。
- 每个缓存必须具有有界条目数和逻辑字节数、确定性的 LRU/TTL 淘汰规则、分区容量、命中/未命中/淘汰/拒绝计数，并在单个分区满时只拒绝该分区，禁止清空其它缓存自救。
- 缓存 identity 至少绑定数据集、来源、主体、请求指纹、交易日或观察点、处理阶段、来源合同、配置身份和 Schema 身份；身份不完整时不得命中。
- 负缓存只用于已经实际尝试且具有稳定失败码的可重试失败，必须携带失败码、写入时刻、短 TTL 或 `retry_at`；尚未开始即取消或 superseded 的请求不得写入负缓存。
- single-flight 只合并完整 identity 相同的并发读取，首个执行者必须在成功、失败、超时和取消时都释放等待者；不得让异常 future 或回调引用永久占位。
- 缓存必须分别公开：
  - `source_age`：原始事实距当前观察点的年龄；
  - `entry_age`：缓存条目进入缓存后的年龄；
  - `expires_in`：距离过期或允许重试的剩余时间。
- 决策或动作年龄不由缓存推断；`decision_age` / `action_age` 由应用层根据决策观察点、生成、冻结和发布时间计算，缓存只能提供上述原始年龄事实。
- 刷新失败时保留仍满足有效期和身份合同的最近有效值，并同步暴露失败；禁止用负缓存条目、空值或失败时间覆盖原始成功时间。

#### 3.5.10 规范序列化与内容哈希
- canonical JSON 只用于持久化、缓存 identity、外部证据和内容寻址等明确序列化边界；进程内领域、应用和基础设施状态仍使用不可变有类型对象，不以 JSON 字典作为内部状态协议。
- 规范序列化必须固定 UTF-8、对象键排序、紧凑分隔符、枚举值、带时区时间格式、日期格式、Decimal 表达、集合顺序和空值规则；禁止依赖默认时区、浮点字符串或对象内存顺序。
- 内容哈希统一使用 canonical bytes 上的 SHA-256，但“同一种算法”不等于“同一个业务身份”：冻结记录、缓存键、配置快照、模型工件和研究证据分别定义自己的 owner、Schema 和参与哈希字段。
- 各 hash payload 必须按用途绑定必要的 Schema、配置、来源、交易日/观察点和父身份；凭证、访问令牌、机器绝对路径、原始异常和非确定性运行字段不得进入内容哈希。
- 读取时必须先按对应 codec 解析和校验，再比较内容哈希；哈希一致只证明内容身份，不自动授予评分、冻结、生产或发布权限。
- 内部状态对象不得定义 `as_dict()`、`to_json()` 或 `to_status()` 自行决定线格式；最终 Web/API/诊断 adapter 按公开字段白名单投影 JSON。

#### 3.5.11 原子写与进程锁
- 可替换运行状态采用“目标同目录临时文件 → 写入并 flush → 文件 fsync → 原子 replace → 必要时目录 fsync”的提交顺序；任一步失败都保留旧有效文件。
- 冻结记录、证据 manifest 和其它不可变工件采用 create-or-conflict：同键同内容幂等，不同内容显式冲突；不得通过原子 replace 覆盖已经存在的正式记录。
- 文件提交前后均校验 Schema、内容哈希和父身份；临时文件、sidecar 或 staged manifest 只服务恢复，不得成为第二套可读活动状态。
- 进程锁和维护锁必须明确锁定范围、持有者摘要、获取 deadline、释放责任和冲突错误；不得无限等待，也不得仅凭陈旧 PID 自动删除无法确认归属的锁。
- 单实例保护由 entrypoint 在启动资源前获取并在最终关停阶段释放；`infra` 提供跨平台锁 primitive 和有类型结果，不自行决定是否启动第二实例。
- 组合根、`create_app()` 和只读 HTTP 请求不得在导入或应用创建阶段获取进程锁、启动线程或写文件。

#### 3.5.12 可关停资源与生命周期协作
- 每个外部客户端、执行器、来源 lane、写入器和数据库资源必须提供幂等的停止/关闭能力、剩余在途状态和有界等待结果；重复调用不能抛出新的生命周期错误。
- 应用运行时拥有统一关停 deadline 和停止顺序，典型顺序为：停止接纳新周期 → 关闭 pending 提交 → 在剩余 deadline 内完成或放弃在途任务 → 提交必要检查点/flush 写入器 → 停止执行器 → 关闭网络与数据库客户端。
- 所有步骤共享同一个递减的关停 deadline，禁止每个资源重新获得完整超时；超时后必须返回未停止资源、在途数和稳定失败码，不得无限 `join`。
- entrypoint 负责 SIGINT/SIGTERM 等 OS 信号协调、退出码和单实例锁释放；`infra` 不注册隐藏信号处理器，Web 请求也不触发进程关停。
- 关停期间拒绝的新任务必须表现为明确的 `cancelled` 或 `resource_rejected`，不得重新启动已停止执行器或在退出路径创建备用线程。

#### 3.5.13 延迟瀑布与探测点
- 14 层实时荐股链路的所有 `latency_ms` 必须来自同一个有界 `LatencyWaterfall` 数据源，禁止每个模块另建不一致的计时和统计口径。
- 各 adapter 在自己拥有的边界记录开始、结束、结果和稳定失败码；应用运行时负责把来源排队、供应商调用、规范化、合并、候选提交、评分排队、数据准备、本地评分、风险、融合、动作门、发布和 SSE 入队串成完整阶段瀑布。
- 时长统一使用单调时钟计算，业务时间使用注入的上海时区时钟记录；超时、取消、superseded、拒绝和降级同样必须闭合 span，禁止只记录成功路径。
- 每个探测点至少关联 `run_id`、`trace_id`、`stage_id`、`input_identity`、`output_identity`、开始/结束时刻、`latency_ms`、输入/输出计数、结果状态和失败码，并与第 4 章各层输入/输出/失败降级/Web 观测点保持一致。
- Web/API 和 `scripts/` 诊断脚本只读取同一有类型诊断快照的白名单投影；公开状态只保留有界的 count、P50、P95、max、队列等待、替换和拒绝计数，不暴露证券明细、原始样本、密钥或完整外部错误。
- 探测不得改变业务结果、触发现场抓取或同步写盘；监控消费者缓慢或失败时只能丢弃监控事件并计数，不能阻塞推荐主链路。

#### 3.5.14 配置与凭证
- 普通配置与凭证严格分级：策略阈值、数据源优先级、容量、TTL、deadline 和功能开关属于可验证普通配置；访问令牌、API key 和账号材料属于凭证。
- 普通配置必须通过单一 settings 入口解析为不可变有类型对象，校验必填项、范围、枚举、未知键和跨字段约束；配置文件路径由 entrypoint 明确传入，不允许业务模块散落读取环境变量或文件。
- 配置快照和配置内容哈希只包含允许审计的普通配置，不包含凭证值；配置增加公开字段时必须同步更新解析、Schema、诊断白名单和契约测试。
- 凭证只允许来自环境变量或权限安全的专用凭证文件，并由组合根读取后注入具体 adapter；不得写入普通配置、数据库、快照、决策记录、研究证据、缓存 identity、API、SSE、日志或异常文本。
- 状态投影最多公开凭证是否配置、脱敏来源类别和最近校验状态，禁止公开值、前后缀、完整文件路径或可用于推断凭证的信息。
- 缺少可选凭证时只降级对应增强能力并保留本地推荐；缺少启动所必需的普通配置或配置校验失败时应在创建后台资源前失败关闭。
- 未明确设计并验证原子切换前不支持隐式热重载；配置变化必须形成新的不可变配置身份，并只影响随后启动或明确接纳的新周期。

### 3.10 模块边界总原则

- 下载、训练和荐股三个业务内部固定依赖方向为 `entrypoints / infra -> application -> domain`，不得反向导入；
- `domain` 只定义纯业务规则、不可变值对象和确定性计算，不读取配置、时钟、网络、文件或数据库；
- `application` 只负责编排用例和端口，不隐藏创建外部客户端，也不直接依赖 Flask；
- 各业务线内的 `infra` 适配本线外部依赖，顶层 `infra` 只承载跨业务线的公共技术能力；
- `http_api` 和 `web` 仅属于荐股交付边界，只读取 `recommendation/application/` 发布的快照与诊断状态；HTTP 请求不得抓行情、评分、训练或调用 DeepSeek；
- `bootstrap.py` 是唯一组合根，显式装配客户端、端口和资源，不使用全局服务定位器；
- 进程内状态使用有真实字段类型的不可变对象；JSON 只存在于配置、供应商解析、持久化 codec、事件载荷和 HTTP 投影边界；
- 模块之间只通过明确接口、DTO、快照或事件通信，不共享可变状态，不保留双实现、隐藏回退或第二套目录所有权。

## 4. 实时荐股链路分层设计

本节固定为一条自数据进入到正式发布的 14 层链路，不再保留合并层、重复层或第二套编号。

### 4.1 第 1 层：数据源

目标：统一接入实时行情、历史行情、证券主数据以及公告、财务、监管和新闻等结构化来源；本层只负责取得原始事实并标注来源，不执行清洗、过滤、评分或风险结论。

输入：

- 已由组合根显式注入的供应商客户端、来源策略、交易日历和超时配置；
- 最近一次校验通过的来源快照及其快照身份；
- 当前评估时刻 `as_of` 和本次采集批次身份。

输出：

- 按数据类别分开的原始数据批次，每批携带 `source_name`、`requested_at`、`received_at`、供应商数据时间和批次身份；
- 每个来源的可用性、新鲜度、接收记录数和错误类别；
- 主源、备用源及最近有效快照的选择结果，但不隐藏实际使用的来源。

失败降级：

- 主源超时、协议错误或载荷校验失败时，按既定来源策略尝试备用源，并显式标记 `degraded`；
- 当前来源全部不可用但存在最近有效快照时，保留该快照并公开其年龄和降级原因，不把旧数据伪装成实时数据；
- 当前来源全部不可用且没有有效快照时，输出 `not_ready`，后续层不得以空数据伪造业务淘汰或正常空推荐；
- 本层不得用默认值、空字符串或补造记录掩盖供应商缺失。

Web 观测点：

- 各来源健康状态、主源与实际使用来源、备用源是否启用；
- 最后成功时间、当前数据年龄、请求耗时和接收记录数；
- 最近有效快照身份，以及 `ready`、`degraded`、`not_ready` 状态和原因摘要。

层内探测点：

- 供 `scripts/` 诊断脚本读取来源 ID、采集批次身份、请求起止时间、耗时、接收行数和供应商数据时间范围；
- 记录错误类别、校验失败数、是否切换备用源、最终选用来源和最近有效快照身份；
- 只输出有界脱敏摘要，不记录密钥、完整外部请求、完整响应或逐股原始载荷。

### 4.2 第 2 层：静态采集

目标：在启动和规定刷新周期内采集全市场相对稳定的证券事实，形成完整的静态原始集合；本层不做字段标准化和资格过滤。

输入：

- 第 1 层输出的证券主数据、市场分类、行业与长期风险事实原始批次；
- 当前交易日、评估时刻和静态刷新策略；
- 上一次静态采集批次的身份与完成状态。

输出：

- 以来源证券代码关联的静态原始记录，包含名称、交易所、候选板块、上市日期、长期交易资格、行业和来源时间；
- 本批预期代码数、接收行数、唯一代码数、重复记录数和缺失记录数；
- 静态采集批次身份及各来源覆盖摘要。

失败降级：

- 单一来源或非关键字段缺失时保留已验证字段和显式缺失证据，继续交给质量评估按合同扣分，不得填造默认值；
- 无法确定证券代码、交易所或候选板块等关键身份时输出 `not_ready`，不得提前记为一级过滤淘汰；
- 刷新失败时保留最近有效静态批次，显式报告批次年龄和 `degraded`，不得覆盖旧有效批次。

Web 观测点：

- 全市场预期数、接收数、唯一代码数、重复数、缺失数；
- 主板、创业板、科创板的原始记录数及板块待确认数；
- 静态批次生成时间、数据年龄、覆盖率和降级原因。

层内探测点：

- 供 `scripts/` 诊断脚本读取输入批次身份、原始行数、去重前后数量、未知代码数和板块无法识别数；
- 记录关键字段覆盖率、来源覆盖率、采集耗时、最后成功批次和失败来源；
- 探测输出只保留计数与脱敏身份，不输出全量证券原始载荷。

### 4.3 第 3 层：静态清洗

目标：把各来源静态记录转换为字段、类型、枚举、单位和缺失语义唯一的标准证券快照，为一级稳定过滤提供同一数据契约。

输入：

- 第 2 层静态原始记录及来源元数据；
- 证券代码、交易所、板块、上市状态和长期资格的规范化规则；
- 当前评估时刻与静态批次身份。

输出：

- 以 `code` 唯一标识的 `StaticSnapshot`；
- 规范化后的 `exchange`、`board=main|gem|star`、上市日期、交易资格元数据、行业及来源证据；
- 重复、冲突、无法转换和缺失字段的有类型清洗结果。

失败降级：

- 非关键字段无法转换时保留显式缺失编码并标记 `degraded`；
- 代码、交易所、板块或来源时间冲突且无法裁决时进入 `data_pending`，不得交给一级过滤；
- 本轮清洗整体失败时保留最近有效标准快照，并公开旧快照年龄，不允许回退为供应商原始字典。

Web 观测点：

- 清洗输入数、成功数、待补充数、冲突数和无效数；
- 各板标准化后的证券数、关键字段覆盖率和快照年龄；
- 主要转换错误类别及受影响记录数。

层内探测点：

- 读取输入/输出批次身份、字段转换成功数、枚举映射失败数、重复合并数和跨源冲突数；
- 记录每类关键字段的缺失计数、清洗耗时及最近有效输出身份；
- 允许定位到字段类别和脱敏证券代码，不输出完整供应商载荷。

### 4.4 第 4 层：一级稳定过滤

目标：依据长期资格事实排除稳定不参与策略的证券，形成可周期复用、可审计的一级资格集合。

输入：

- 第 3 层输出的标准 `StaticSnapshot`；
- 交易所与板块范围、上市交易日龄、退市事实、稳定黑名单和长期风险证据；
- 带 `as_of` 的一级资格规则和最近有效排除名单。

持久化与刷新合同：

- 一级资格事实与稳定排除名单由 `recommendation/infra/persistence/eligibility_ledger.py` 中的单一追加型 `EligibilityLedger` 持久化，不把每轮过滤的临时集合另存为第二状态源；
- 启动时先恢复 schema、内容身份、生效时间、有效期和覆盖范围均校验通过的最近快照，不为等待网络而阻塞荐股启动热路径；
- 权威来源同步在后台按计划增量刷新；快照过期、覆盖不足或身份校验失败时必须进入 `data_pending` 或 `not_ready`，不得以“稳定”为由永久停止网络刷新；
- Web 只读取应用层内存中已接纳的资格聚合状态，不在 HTTP 请求中现场查询 SQLite 或触发刷新。

输出：

- 通过一级资格的静态证券集合；
- 以 `code` 索引的稳定排除名单，包含首个拒绝原因、证据身份和更新时间；
- 本层输入数、通过数、业务拒绝数和数据待补充数。

失败降级：

- 只有完整可信事实确认违反长期规则时才记为业务拒绝；
- 关键资格事实缺失或名单过期时进入 `data_pending` 并触发刷新，不得当作业务淘汰；
- 排除名单读取失败时使用仍在有效期内的最近快照并标记 `degraded`；没有有效快照时本层为 `not_ready`。

Web 观测点：

- 一级过滤输入、通过、拒绝、待补充数量和过滤率；
- 按原因聚合的长期拒绝数量、排除名单年龄和最近更新时间；
- 业务拒绝与数据待补充必须分开展示。

层内探测点：

- 读取规则身份、输入快照身份、命中原因计数、首个拒绝边界和名单读写状态；
- 记录缓存命中数、重新计算数、待刷新数、执行耗时和输出快照身份；
- 支持按脱敏 `code` 查询拒绝原因与证据摘要，不回传完整风险原文。

### 4.5 第 5 层：动态采集

目标：只针对一级资格通过的证券采集当前行情、分钟信号和策略所需历史窗口，并保留真实时点和来源身份。

输入：

- 第 4 层通过的 `code` 集合及其静态快照；
- 第 1 层可用行情来源、交易日历和当前评估时刻；
- tomorrow、d25 及所选评分档位声明的行情字段和历史 session 要求。

输出：

- 未清洗的全市场当前行情、候选定向行情、分钟信号和前复权日线窗口；
- 每只证券的请求状态、来源时间、接收时间、历史覆盖 session 和缺失字段；
- 动态采集批次身份以及各来源、各板成功率。

失败降级：

- 分片或单股失败时只标记受影响证券为 `refresh_pending`，不得丢弃其它已成功证券；
- 主源失败时按来源策略切换备用源；只有时间仍有效的最近快照可以复用，并必须标注年龄；
- 全部动态来源不可用且无有效快照时输出 `not_ready`，不得用收盘价、零值或未来数据补造盘中输入。

Web 观测点：

- 请求证券数、成功数、部分成功数、待刷新数、超时数和过期数；
- 各来源、各板成功率，最新来源时间和历史覆盖分布；
- 当前批次是否使用备用源或最近有效快照。

层内探测点：

- 读取请求批次、分片身份、请求/成功/失败代码数、队列等待、供应商耗时和总耗时；
- 记录动态数据最早/最晚来源时间、历史最短/最长 session、失败类别和备用源切换结果；
- 探测只输出有界代码样本与计数，不输出完整逐股行情载荷。

### 4.6 第 6 层：动态清洗

目标：把当前行情、分钟信号和日线窗口转换为同一时点、同一单位、同一缺失语义的动态标准对象。

输入：

- 第 5 层输出的原始当前行情、分钟数据和前复权日线窗口；
- 第 3 层标准 `StaticSnapshot`；
- 价格、成交量、成交额、比例、时间戳、复权和异常值规范。

输出：

- 标准 `DynamicSnapshot`、`IntradaySignal` 和 `DailyFeatureWindow`；
- 同一证券同一评估周期的统一 `as_of`、来源时间、质量状态和缺失字段集合；
- 字段冲突、陈旧、越界值和时间不一致的清洗证据。

失败降级：

- 字段无法转换但证券、来源和时点身份可信时保留显式缺失与严重度，继续交给质量评估；关键缺失最终在评分层扣至 0 分；
- 评估时刻、证券身份、来源身份或复权身份冲突时进入 `refresh_pending`，不得借用缺失扣分语义继续；
- 清洗失败不得回退为原始供应商对象；可继续使用的最近有效标准快照必须公开年龄。

Web 观测点：

- 动态清洗输入数、成功数、降级数、待刷新数和无效数；
- 时间不一致、跨源冲突、异常值和关键字段缺失的聚合计数；
- 各板标准动态快照数量及最新 `as_of`。

层内探测点：

- 读取输入/输出批次身份、字段解析失败数、单位转换数、重复合并数和时间冲突数；
- 记录快照时间跨度、关键字段覆盖率、清洗耗时和最近有效输出身份；
- 支持定位转换阶段和字段类别，不记录完整逐股原始数据。

### 4.7 第 7 层：二级动态过滤

目标：按策略在当前评估时点执行交易状态、流动性、波动和异常行情硬过滤，得到可以进入候选生成的合格集合。

输入：

- 第 6 层标准动态对象及第 4 层一级资格结果；
- tomorrow、d25 各自的动态硬过滤规则、评估时刻和交易日历；
- 当前来源健康与数据新鲜度状态。

输出：

- 按策略和板块组织的动态资格集合；
- 每只被拒绝证券的首个动态拒绝原因与证据；
- 身份可信但字段缺失、需要继续进入质量评估和评分归零的 `quality_pending` 集合；
- 独立的待刷新集合，不与业务拒绝或 `quality_pending` 混写。

失败降级：

- 只有完整可信输入确认违反当前规则时才进入动态业务拒绝；
- 身份可信且仅字段缺失时进入 `quality_pending`，后续按严重度扣分；数据陈旧、来源失败或身份冲突时进入 `refresh_pending`，不增加业务拒绝数；
- 某板数据不足时只标记该板状态，不降低其它板门槛，也不为了页面非空放宽规则。

Web 观测点：

- 各策略、各板输入数、通过数、业务拒绝数、`quality_pending` 数和待刷新数；
- 动态拒绝原因、首个阻断原因、数据新鲜度和降级状态；
- 业务漏斗与数据就绪漏斗必须分开展示。

层内探测点：

- 读取策略、板块、规则身份、输入快照身份、逐原因命中数和首个拒绝阶段；
- 记录业务拒绝、`quality_pending`、数据待刷新、通过数量及执行耗时；
- 可按脱敏代码复核单股首个拒绝原因，不重复记录后续未执行规则。

### 4.8 第 8 层：候选生成

目标：把二级动态过滤通过的证券组织成可评分候选，并在评分前实施确定性的分策略、分板预选上限；同时把可信缺失记录作为不可执行的质量审计输入送入评分归零链。

输入：

- 第 7 层按 tomorrow、d25 和 `main|gem|star` 划分的动态资格集合及 `quality_pending` 集合；
- 候选排序事实、稳定同分规则和每策略每板预选上限；
- 标准静态、动态快照身份和当前评估时刻。

输出：

- tomorrow 与 d25 分别拥有 `main`、`gem`、`star` 三个候选桶；
- 每策略每板最多 120 只预选候选，每策略三板合计最多 360 只；
- 每桶的有序候选、未入选储备、截断原因和候选批次身份；
- 每桶另带不占 120 个可执行预选名额的 `quality_pending` 审计输入；这些记录只用于形成可观测的质量扣分和 0 分结果，不能进入模型、DeepSeek 或动作升级。

失败降级：

- 某板不足 120 只时保留全部合格证券，不从其它板补足，也不降低过滤或质量门槛；
- 输入可信但无合格证券时输出可审计的业务空候选；输入不可信时保持 `not_ready`；
- 候选生成失败不得影响上一份有效候选快照，也不得直接生成正式推荐。

Web 观测点：

- 各策略、各板进入候选生成的数量、预选数量、储备数量和上限截断数量；
- 每策略合计候选数、候选批次时间和是否降级；
- 空候选必须区分“真实无合格证券”和“上游数据未就绪”。

层内探测点：

- 读取策略、板块、输入快照身份、排序规则身份、上限和稳定同分键；
- 记录截断前后数量、储备数量、边界同分数量、执行耗时和候选批次身份；
- 允许诊断脚本验证同一输入产生相同候选顺序，不输出完整候选行情载荷。

### 4.9 第 9 层：质量评估

目标：逐股确认静态、动态、历史和特征字段是否满足对应策略与评分档位的输入合同，并生成评分层唯一可消费的缺失严重度与质量扣分证据。

输入：

- 第 8 层预选候选、`quality_pending` 审计输入及其静态、动态、历史窗口；
- tomorrow、d25 与 V2/V3 对应的必需字段、最少 session、字段年龄和缺失严重度合同；
- 当前评估时刻和候选批次身份。

输出：

- 每只候选的 `QualityAssessment`，包含缺失字段、字段年龄、历史覆盖、最高严重度、`quality_penalty` 和 `model_input_eligible`；
- `ready`、`degraded`、`critical_missing`、`refresh_pending`、`invalid` 五类有类型结果；
- 一般缺失按档位合同给出确定性扣分；关键缺失固定 `quality_penalty=100`，使评分层结果归零，并禁止模型、DeepSeek 与动作升级。


失败降级：

- 字段真实缺失但来源身份可信时按严重度进入评分扣分；关键缺失不补默认值、不执行模型推理，最终基础分固定为 0；
- 来源批次不可信、时点陈旧、身份冲突或质量评估本身失败时进入 `refresh_pending` 或 `invalid`，不能伪装成普通字段缺失；
- 缺失严重度和扣分值只能来自所选档位的已版本化合同，不得在运行中临时改变权重。

Web 观测点：

- 各策略、各板候选总数、完整输入数、一般缺失数、关键缺失归零数、待刷新数和无效数；
- 缺失字段、历史不足、陈旧和合同不匹配的原因聚合；
- 当前策略与评分档位要求的历史 session 和字段覆盖率。

层内探测点：

- 读取策略、评分档位、候选批次、字段合同和特征 manifest 身份；
- 记录必需字段覆盖、可选字段覆盖、历史 session 分布、各质量终态数量和评估耗时；
- 支持定位单股缺少的字段身份及严重度，不输出原始行情或模型工件内容。

### 4.10 第 10 层：评分

目标：生成可解释的规则分、质量扣分后的基础分与模型诊断，并按评分档位、策略和板块形成互相隔离的评分组；本层不产生最终名次或 TopK。

输入：

- 第 9 层候选、标准特征向量和 `QualityAssessment`；
- 规则评分组件、V2/V3 档位身份及其 tomorrow、d25 模型头；
- 第 8 层每策略每板最多 120 只的预选候选和稳定同分规则。

评分与独立组规则：

- 规则评分先产生统一 0–100 标尺的 `raw_base_score`，再计算 `base_score = clamp(raw_base_score - quality_penalty, 0, 100)`；关键缺失固定得到 0 分；
- 缺失字段必须先按用途分流，不得把所有缺失都伪装成评分扣分：

| 缺失字段或用途 | 严重度 | `quality_penalty` | 处理结果 |
| --- | --- | --- | --- |
| `code`、`as_of`、`source` 或证券/批次身份冲突 | 身份无效 | 不适用 | 进入 `refresh_pending` 或 `invalid`，不创建评分记录 |
| `exchange`、`board`、`listed_date`、`delisted`、`blacklist`、`long_term_risk`、`price`、`prev_close`、`trading_status`、`price_limit` 或策略必需历史覆盖 | 过滤/就绪前提不足 | 不适用 | 进入 `data_pending`、`refresh_pending` 或 `invalid`，不进入评分 |
| 所选档位与策略明确标为必不可少的规则评分输入 | `critical` | `100` | `base_score=0`、`model_input_eligible=false`，禁止模型、DeepSeek 和动作升级 |
| `return_30m`、`volume_ratio`、`closing_position`、`change_5m`、`speed_5m`、移动均线、`atr`、`volatility`、`drawdown` 或 `liquidity_score` 中被档位合同声明为可降级的评分组件 | `major` 或 `minor` | 该组件在所选档位中的最大可得分 | 保留规则评分并记录缺失证据；最大可得分不小于 10 时为 `major`，小于 10 时为 `minor` |
| `industry` 或工件 manifest 声明的其他仅模型必需输入 | `model_only` | `0` | 保留本地规则分，设置 `model_input_eligible=false`，不伪造模型预测 |
| `name` 或仅用于展示/诊断的可选字段 | `informational` | `0` | 保留显式缺失，不改变任何分数 |

- V2/V3 的 Tomorrow/D25 档位合同必须逐字段登记所属用途、严重度、组件最大可得分和模型输入资格，不得在运行时依字段名猜测。
- 同一缺失事实只取最高严重度，同一评分组件最多扣除一次；不同组件扣分求和后以 `100` 为上限。
- 模型头只读取本策略、本档位的固定特征合同；`model_input_eligible=false` 时不调用模型，也不补造中性预测；
- “规则 + 模型结合”表示二者进入同一档位评分记录，由档位合同明确模型预测、分歧和成本门的作用；不得把两个来源简单相加，也不得让模型结果覆盖规则证据；
- 同时选择 V2 与 V3 时形成 `V2/V3 × tomorrow/d25 × main/gem/star` 共 12 个 `ranking_group`；只选择一个档位时形成对应 6 个组；
- 同一策略同一板块的最多 120 只预选候选分别送入 V2、V3 对应组，两个档位共享输入事实但不共享模型输出对象；
- 各组分别评分并保留完整评分记录供风险、动作和最终选择使用；最终稳定名次和 TopK 只能在第 14 层产生；
- 组间禁止混排、借位或用另一档位补缺；两个档位同时运行时各自形成完整且隔离的发布结果。

输出：

- 每个独立评分组包含 `ranking_group`、候选数、原始规则分、质量扣分、基础分、模型诊断和档位/模型身份；
- 未进行 V2/V3 并行评估时，只输出显式选择档位对应的 6 个组，不伪造另一档结果；
- 风险前评分记录，不在本层执行 DeepSeek 融合、动作门、集中度或冻结。

失败降级：

- 启动加载或工件校验失败属于所选集合原子启动失败，不能进入本层；
- 合法启动后的单次在线推理超时或失败时保留该次规则结果，标记 `model_inference_degraded`，不得静默切换档位或模型头；
- 可信缺失按质量合同扣分，关键缺失归零；不可信批次、身份冲突或评分器故障不得借用归零语义伪装正常评分。

Web 观测点：

- 每个已加载组分别显示预选数、完整输入数、关键缺失归零数、规则评分数、模型成功数和推理降级数；
- 展示档位、策略、板块、模型身份、评分完成时间和降级状态；
- V2/V3 结果必须分栏或按组切换，不提供跨档混合总榜。

层内探测点：

- 读取 `ranking_group`、候选批次、特征 manifest、档位、模型头和规则配置身份；
- 记录每组输入数、规则评分数、模型评分数、关键缺失归零数、失败数、同分数量和耗时；
- 生成稳定排序摘要以复核相同输入的顺序一致性，不输出完整模型载荷或全量逐股特征。

### 4.11 第 11 层：风险复核（含 DeepSeek）

目标：对风险前评分结果执行一次且仅一次的本地风险处理，并用符合时序和 schema 的 DeepSeek 结构化证据进行可选复核。

输入：

- 第 10 层各排序组的评分记录和结构化因子证据；
- 当前时点本地风险事实、严重风险规则及其互斥组；
- 不晚于评估时刻的公告、财务、监管、新闻证据 manifest，以及 DeepSeek 预算和 deadline。

输出：

- `local_risk_penalty`、本地 veto 和风险证据，并计算 `local_score = clamp(base_score - local_risk_penalty, 0, 100)`；
- 经 schema、时序和证据身份校验的 `deepseek_score`、`deepseek_risk_penalty`、结构化风险事实或 `abstain`；
- 每组风险通过、降级、观察终态和否决结果；自由文本不进入扣分或排序。

失败降级：

- DeepSeek 超时、失败、预算耗尽、证据不足或返回 abstain 时保留 `local_score`，不得阻塞本地推荐；
- 本地风险事实缺失时按风险合同进入保守观察或不可执行状态，不得假设“无风险”；
- DeepSeek 每日物理 HTTP 请求全局上限保持 168，失败和重试同样计数，不得为单组另开预算。

Web 观测点：

- 各组本地风险扣分数、veto 数、DeepSeek 应用数、abstain 数、失败数和预算状态；
- 风险原因只展示结构化事实摘要、证据时间和稳定证据 ID；
- 明确显示当前结果是 local-only 还是等待融合的 hybrid 输入。

层内探测点：

- 读取排序组、评分记录、风险规则、证据 manifest、预算桶和 deadline 身份；
- 记录本地风险命中、互斥合并、DeepSeek 请求/缓存/单飞命中、schema 拒绝、迟到和 abstain 数；
- 不记录提示词、自由文本、密钥或完整外部请求响应。

### 4.12 第 12 层：固定 68/32 融合

目标：在风险复核完成后，按唯一固定公式生成可进入动作判断的最终分数，并保留 local-first 降级语义。

输入：

- 第 11 层已经扣除本地风险一次的 `local_score`；
- 合法 `deepseek_score`、`deepseek_risk_penalty` 及结构化证据校验状态；
- 排序组、评分档位、策略、板块和风险记录身份。

输出：

- hybrid 可用时计算 `clamp(local_score * 0.68 + deepseek_score * 0.32 - deepseek_risk_penalty, 0, 100)`；
- 使用十进制定点规则和 `ROUND_HALF_UP` 得到两位小数 `final_score`；
- 输出 `hybrid` 或 `local_only` 融合模式、公式输入项和结果身份。

失败降级：

- DeepSeek 不可用、迟到、预算耗尽或证据不合法时固定 `final_score = local_score`；
- 融合时禁止再次扣除 `local_risk_penalty`，也不允许自由文本改变分数；
- `local_score` 本身不可用时本记录不得融合，不能以 DeepSeek 分数单独生成推荐。

Web 观测点：

- 各组 hybrid 数、local-only 数、融合失败数和完成时间；
- 展示 `local_score`、合法 DeepSeek 分项、风险扣分和 `final_score`，同时标明融合模式；
- 不向页面暴露原始 DeepSeek 文本。

层内探测点：

- 读取排序组、风险记录身份、三个公式输入项、融合模式和舍入结果；
- 记录 hybrid/local-only 数、clamp 命中数、证据拒绝数、重复本地风险扣分保护和耗时；
- 允许用固定向量复核公式结果，不记录外部模型完整载荷。

### 4.13 第 13 层：下行保护与动作门

目标：根据最终分数、结构化风险、成本净效用和不确定性决定正式、观察或不行动，不再产生新的正向评分。

输入：

- 第 12 层 `final_score` 及融合模式；
- 第 11 层风险 veto、严重亏损事实、模型分歧和不确定性；
- 交易成本、容量、可执行性事实及策略动作阈值。

输出：

- 每只证券的 `formal_eligible`、`watch_only`、`abstain` 或 `veto` 动作结论；
- 首个动作阻断原因、下行保护原因和稳定同分所需的约束证据；
- 按排序组保留的正式候选、观察候选和有序储备。

失败降级：

- 下行保护所需关键事实缺失时只能收缩为观察或不行动，不能升级为正式候选；
- 成本后效用非正、严重风险或合法 veto 必须阻止正式动作，但不得反向改写原评分；
- 单股或单组动作判断失败时保留最近有效结果并标记 `degraded`，其它组继续处理。

Web 观测点：

- 各组正式合格、仅观察、abstain、veto 数量和首个动作阻断原因；
- 下行保护、成本门、不确定性收缩和风险 veto 分开展示；
- 页面必须区分“分数较低”和“分数足够但动作门阻断”。

层内探测点：

- 读取排序组、融合记录、动作规则、成本和风险证据身份；
- 记录各动作终态数量、首个阻断门、阈值边界命中、储备补位资格和耗时；
- 支持诊断脚本定位动作门而不重新执行评分或修改动作状态。

### 4.14 第 14 层：TopK、集中度、冻结与发布

目标：在每个独立排序组内完成最终 TopK、集中度约束、正式/观察池形成、冻结和只读发布。

输入：

- 第 13 层各排序组的正式候选、观察候选和有序储备；
- 每组 TopK、组内行业/发行人集中度、稳定同分和补位规则；
- 上海时区可注入时钟、既有正式记录和持久化/发布端口。

输出：

- 每个已加载的“档位 × 策略 × 板块”组各自产生最终 TopK、观察项和选择证据；组间不混排、不借位、不设跨板全局 TopK，也不因其它板块空缺而扩大本组名额；
- 同时运行 V2 与 V3 时保留 12 组独立结果，只运行一个档位时保留对应 6 组；两个档位的冻结键、正式记录和发布身份完全隔离；
- 不可变正式记录、当前观察快照、发布快照和相应的冻结/发布身份。

失败降级：

- Tomorrow 与 D25 在 15:00 收盘价冻结；每个独立组的同日正式记录 first-wins，迟到结果不得覆盖；
- 同日正式记录缺失时，15:00 后只按既定当前决策或合法 `close_fallback` 规则创建一次，创建后不可覆盖；
- Long 只展示当前快照，不评分、不排序、不进入 TopK、不冻结、不写推荐历史；
- 持久化或发布失败时保留最近有效正式记录和只读快照，显式标记 `degraded`，不得让 Web 请求现场重算。

Web 观测点：

- 各档位、策略、板块组的最终 TopK、观察数、集中度剔除数、补位数和空缺数；
- 冻结状态、冻结时间、记录来源、发布版本身份和最近成功发布时间；
- 明确区分正式记录、观察快照、并行档位结果和 close fallback。

层内探测点：

- 读取排序组、动作记录、TopK/集中度规则、冻结时钟、既有记录和发布身份；
- 记录集中度拒绝、储备补位、最终选择、冻结 CAS 冲突、迟到丢弃、持久化和发布结果；
- 诊断脚本只读取已发布状态与有界选择摘要，不触发 TopK、冻结、写盘或重新发布。

## 7. 模块独立性与互不干扰约束

在重构时必须落实以下原则：

1. 无共享可变状态
   - 所有中间结果都必须是不可变类型对象。
   - 不允许一个模块直接写另一个模块中的缓存对象。

2. 无隐式依赖
   - 如果 A 模块要使用 B 模块的结果，必须通过明确的接口/DTO。
   - 禁止“读全局字典、拿到临时状态、直接判断是否存在字段”的方式。

3. 无跨层调用
   - `web` 不能调用 `infra`。
   - `application` 不能访问 `web` 和 `infra`。
   - `domain` 不能访问时钟、文件、数据库、HTTP 网络。

4. 事件驱动和快照控制
   - 业务链路以快照为主，阶段状态写入监控日志，不直接影响正式推荐结果。
   - 所有日志和状态都通过事件或快照投影，而不是直接改写业务对象。

5. 失败隔离
   - 单一来源失败只在存在身份、时点和有效期都合法的备用源或最近快照时降级；缺少可信输入时对应组为 `not_ready`，不能把空集合当作正常结果。
   - 启动期档位校验按所选集合原子失败；合法启动后的单次在线推理失败才允许保留规则结果并显式降级。
   - 失败时保留最近有效快照，并显式记录 `degraded` 和 `last_successful_snapshot`。

```python
    code: str                                               # 动作结论所属证券代码
    action: ActionState                                     # 正式、观察、abstain 或 veto 终态
    first_blocker: ActionBlocker | None                     # 首个动作阻断原因


@dataclass(frozen=True, slots=True)
class SelectionRecord:
    group: RankingGroupKey                                  # 最终选择所属独立组
    formal: tuple[SelectedDecision, ...]                    # 本组最终正式 TopK
    watch: tuple[SelectedDecision, ...]                     # 本组最终观察项
    concentration_rejected_count: int                       # 组内集中度约束剔除数
    replacement_count: int                                  # 本组储备补位数
    vacancy_count: int                                      # 本组无法合法补足的空缺数
```

这些类型分别拥有自己的语义；不得把模型分数命名为最终分，不得合并本地风险与 DeepSeek 风险，也不得由类型自身决定 JSON 线格式。

### 8.6 决策与 Long 快照

```python
@dataclass(frozen=True, slots=True)
class DecisionPool:
    group: RankingGroupKey                                  # 决策池所属独立组
    trade_date: date                                        # 决策对应交易日
    formal: tuple[SelectedDecision, ...]                    # 已冻结或待冻结的正式项
    watch: tuple[SelectedDecision, ...]                     # 当前观察项
    freeze_state: FreezeState                               # 未就绪、待冻结、已冻结或发布状态
    decision_identity: str                                  # 决策内容与父输入绑定的稳定身份


@dataclass(frozen=True, slots=True)
class LongSnapshot:
    as_of: datetime                                         # Long 当前快照对应的上海时区时刻
    items: tuple[LongMarketItem, ...]                       # 不含评分和排名的市场展示项
    snapshot_identity: str                                  # 当前快照内容身份
```

`DecisionPool` 只用于 Tomorrow 与 D25；每个档位 × 策略 × 板块组分别拥有正式池和观察池，不建立跨板总池。`LongMarketItem` 只包含当前市场事实与展示身份，不包含任何分数、名次、TopK、冻结或推荐历史字段。

### 8.7 `BoardMarketIndex`

实时标准数据固定按三板分桶，并在每个桶内以 `code` 为唯一索引：

- `as_of: datetime`：三个桶共同绑定的评估时刻；
- `main: Mapping[str, DynamicSnapshot]`：主板实时数据，键为 `code`；
- `gem: Mapping[str, DynamicSnapshot]`：创业板实时数据，键为 `code`；
- `star: Mapping[str, DynamicSnapshot]`：科创板实时数据，键为 `code`；
- `snapshot_id: str`：本次三板索引绑定的不可变快照身份。

结构约束：

- 三个桶及其内部映射在发布后均为只读，不允许评分、风险或 Web 在原对象上追加字段；
- 映射键必须等于对应快照的 `code`，同一 `code` 在同一 `snapshot_id` 下只能属于一个板块桶；
- 分桶只依据静态清洗后的规范 `board=main|gem|star`，未知板块进入待补充集合，不得猜测归类；
- 三个桶必须共享同一 `as_of`，动态清洗完成后一次性构建；后续层只读取索引，不重复复制三份股票列表；
- tomorrow、d25 的候选生成分别从该索引读取三板数据，并在各自策略、各板内实施最多 120 只预选。

- 依次迁移评分、风险复核、固定融合、下行保护/动作门、组内排序/集中度/TopK/冻结/发布；公式和排序只能由对应 recommendation domain owner 持有。
- 每个 `档位 × 策略 × 板块` 组独立形成最终 TopK，组间不混排、不借位；规则分、模型诊断、本地风险、DeepSeek 风险、融合、动作和选择保持阶段对象分离。
- 固定融合继续验证 `clamp(local_score * 0.68 + deepseek_score * 0.32 - deepseek_risk_penalty, 0, 100)`、`ROUND_HALF_UP` 和向量 `83.40`；本地风险只扣一次，DeepSeek 自由文本不直接扣分。
- Tomorrow/D25 15:00 收盘价 first-wins、15:00 后合法 `close_fallback`、迟到结果 CAS、重启恢复、哈希一致性和 Long 不冻结必须逐项覆盖；删除旧 decisions、scored、freezing 和 ranking owner。
- 退出条件：14 层端到端在应用层只有一条生产链，冻结记录与当前发布使用同一决策身份。

#### 阶段 8：迁移推荐基础设施、运行调度与模型加载

- 把行情业务适配、标准化、业务缓存、DeepSeek、推荐 SQLite、模型加载/推理迁入 `recommendation/infra/`；共享供应商 HTTP 客户端与参考 primitive 继续由顶层 `infra/` 注入，不重复创建连接池或线程池。
- 推荐加载器只从 `data/train/v2/{tomorrow,d25}/`、`data/train/v3/{tomorrow,d25}/` 读取；启动前对用户选择的全部档位和两个 head 原子校验，任一失败则所选集合不启动，在线单次推理失败才允许该次规则结果显式降级。
- 将 cadence、latest-wins、资源车道、deadline、停止顺序和状态聚合迁入 recommendation application/runtime 边界；DeepSeek 继续执行每日 168 次全局物理请求上限、独立预热/emergency 桶、缓存和 single-flight。
- 退出条件：推荐 application 不导入 infra，适配器没有隐藏客户端，启动失败与在线降级语义由直接组件/并发测试证明。

#### 阶段 9：拆出 `http_api/` 并保持 Web 主页行为

- 将 `web/api/` 的路由、请求校验、schema、SSE 和白名单投影迁入顶层 `http_api/`；`web/` 只保留 pages、widgets、templates 和 static 资源，页面路由由 `http_api/routes/page_routes.py` 唯一注册。
- 保持主页 Tomorrow、D25、Long、正式池、观察池和现有布局不变；按实际加载的 V2/V3 生成切换按钮，只新增“流水线监控”按钮及只读模态框。
- 模态框只显示候选、两级过滤、动态数据、质量、规则/模型评分、风险和融合聚合；不显示、复制或重排正式池/观察池，不返回未入选证券身份。HTTP 请求不得访问数据库、抓行情、评分、调用 DeepSeek 或写状态。
- 同阶段更新 API schema、GET、SSE 游标恢复/完整替换、ETag、JS 和三档桌面断言，删除 `web/api/` 和重复路由资源。
- 退出条件：API 与展示物理分离但都只属于 recommendation 交付边界，`create_app()` 仍无线程、无网络、无数据库和无文件写入副作用。

#### 阶段 10：收敛组合根、公开入口、包资源与数据布局

- `bootstrap.py` 只负责显式装配三个业务、推荐交付模块和共享 primitive；把状态构造、策略构造、数据初始化等业务逻辑移回 owner 后删除 `bootstrap_clock.py`、`bootstrap_data_plane.py`、`bootstrap_policy.py`、`bootstrap_status.py`，不得把它们简单内联成超大组合根。
- `entrypoints/cli.py` 与 `entrypoints/server.py` 继续对应 `trader-cli`、`trader-server`，并且都只调用 `bootstrap.py`；组合根按已解析命令延迟装配 `download/entrypoints/commands.py`、`training/entrypoints/commands.py` 或 `recommendation/entrypoints/commands.py` 的 runner。现有 research、history projection 和训练进度入口迁入对应业务，性能与可复用诊断迁入 `scripts/` 既有框架；根入口和业务命令模块都不得成为第二组合根。
- 更新 `pyproject.toml` 包资源，使 `http_api/`、新 Web 资源和必要模型合同进入 wheel，移除 V1、Today、旧 `web/api/` 和旧包路径资源。
- 固化一次性、可重入、失败关闭的数据迁移脚本，并只在仓库外隔离副本演练：校验当前 `data/history/baostock/` 的控制身份、月分片 hash、空间和权限，在旁路位置生成 `data/history/control.sqlite3 + partitions/YYYY/MM.sqlite3`；当前 `.runtime/trader` 中的冻结记录和 V2/V3 工件同样先校验身份再生成目标副本。脚本必须支持停服锁与最终原子切换，但本阶段不得触碰活动数据。运行时不双读、不双写，也不识别旧布局。
- 退出条件：两个公开入口从仓库外安装的 wheel 可运行并读取全部资源；迁移脚本在隔离副本完成正向、故障注入和回退演练，活动数据保持未变。

#### 阶段 11：删除旧活动树与执行全局命名清理

- 按第 10.3 节逐项证明旧 owner 已被新 owner 消费后，删除空的旧 `domain/`、`application/` 业务实现、业务型顶层 `infra/` 路径、`web/api/`、旧 bootstrap 辅助模块、旧测试夹具和旧静态资源；共享顶层目录只保留第 3.1 节允许项。
- 更新 `tests/contract/test_architecture.py` 为最终目录/依赖图，增加所有旧路径、Today、V1、复数 `profiles/`、跨板总榜和重复 API owner 的禁止清单。

### 10.5 切换、失败处理与回退边界

- 代码切换与数据切换是两个显式门。代码未通过阶段 12 且用户未单独授权维护窗口前不得触碰活动数据；阶段 10–12 只允许操作仓库外隔离副本。实际数据预检或迁移失败时继续运行旧 release 与其原数据，不得让新代码读取半成品。
- 新 release 首次启动只能读取新目录、新 schema 和新模型工件；旧 release 只能与完整旧运行目录和旧数据副本整体回退。V2/V3 新数据不得写回旧库，也不提供向下转换、运行时 fallback、双读或双写。
- 已冻结记录迁移必须逐条校验策略、档位、交易日、父输入和内容 hash；冲突、损坏或未知 schema 立即失败关闭，不能用空集合或重新评分覆盖。
- 回退通过切换完整 release 与匹配的数据快照完成，不使用破坏性 Git 命令，不在失败现场改写数据库。一次性迁移脚本的旁路输出和外部备份不属于活动读取面，验证结束后按交付记录中的保留/清理规则处理。
- 任何阶段若发现目标结构需要改变，先停止实现并回到本文件、`docs/01_评分逻辑.md` 和契约测试重新裁决；不得在代码中临时增加第六个业务目录、第二 API owner 或新的项目版本命名。

## 11. 结论

这次重构的关键，不是把项目“拆得更碎”，而是让下载、训练和荐股三个业务各自拥有明确边界、固定输入输出和可观测状态，同时让 HTTP 与 Web 仅作为荐股的外置交付模块。候选筛选、评分、风控、冻结和 Web 监控必须各司其职，任何一个环节发生问题都能直接定位，而不是让模块互相越界、互相污染。

最终目标是：

- 模块独立且不互相干扰。
- 候选筛选分层清晰，且每层都保留过滤证据。
- Web 能看到完整漏斗和过滤状态。
- 推荐链路既可维护，又可审计，也便于后续扩展与回归验证。

在实现阶段，所有新增模块都必须遵循上述边界；Web 监控必须准确说明“因何减少、减少多少、在哪一层停止”，但不公开或持久化未入选股票身份。
