# 项目重构详细设计

## 1. 项目评审结论

当前仓库已经具备较清晰的技术骨架：`src/trader` 中已形成 `domain / application / infra / web / entrypoints` 的分层雏形，`bootstrap.py` 也承担组合根职责，且 `web` 以只读 API 方式暴露状态。整体方向是正确的，但还需要进一步固化“模块职责边界”和“推荐漏斗可观测性”，避免后续各功能之间相互耦合、共享状态和隐式副作用。

重点结论：

- 业务必须按照“数据源 -> 静态数据采集 -> 静态数据清洗与特征构建格式统一 -> 一级稳定过滤 -> 动态数据采集 -> 动态数据清洗与特征构建格式统一 -> 二级动态过滤 -> 候选生成 -> 质量评估 -> 评分 -> 风险 -> 融合 -> 冻结/发布”的链路推进，不允许模块直接跨层读取别的模块的临时缓存。
- 清洗与格式统一必须尽早落在数据采集之后，保证后续所有过滤、候选生成、评分、风险、Web 监控都在统一 schema 下进行；这是整个推荐流程的前置契约，不属于后期特征工厂的延迟处理。
- 一级稳定过滤和二级动态过滤必须严格区分：前者解决“长期不具备参与资格”的问题，后者解决“当前时点不具备交易/风险条件”的问题；二级过滤对应大纲中定义的动态硬过滤，属于当前时点的硬筛选，不是最终推荐结果。
- 候选生成不是“临时缓存拼接”，而是“在全市场标准化数据上，完成稳定资格过滤、动态时点过滤、必要的特征准备，输出一个可进入评分流程的候选清单”。它只负责生成候选集合，不赋值最终推荐，不直接写 Web 视图，也不做评分和风控结论。
- 质量评估，是在采集到数据清洗与特征构建格式统一后，缺少某些字段，按照缺省字段的严重程度，在评分时进行相应的扣分处理。
- 风险，“在评分结果已经出来后，确认这只票有没有明显违反策略可交易前提和风险证据标准；如果有，就在融合前把它降级或剔除，否则不允许直接进入最终推荐。”。
- “下载 / 训练 / 实时荐股 / HTTP 服务 / Web 展示”必须作为独立能力块运行，彼此之间只通过明确 DTO、状态对象和持久化快照通讯；HTTP 服务只提供只读 API 与状态投影，不执行数据抓取、评分或 DeepSeek 请求。
- 每一层过滤都必须保留过滤上下文，Web 必须能看清：过滤前总数、过滤后数量、过滤理由、来源状态、耗时和降级状态。
- 评分和 Web 必须区分“业务状态”和“诊断状态”：Web 监控是只读观测，不允许参与业务决策。

## 2. 重构总目标

本次重构目标不是简单拆文件，而是把推荐链路建成一个可审计、低耦合、高可观察的分层系统，满足以下要求：

1. 各独立功能不能互相干扰
   - 下载数据、训练模型、实时荐股、Web 展示是四类不同生命周期。
   - 每个模块只负责自己的输入输出，不直接写入其他模块的运行态。
   - 任何共享对象都必须是不可变值对象，禁止跨模块附加临时字段。

2. 荐股链路采用分层设计
   - 层次必须清晰：数据源 -> 静态数据采集 -> 静态数据清洗与特征构建格式统一 -> 一级稳定过滤 -> 动态数据采集 -> 动态数据清洗与特征构建格式统一 -> 二级动态过滤 -> 候选生成 -> 质量评估 -> 评分 -> 风险 -> 融合 -> 冻结 -> 发布。
   - 每一层都必须具有独立输入、独立输出、独立错误处理和独立监控状态，确保问题能够在具体层级中定位，不跨层污染其他模块。
   - 其中：
     - 数据源负责统一进入链路的原始输入来源；
     - 静态数据采集负责全市场静态基础信息拉取；
     - 静态数据清洗与特征构建格式统一负责统一字段名、字段类型、时间格式、单位、精度、缺失值编码以及静态特征结构，形成稳定基础对象；
     - 一级稳定过滤负责长期排除缓存，处理停牌、退市、黑名单、风险名单、永久资格门槛等；
     - 动态数据采集负责当前时点行情与行为信号的获取；
     - 动态数据清洗与特征构建格式统一负责统一动态特征 schema 和时序规范，保证同一评估时刻数据一致；
     - 二级动态过滤负责当前时点硬过滤，处理交易状态、流动性、均线、波动率、异常行情和高风险波动等；
     - 候选生成负责将通过一、二级过滤的股票组织为“可进入评分的候选清单”；
     - 质量评估负责数据缺失与严重程度分级；
     - 评分负责本地和模型评分；
     - 风险负责策略风险和 DeepSeek 证据校验；
     - 融合负责固定 68/32 融合与降级；
     - 冻结负责时间冻结与正式池/观察池锁定；
     - 发布负责只读快照输出和 Web 展示。

3. Web 需要监控每次过滤情况
   - 每一层筛选必须留下统计：进入数量、剩余数量、剔除数量、剔除理由、剔除百分比、耗时、失败来源。
   - Web 页面只展示“可观测状态”，不能直接发起行情抓取、评分或 DeepSeek 请求。

4. 业务与运维状态分离
   - 业务状态：候选池、正式池、观察池、评分结果、冻结状态。
   - 诊断状态：过滤日志、降级状态、源健康、耗时、水位等。
   - 两类状态必须分别命名和持久化，避免一份状态对象同时承担业务决策和设备诊断。

## 3. 目录结构与模块化设计

本部分的重构目标不是沿用“现有实现目录”，而是建立三条明确的设计主线：

1. 主业务域：推荐业务本身必须成为一个清晰的核心域，而不是泛化的 `business`，例如 `recommendation/`；
2. 能力模块化：下载、训练、行情、筛选、评分、风险、Web 监控等作为独立能力栈；
3. 基础设施分层：时钟、缓存、配置、数据库、DeepSeek、行情适配器等作为公共基础设施。

重要原则：

- 不再使用 `business` 这种泛化命名；荐股本身就是主业务，所以主业务目录命名应当明确为 `recommendation/`；
- 业务链路和功能能力不能混用同一套目录命名；
- 目录设计必须与链路语义一一对应，能直接回答“这一步是哪一层、哪一个能力在做什么”。

### 3.2 能力模块化：按独立能力拆分

能力模块化必须服从 3.1 中确立的主业务线结构，并把 `V2` / `V3` 视为 `recommendation` 评分链路中的档位身份，而不是额外的顶层业务线。也就是说，能力拆分应当沿着“业务线 -> 能力块 -> 评分档位”三层展开，而不是再制造一套泛化的横向能力目录。

核心原则：

- `download/`、`training/`、`recommendation/` 是主业务线；
- `http_api/` 和 `web/` 是并行的接口与展示能力；
- `V2` / `V3` 是训练与评分的策略档位身份，不是独立业务线；
- `infra/` 负责统一公共适配；
- 能力模块的边界是“职责独立 + 数据契约清晰 + 生命周期分离”，而不是泛化能力目录。

- `V2` / `V3` 必须在 `training/` 与 `recommendation/` 的能力结构中体现为独立 profile 与 bundle 目录，而不是作为单独顶层模块出现；
- 每个能力块都必须具备独立输入、独立输出、独立错误处理、独立诊断状态和独立失败降级策略；
- 能力块之间不能直接共享可变状态，只能通过清晰的 DTO、快照、状态对象、事件对象通信；

  - `download/` 只负责历史归档与缺口补齐；

  - `web/` 只负责展示与监控；
  - `infra/` 只负责外部差异适配与通用基础设施。

#### 3.2.1 下载与训练能力边界

下载和训练必须作为独立能力块存在，且都不能直接参与实时荐股主链路，也不能直接写入推荐业务状态。训练能力中必须显式保留 `v2/` 和 `v3/` 的档位目录。

```text
src/trader/
  download/
    application/
      sync_service.py
      gap_fill_service.py
      archive_service.py
    infra/
      repository/
      persistence/
      history/

  training/
    application/
      training_pipeline.py
      export_service.py
      profiles/
        v2/
        v3/
      artifacts/
        v2/
        v3/
    infra/
      repository/
      profiles/
      artifacts/
```

核心要求：

- `download/` 只维护历史归档和缺口补齐，不修改实时推荐池；
- `training/` 负责生成 `V2` / `V3` 的独立训练产物，不影响实时推荐状态；
- `training` 中的 `v2/` 与 `v3/` 目录分别持有特征契约、模型 manifest 和输出 bundle；
- 两个能力块互不共享写锁，也不直接写入同一运行态对象；
- 训练产物只能作为 artifact 输出，不能与 Web 或实时荐股共用同一可写状态。

#### 3.2.2 推荐评分档位能力边界

在推荐链路中，`V2` / `V3` 不属于独立业务线，而属于模型评分能力的一部分：它们负责当前评估时刻选择哪一档评分 profile、加载哪一组模型 bundle，并输出对应的风险与排序结果。

```text
src/trader/
  recommendation/
    application/
      pipeline/
        model_score/
          profile_identity.py
          loader/
            v2/
            v3/
          predictor.py
```

核心要求：

- `recommendation/application/pipeline/model_score/loader/v2` 与 `loader/v3` 分别处理对应档位的模型加载和执行；
- `profile_identity.py` 负责声明当前评分档位，不允许把 V2/V3 当成未绑定的泛化配置；
- `recommendation` 只能读取当前已选定档位的 bundle，不允许在评分线程中混用不同 profile 的临时对象；
- `V2` / `V3` 的选择必须由显式配置或用户授权决定，不能隐式改写业务状态；
- 当前评估中使用哪一档，如果失败则必须显式降级，不允许悄悄回退到另一个档位。

#### 3.2.3 HTTP 与 Web 能力边界

HTTP 和 Web 都属于展示和接口能力，不承担业务决策，不触发行情抓取、评分或 DeepSeek 请求。

```text
src/trader/
  http_api/
    routes/
    handlers/
    schemas/
    response/

  web/
    pages/
    widgets/
    api/
    templates/
    static/
```

核心要求：

- `http_api/` 只读取已发布快照和诊断状态；
- `web/` 只负责页面渲染、组件展示和监控聚合；
- 两者都不直接访问底层行情 SDK、评分器或 DeepSeek；
- 所有输出都必须使用投影对象或只读快照，而不是内部业务对象直接透传；
- 前端和页面仅依赖接口层返回的只读状态，不具备修改业务状态的能力。

#### 3.2.4 能力模块与业务链路的关系

在三条主线中，能力模块和业务链路的边界必须保持稳定：

- 业务链路负责“推荐过程”和“阶段决策”；
- 能力模块负责“数据获取、训练、接口、展示、监控”；
- `V2` / `V3` 是模型评分能力的一部分，负责档位绑定与模型选择；
- 能力模块不能理解业务链路中的临时状态；
- 业务链路只能消费能力模块输出的标准 DTO / snapshot / status；
- `http_api/`、`web/` 和 `infra/` 都只能提供可观察的只读能力，不参与业务执行。

换句话说：

- 业务层次模块化负责“过程”；
- 能力模块化负责“能力”；
- `V2` / `V3` 负责“评分档位身份”；
- 三者的耦合点只能是统一的状态对象和明确的接口协议，而不是共享可变缓存。

---

### 3.3 两条主线的关系

“业务层次模块化”和“功能模块化”不是互斥，而是互补关系：

- 业务层次模块化回答：链路在什么阶段出现问题？
- 功能模块化回答：哪个独立能力负责这件事？
- 业务链路可以调用能力模块；
- 能力模块不应理解业务链路中的中间状态；
- 能力模块的输入输出必须规范化，并且被业务链路按阶段消费。

换句话说：

- 业务层次模块化负责“过程”；
- 功能模块化负责“能力”；
- 两者都必须具备独立输入、独立输出、独立错误处理和独立监控状态。

---

### 3.4 最终目标架构：业务线并列 + 接口展示并行 + 基础设施统一

推荐采用“下载 / 训练 / 推荐并列主业务线 + HTTP/Web 并行展示层 + 通用基础设施底层”的总结构，不再把所有内容放在泛化的 `business` 或单一 `recommendation` 容器中：

    entrypoints/

    application/

    entrypoints/

- `download`、`training`、`recommendation` 是顶层并列的业务主线；
- `http_api` 和 `web` 是并行的接口与展示能力，不属于推荐主链路内部实现；
- `recommendation` 负责真实的推荐流程和状态，但不再是唯一的顶层业务入口；
- `infra` 负责公共适配层，包括时钟、配置、数据库、行情源、DeepSeek、失败策略、清洗标准和缓存；
- `domain` 负责纯业务对象和值对象；
- `application` 负责各业务线的编排与业务实现；
- `entrypoints` 负责启动、命令和装配；
- 不再出现泛化命名 `business`，也不再把下载、训练和推荐混在一个顶层业务目录里。

### 3.5 infra 模块：公共部分提取

`infra` 是整个项目的基础设施层，职责是隔离外部依赖、统一时钟、统一数据库能力、统一行情来源、统一清洗逻辑并提供稳定对外接口。它必须对上层隐藏“供应商差异、网络失败、数据缺失、格式转换”这些细节。

#### 3.5.1 数据库操作
- 负责统一数据库连接、事务管理、Schema 约束和查询封装。
- 只暴露明确接口，不允许 `application` 或 `web` 直接写裸 SQL。
- 需要区分：
  - 运行态数据库：状态、快照、Frozen 结果；
  - 历史归档数据库：历史行情与训练归档；
  - 过滤名单数据库：稳定排除名单和过滤日志缓存。
- 数据访问必须遵循职责分离：持久化层只做数据落地，不做业务评分逻辑。

#### 3.5.2 时间
- 统一使用上海时区的时钟实现，支持注入可测试时钟。
- 任何业务时间判断必须来自同一时钟来源，不允许各模块自造本地时间。
- 需明确区分：
  - 评估时间 `as_of`
  - 生成时间 `generated_at`
  - 冻结时间 `freeze_time`
  - 发布时间 `published_at`
- 这样可以保证评估、冻结和 Web 展示都在线性一致的时间维度上运作。

#### 3.5.3 股票实时获取
- 对外仅提供统一的行情适配接口，不允许业务层直接依赖具体 SDK。
- 具体实现中，如果当前实时源失败，应自动切换备用来源，保证整体数据能力持续可用。
- 所有实时来源输出统一收敛到同一标准对象模型，外部无感。
- 需统一处理：
  - 主源失效切换；
  - 实时行情合并；
  - 多源时间戳冲突；
  - 价格字段、成交量字段、板块字段的标准化。
- 对上层只暴露“可用的标准行情快照”，而不是各个 SDK 的原始结构。

#### 3.5.4 历史数据获取
- 历史数据获取同样必须封装成统一接口，对上层隐藏不同数据源差异。
- 对外提供的数据必须是统一的历史窗口、统一的字段标准和统一的时间轴。
- 历史数据获取失败时，不应阻断启动和本地推荐；应转入 fallback 或最近有效快照。
- 历史数据加载与训练模块之间仅通过明确的数据接口通信，不允许反向写入实时候选状态。

#### 3.5.5 数据清洗与格式转换
- 所有股票信息在进入业务层之前必须经过统一清洗与标准化，并且在内存中形成完全统一的标准对象模型。
- 这一层的目标不是“简单修正字段”，而是把所有股票信息在接入业务逻辑前统一收敛为同一 schema：
  - 字段名统一；
  - 字段类型统一；
  - 时间格式统一；
  - 单位和精度统一；
  - 缺失值统一编码；
  - 板块、交易状态、交易所、价格限制统一规范；
  - 主板/创业板/科创板的同类字段必须有一致封装方式。
- 任何数据源、任何模块产出的股票对象都不能继续保留“原始字段名 + 原始类型 + 原始格式”的不同实现；内存中同一语义只能存在一种字段结构。
- 目标是：所有上层逻辑都只处理标准对象，不再处理“不同来源字段名和不同数据格式”，从而让一、二级过滤、候选生成、评分、风险、Web 监控都在同一数据契约之下进行。
- 这一层是候选筛选、评分、风险、Web 展示的基础，也是保证过滤漏斗可观测的关键前置环节。

- 对外统一标准对象必须满足如下字段契约，所有字段均在内存中按统一 schema 进行落地，不允许不同模块各自定义同义字段。这里必须区分两类字段契约：
  - 静态过滤字段：用于长期资格判断与稳定排除名单；
  - 动态过滤字段：用于当前时点硬过滤与候选生成前的实时筛选；
  - 历史下载字段：用于归档、训练和回溯，不直接进入实时推荐主链路。

  1. 静态过滤字段（长期资格门槛）
     - `security_code: str`：证券代码；
     - `security_name: str`：证券简称；
     - `exchange: str`：交易所，统一枚举 `SSE` / `SZSE` / `BSE`；
     - `board: str`：板块类型，统一为 `main_board` / `smaller_board` / `science_board`；
     - `industry: str | None`：所属行业；
     - `concept: tuple[str, ...]`：概念标签；
     - `listed_date: date | None`：上市日期；
     - `delisted_flag: bool`：是否退市；
     - `is_tradeable: bool`：是否具备长期交易资格；
     - `trading_status: str`：交易状态，统一枚举 `normal` / `suspended` / `halted` / `closed`；
     - `price_limit: Decimal`：涨跌停价格限制；
     - `market_cap: Decimal | None`：总市值；
     - `float_market_cap: Decimal | None`：流通市值；
     - `risk_flag: bool`：是否处于长期风险名单；
     - `blacklist_flag: bool`：是否在稳定排除名单；
     - `source_name: str`：来源名称；
     - `source_status: str`：来源状态；

     这些字段主要用于一级稳定过滤，解决“长期不具备参与资格”的问题，不要求实时行情强一致性，但要求静态属性恒定、可审计、可缓存。

  2. 动态过滤字段（当前时点硬筛选）
     - `last_price: Decimal | None`：最新价；
     - `prev_close: Decimal | None`：昨日收盘价；
     - `open_price: Decimal | None`：开盘价；
     - `high_price: Decimal | None`：最高价；
     - `low_price: Decimal | None`：最低价；
     - `change_pct: Decimal | None`：涨跌幅；
     - `change_amount: Decimal | None`：涨跌额；
     - `turnover_rate: Decimal | None`：换手率；
     - `volume: int | None`：成交量；
     - `turnover: Decimal | None`：成交额；
     - `minute_return_5: Decimal | None`：5 分钟收益；
     - `minute_return_30: Decimal | None`：30 分钟收益；
     - `volume_ratio: Decimal | None`：量比；
     - `closing_position: Decimal | None`：收盘位置；
     - `ma5: Decimal | None`：5 日均线；
     - `ma10: Decimal | None`：10 日均线；
     - `ma20: Decimal | None`：20 日均线；
     - `atr: Decimal | None`：真实波幅；
     - `volatility: Decimal | None`：波动率；
     - `drawdown: Decimal | None`：回撤；
     - `liquidity_score: Decimal | None`：流动性得分；
     - `as_of: datetime`：评估时点；
     - `source_time: datetime | None`：来源时间；
     - `data_quality: str`：数据质量级别，统一为 `excellent` / `normal` / `degraded` / `invalid`；
     - `missing_fields: tuple[str, ...]`：缺失字段列表；
     - `missing_code: str | None`：缺失值编码，统一为 `UNAVAILABLE` / `UNKNOWN` / `NOT_APPLICABLE` / `DEGRADED`；
     - `quality_penalty: Decimal`：质量扣分；

     这些字段主要用于二级动态过滤和候选生成前的时点过滤，解决“当前时刻不具备参与条件”的问题，必须带 `as_of` 和 `source_time`，以保证同一评估窗口内 semua 字段来自同一快照。

  3. 历史库下载字段（归档与训练输入）
     - `trade_date: date`：交易日；
     - `security_code: str`：证券代码；
     - `security_name: str`：证券简称；
     - `exchange: str`：交易所；
     - `board: str`：板块；
     - `open_price: Decimal`：开盘价；
     - `high_price: Decimal`：最高价；
     - `low_price: Decimal`：最低价；
     - `close_price: Decimal`：收盘价；
     - `adjusted_close: Decimal | None`：复权收盘价；
     - `pre_close: Decimal | None`：昨收；
     - `volume: int`：成交量；
     - `turnover: Decimal`：成交额；
     - `change_pct: Decimal | None`：涨跌幅；
     - `turnover_rate: Decimal | None`：换手率；
     - `adj_factor: Decimal | None`：复权因子；
     - `is_trade_day: bool`：是否交易日；
     - `source_name: str`：数据源；
     - `downloaded_at: datetime`：下载时间；
     - `record_status: str`：记录状态，例如 `raw` / `normalized` / `archived`；

     历史库下载字段是归档数据的“原始主数据 + 交易日快照”的标准格式，用于下载、校验、训练和回溯，不能混入实时荐股主链路的动态过滤字段。

  4. 统一通用字段（所有阶段都可共享）
     - `security_code: str`：证券代码；
     - `security_name: str`：证券简称；
     - `exchange: str`：交易所；
     - `board: str`：板块；
     - `as_of: datetime`：评估时间；
     - `source_name: str`：来源；
     - `source_status: str`：来源状态；
     - `data_quality: str`：数据质量等级；
     - `missing_fields: tuple[str, ...]`：缺失字段；
     - `filter_stage: str`：当前阶段；
     - `filter_reasons: tuple[str, ...]`：过滤理由；
     - `eligible_flag: bool`：是否通过阶段资格；

  5. 评分与风险输出字段
     - `local_score: Decimal | None`：本地规则评分；
     - `model_score: Decimal | None`：模型评分；
     - `risk_penalty: Decimal`：风险扣分；
     - `deepseek_score: Decimal | None`：DeepSeek 结构化参考分；
     - `fused_score: Decimal | None`：融合后最终分；
     - `decision_bucket: str`：决策桶，例如 `tomorrow` / `d25` / `long`；
     - `freeze_status: str`：冻结状态，例如 `not_ready` / `frozen` / `published`；

- 上述字段必须经过统一的转换规则处理：
  - 所有时间统一转为 `Asia/Shanghai` 时区的 `datetime`；
  - 所有数值统一为 `Decimal` 或标准整数，禁止混用 `float` 与字符串；
  - 所有缺失统一编码为显式缺失值，不允许通过 `0`、空字符串或者 `None` 混用；
  - 所有板块/交易状态/所处交易所、涨跌停约束必须统一枚举，不允许同一语义存在不同字段名；
  - 主板、创业板、科创板的字段结构必须保留一致，并通过 `board` 维度区分具体市场；
  - 任何来源模块产出的原始对象都必须在标准化入口被转换成统一 schema；
  - 静态过滤字段、动态过滤字段、历史下载字段不能混写到同一对象中，而是按阶段分别使用各自标准契约，保证一阶段只读取自己需要的字段，并保留可观测的过滤证据。

- 这意味着：一、二级过滤、候选生成、质量评估、评分、风险复核、融合与 Web 监控都不再处理“不同来源字段名 + 不同数据格式”，而是统一处理同一份标准对象契约。静态过滤和动态过滤虽然都属于统一对象模型，但它们分别使用不同的字段子集：静态过滤依赖长期资格字段，动态过滤依赖时点行情和因子字段；历史下载字段则用于归档与训练，不直接参与实时推荐决策。这样才真正保证：每一层的数据契约明确、字段语义稳定、漏斗统计可追踪、Web 能根据阶段展示“哪些字段在何处被过滤”。

#### 3.5.6 失败处理与降级
- `infra` 必须统一封装失败策略，包括超时、retry、fallback、source switch 和 degraded 标记。
- 任何外部源失败都必须记录：
  - 失败来源；
  - 失败时间；
  - 失败类别；
  - 是否启用了 fallback；
  - 当前快照是否仍然可用。
- 失败状态不能直接传染到评分逻辑，必须通过显式 `degraded` 状态暴露给上层。

### 3.9 Web 展示层：Web 能力模块化设计

      dashboard.py
      decision_view.py
      monitoring_view.py
    widgets/
      recommendation_funnel.py
      filter_summary.py
      source_health_panel.py
    api/
      monitoring_api.py

设计要求：

- `tomorrow / d25 / long` 页面保持不变，新增“监控区”；
- 监控展示只看“快照 + 诊断状态 + 过滤日志”，不参与决策；
- 所有过滤信息必须按层级呈现，便于知道“在哪一层被过滤掉、为什么过滤、剩余多少”；
- 页面监控必须显示：
  - 候选池数量；
  - 稳定名单过滤数量；
  - 一级过滤数量；
  - 二级过滤数量；
  - 动态数据获取状态；
  - 评分输入质量；
  - 最终正式池/观察池数量。

- `entrypoints`：装配启动入口；
- 所有模块必须通过明确接口、DTO、快照或事件通信，不能直接共享可变状态。

## 4. 分层设计：实时荐股链路

### 3.1 设计原则

- `domain`：纯业务模型，不可读写配置、时钟、文件、网络。
- `application`：业务编排，协调多个 domain/infra 能力，禁止直接使用 Flask 或旧实现。
- `infra`：外部系统适配、缓存、持久化、时间、网络、市场数据源。
- `web`：只读展示层，不能触发评分、抓行情、下载数据或 DeepSeek 请求。
- `entrypoints`：命令行/启动入口，统筹服务装配与生命周期。

### 3.2 模块隔离要求

- 下载模块不能直接修改训练结果。
- 训练模块不能直接影响实时荐股筛选。
- Web 只读取发布快照，不写入工作态。
- 每个模块拥有独立状态、独立日志、独立失败处理，不能在共享对象中塞入业务参数。

## 4. 分层设计：实时荐股链路

### 4.1 第 1 层：静态数据采集层

目标：获取股票基础信息，建立全市场静态索引。

负责内容：

- 证券主数据：代码、名称、交易所、板块、上市日、上市龄、价格限制、交易状态。
- 基础行情：当前价格、开高低收、涨跌幅、成交量、成交额、换手率、来源时间。
- 市场分类：主板、创业板、科创板、行业、概念等。

实现要求：

- 只在启动或周期性刷新时拉取一次完整静态快照。
- 所有字段统一进内存标准对象，禁止不同数据源输出不同字段名。
- 静态数据必须具备 `source`、`as_of`、`quality_level` 等元数据。
- 缺失时用 `UNAVAILABLE` 和 `DEGRADED` 进行显式降级，而不是隐式填 0。

### 4.2 第 2 层：一级稳定过滤与二级动态过滤层

目标：在全市场基础数据上先去掉长期不参与条件，再去掉当前时点不具备交易/风险条件的股票，最终形成进入候选生成阶段的基础股票集合。

这部分必须严格遵循项目重构大纲中的二级过滤定义：

1. 一级稳定过滤（长期资格过滤）
   - 目标：去除明显不参与策略的股票，解决“长期不具备条件”的问题。
   - 典型规则：
     - 是否停牌、退市、无交易状态；
     - 是否在黑名单、风控名单、公告风险名单；
     - 是否不满足交易所允许范围；
     - 是否属于持久不参与策略的行业/类型。
   - 这些问题通常不会因为单次行情变化而改变，适合做长期缓存。

2. 二级动态过滤（当前时点硬过滤）
   - 目标：去除“当前时点不能继续往下走”的股票，解决“当日/当次评估不合格”的问题。
   - 典型规则：
     - 当日成交/流动性门槛；
     - 最近 N 日均线、波动率、换手率等约束；
     - 是否存在明显非交易日或异常行情；
     - 是否已被系统判定为连续停牌或高风险。
   - 这是一层“硬过滤”，属于当前评估的实时安全门槛，不是最终推荐。

稳定名单与更新策略：

- 一级过滤后形成的“稳定负名单”可以写入数据库，保存 `stock_code`、`filter_reason`、`reason_level`、`last_updated_at`、`source` 等字段。
- 这部分名单适合作为长期缓存，按固定周期刷新一次，而不是每次启动都重新扫描全市场。
- 启动时优先读取缓存名单，缓存失效后再触发补算；这样能大幅减少启动时间，同时保留动态调整能力。
- 稳定名单只维护“长期不参与候选”的股票，不应混入实时硬过滤的临时结果。

输出：

- `qualified_pool`: 通过一、二级过滤后的股票集合。
- `filter_log`: 每次踢掉股票的原因、时间、来源、级别。
- `stable_exclusion_registry`: 经过周期更新的长期排除名单。

要求：

- 二级过滤不能直接给出最终推荐；它只是把“当前时点不具备继续进入评分流程资格”的股票剔除掉。
- 真正的候选生成发生在一、二级过滤之后：它将“合格股票集合”组织成 `candidate_set` / `candidate_pool`，提供给后续动态行情、特征构建和评分输入使用。
- 过滤日志必须保留一份可追踪记录，Web 中展示“一级过滤 / 二级过滤 / 候选生成剩余数”。
- 一、二级过滤必须分离：前者是长期资格缓存，后者是当前评估门槛；两者共同保证候选池稳定、可审计且不混用临时状态。

### 4.3 第 3 层：候选生成与候选池层

目标：在一、二级过滤之后，生成一份真正可进入评分流程的候选清单，并维护标准候选池状态。

候选生成不是“临时缓存拼接”，而是把已通过过滤的股票统一整理成标准候选对象集合，供后续动态行情、特征构建和评分链路使用。

它必须满足：

- 只负责生成候选清单；
- 只负责候选池的组织和状态；
- 不赋值最终推荐；
- 不直接写 Web 视图；
- 不做评分和风控结论。

输出：

- `candidate_set`: 可进入评分流程的候选清单；
- `candidate_pool`: 候选集合的组织与状态管理对象；
- `candidate_status`: 当前候选数、质量等级、来源状态、是否降级等。

这个阶段必须发生在“过滤之后”，而不是“过滤之前”，并且必须保持与后续评分阶段的明确分离。

### 4.4 第 4 层：动态行情与特征层

目标：对候选股票拉取动态行情和策略关键因子，并保证每次获取都具备时效性和统一清洗标准。

必须包含：

- 当前价、分钟涨幅、涨速、30 分钟收益、尾盘量比、收盘位置等。
- 日线前复权数据：均线、ATR、波动、回撤、流动性、成交活跃度。
- 策略窗口所需的历史周期数据。
- 时间维度，确保历史不是“永远最新”，而是“可追踪到评估时刻”的数据。

关键要求：

- 动态指标必须带 `as_of`（采集时间）、`source`（数据来源）、`quality_level`（质量等级）。
- 同一股票在同一评估周期内的动态特征必须来自同一快照，禁止出现混用不同时间戳的数据。
- 数据清洗与格式转换必须统一：字段名、时间格式、单位、缺失值表示、编码和精度必须标准化，避免不同数据源产生隐性差异。
- 缺失数据不能简单填 0，而应实现分级标记；严重缺失必须在评分前扣分。

建议的实现方式：

- 先按候选池获取动态行情，再对缺失值做统一标记；
- 采集与清洗分层，确保 `source -> normalization -> feature -> scoring` 的顺序清晰；
- 所有股票信息在内存中都用标准对象表示，统一字段，同一语义只存在一种结构。

这类设计比“每次都直接在原始行情上做裸过滤”更合理：

- 稳定排除名单负责长期规则门槛；
- 动态硬过滤负责当前市场状态；
- 统一清洗负责数据标准化；
- 评分前质量评估负责定量扣分；
- 整条链路更稳定、更可追踪，也更容易在 Web 上展示漏斗与异常来源。

### 4.5 第 5 层：评分输入与质量评估层

目标：在进入本地评分和模型评分前，对输入质量进行验证。

核心动作：

- 逐股检查：静态数据完整性、动态数据完整性、时间有效性、特征覆盖率。
- 质量分级：
  - `excellent`
  - `normal`
  - `degraded`
  - `invalid`
- 对缺失指标按严重程度扣减资源分数，而不是随意跳过。

要求：

- 评分输入资格不可放在地方中间判断逻辑里散落。
- 这层的作用是“保证评分的数据有效性”，而不是“重新做筛选”。
- Web 中统一显示：数据缺失多少、哪些因子缺失、造成多少分值惩罚。

### 4.6 第 6 层：本地规则评分层

目标：执行本地策略规则评分，给候选股票一个基础分数。

职责：

- 规则型因子打分。
- 组合因子与边界条件判断。
- 通过数据完整性和质量护栏保证规则评分可解释。

设计要求：

- 输入必须是标准特征对象，不允许再混入原始字典或裸 JSON。
- 评分结果必须保留 `base_score`、`factor_summary`、`quality_penalty` 等结构。
- 评分过程必须纯函数化，便于回归测试和证据复现。

### 4.7 第 7 层：模型评分层

目标：将本地规则输出与模型评分结果统一归一化。

要求：

- V2 / V3 分别独立声明策略身份。
- `Tomorrow` 和 `D25` 作为不同策略头，不能混写在同一结果对象里。
- 对不同板块（主板/创业板/科创板）分别建立评分池，最终再统一排序。
- 模型评分输入必须遵循固定的特征契约，不接受“临时字段”扩展。

### 4.8 第 8 层：风险复核与 DeepSeek 证据层

目标：在评分完成后做风险校验和必要的证据复核。

职责：

- 过滤极端风险事件。
- 对公告、财务、政策、监管和新闻证据做结构化检查。
- DeepSeek 只参与“结构化证据校验”，不能直接决定分值。

必须遵守：

- DeepSeek 自由文本不能直接扣分。
- 证据必须是符合时序要求的、且不晚于评估时刻的结构化事实。
- 使用 `manifest` 记录证据来源、证据ID、时间戳和稳定性级别。

### 4.9 第 9 层：融合与降级层

目标：根据固定融合公式输出最终分数。

固定公式：

- `local_score * 0.68 + deepseek_score * 0.32 - deepseek_risk_penalty`
- 结果必须使用 `ROUND_HALF_UP`，保留两位小数。
- 不能在融合时再次扣除 `local_risk_penalty`。

并且：

- 如果数据源降级，必须显式标记 `degraded` 状态。
- 如果历史或市场数据不可用，保留最近有效快照，不阻塞本地推荐。
- 失败必须有清晰的降级路径，而不是直接静默返回空集。

### 4.10 第 10 层：正式池/观察池与冻结层

目标：生成最终可展示的推荐结果。

职责：

- 将 TopK 结果按 `tomorrow` / `d25` / `long` 分别分发到正式池和观察池。
- 处理冻结时间：
  - `today` 在 11:20 冻结。
  - `tomorrow` / `d25` 在 14:50 冻结。
- 冻结后的结果不可被迟到结果覆盖。
- `long` 只展示当前快照，不写推荐历史。

要求：

- 正式结果写入持久化记录；不影响实时采集与 Web 只读状态。
- 冻结逻辑必须独立模块，不与评分模块共用状态对象。

## 5. 过滤日志与 Web 监控设计

### 5.1 过滤日志对象

每个过滤步骤都必须生成统一的日志对象，字段至少包含：

@dataclass(frozen=True)

## 6. 功能模块划分

### 6.1 下载历史数据模块

功能：下载历史行情、维护归档和补齐缺失数据。

要求：

- 独立命令入口：`download`。
- 维护固定格式：`control.sqlite3 + partitions/YYYY/MM.sqlite3`。
- 下载和训练之间不共享写锁。
- 只更新历史归档，不修改实时推荐状态。
- 历史补齐必须只补“缺失的最新日线”，不能影响已有正式快照。

### 6.2 训练历史数据模块

功能：从归档历史数据训练 V2 / V3 模型。

要求：

- 训练由独立入口：`train-v2`、`train-v3`。
- 读取数据库时只读不修改业务运行态。
- 两个档位各自拥有其训练数据、特征契约和输出目录。
- 不允许 V2/V3 在运行时共享同一模型输出对象。

### 6.3 实时数据荐股模块

功能：实时候选生成、过滤、评分、风险、融合和发布。

分层：

- 静态数据聚合
- 候选资格过滤
- 动态行情抓取
- 特征构建与质量检查
- 规则评分
- 模型评分
- 风险复核
- 融合
- 冻结 / 发布

这部分必须作为独立主链路存在，不允许被训练、下载或 Web 直接插手。

### 6.4 Web 展示模块

功能：只读展示推荐结果、状态和漏斗监控。

要求：

- 只展示当前快照与状态。
- 不抓行情、不评分、不执行 DeepSeek。
- 只读 `api/status`、`api/decisions/...`、`api/events` 等接口。
- 对过滤漏斗、记录失效阶段、源状态下降进行监控。

## 7. 模块独立性与互不干扰约束

在重构时必须落实以下原则：

1. 无共享可变状态
   - 所有中间结果都必须是不可变类型对象。
   - 不允许一个模块直接写另一个模块中的缓存对象。

2. 无隐式依赖
   - 如果 A 模块要使用 B 模块的结果，必须通过明确的接口/DTO。
   - 禁止“读全局字典、拿到临时状态、直接判断是否存在字段”的方式。

3. 无跨层调用
   - `web` 不能调用 `infra`。
   - `application` 不能访问 `web` 和 `infra`。
   - `domain` 不能访问时钟、文件、数据库、HTTP 网络。

4. 事件驱动和快照控制
   - 业务链路以快照为主，阶段状态写入监控日志，不直接影响正式推荐结果。
   - 所有日志和状态都通过事件或快照投影，而不是直接改写业务对象。

5. 失败隔离
   - 某一条数据源失败，不应阻碍其他数据源的股票推荐。
   - 失败时保留最近有效快照，并显式记录 `degraded` 和 `last_successful_snapshot`。

## 9. Web 监控的具体要求

## 10. 实施顺序建议

建议按以下顺序重构，避免互相干扰：

1. 先分离 `domain` 与 `application` 边界
   - 先定义值对象与策略对象。
   - 再定义业务服务接口。

2. 再做 `infra` 数据源适配
   - 统一静态和动态行情结构。
   - 建立 source lane registry 和 degradation handling。

3. 再构建推荐漏斗
   - 候选生成 -> 过滤 -> 评分 -> 风险 -> 融合 -> 冻结 -> 发布。
   - 每一步都保留日志和计数。

4. 最后接 Web
   - Web 只展示状态，不影响业务链路。
   - 过滤监控先行，正式展示后补。

## 11. 结论

这次重构的关键，不是把项目“拆得更碎”，而是把每个业务功能变成一个有明确边界、有固定输入输出、有可观测状态的模块。候选筛选、评分、风控、冻结、Web 监控必须各司其职，任何一个环节发生问题都能直接定位，而不是让模块互相越界、互相污染。

最终目标是：

- 模块独立且不互相干扰。
- 候选筛选分层清晰，且每层都保留过滤证据。
- Web 能看到完整漏斗和过滤状态。
- 推荐链路既可维护，又可审计，也便于后续扩展与回归验证。

在实现阶段，所有新增模块都必须遵循上述边界，且 Web 监控优先保证“过滤掉了什么、过滤了多少、在哪一层丢失”这三类信息完全可见。
