# Web实时荐股恢复与下载、训练、数据库完整优化计划

本文件保存用户确认的完整计划；执行状态、实际改动、验证证据与未完成项只维护在[工程实施台账](3_工程实施.md)，不在这里维护第二份进度。评分、工程和下载训练合同分别以docs/1、2、4为准。

## 1. 目标与实施原则

第一优先级：恢复Web实时荐股，保证有效报价经过评分、发布和页面刷新后，用户能及时看到当前结果。

用户已明确：当前本地未提交修改都是为解决该问题。全部纳入问题排查、完整Review和交付范围，不再作为与本任务无关的并行改动排除。

- 荐股：逐股过滤、特征和评分在内存完成，避免频繁数据库操作及同步写入等待。
- 训练：减少重复读取、解码、全文件扫描和重复校验。
- 下载：保证完整性、可恢复和可靠发布，在此基础上提高吞吐。

荐股期间禁止任何历史或尾部补缺；资料更新只能手动执行sync history/market/company。

### 下一批的具体执行步骤

1. **确认运行身份。** 核对实际启用档位、模型和输入窗口、服务PID及代码身份，使用新进程验收。只操作本任务服务，不停止其它终端的下载或训练；缺工件的档位记录明确失败原因，不现场补训练或下载。
2. **核验整轮边界并集中修复。** 通过既有[scripts/diagnose_runtime.py](../scripts/diagnose_runtime.py)及其所属模块追踪轮次：开始采集、各档采集结束、双策略输入接纳、评分结束、本地发布及Web事件。确认上一轮各启用档位未发布或未明确失败退出前，下一轮采集数不增长；慢档、缺资料、超时、会话变化和停止不能遗留占用。检查不再使用的独立调度入口、参数和状态，避免旧路径绕过整轮约束。
3. **核验Web到达。** 连续观察至少5个不同完整轮次，对齐API、SSE和实际页面的档位、策略、决策身份、数量、发布时间及来源年龄。结果为空时核对首个阻断原因；失败保留最近有效结果。服务端发布是后端轮次完成边界，浏览器绘制单独计时；15:00冻结仍独立优先，Long仍是不评分的独立快照通道。
4. **同次记录效率。** 分开统计启动预读、逐股计算、异步资格写入、整轮持久化和只读查询的SQL次数与耗时；目标是逐股主计算零业务数据库操作。记录采集、准备、评分、发布及整轮耗时，检查公共输入是否重复构建，并观察旧轮次对象释放后的RSS。5轮仅报告本次样本分布，不冒充长期稳定性证明；可复用同次运行覆盖后续100 tick观察，不把tick数量当作完整轮次数。
5. **一次性收尾。** 验证SSE重连/轮询恢复和正常停止，核对批量写队列排空或明确报告未完成项。发现问题先集中修复，再运行受影响的最小回归；仅因修复、失败或证据缺口重测，不重复全仓测试或无关长测。提交代码、必要诊断与测试及281台账，推送确认后打印下一批任务。

真实盘中条件不具备时，先完成可独立实施的修复、隔离失败路径和只读检查；预览、合成输入及历史证据不能替代盘中5轮验收。无法取得的证据继续留在281，不标记整个阶段完成。确认首个阻断后直接处理，不为等待真实窗口反复启动长时间探测。

## 3. 第一优先级：完整解决Web没有实时荐股

### ① 统一接续阶段281，纳入全部本地修改

- 沿用281原阶段和台账，直到当前Web实时荐股问题完整闭合，不另建阶段拆走剩余修复。
- 对照已推送基线bf76800b，登记全部未提交、新增、删除文件及其在问题链路中的作用。
- 将历史预读、公司计算、行情缓存、输入身份、超时、诊断、HTTP、前端状态以及相关测试修改作为完整修复切片Review。
- 本地模型和配置变化一起核对，明确当前服务实际采用的模型、窗口和配置身份，确保代码、模型与运行证据一致。
- 最终验证Web得到当前轮次的结果或准确原因，不能仅以启动提速完成问题交付。

### ② 从页面反向定位，再沿数据正向验证

完整核对：报价取得 → 输入就绪 → 动态过滤 → 公共特征 → 模型及评分 → 本地结果发布 → 只读API → SSE/轮询 → 页面渲染。

每个边界核对同一策略、交易日、轮次、输入身份、数量和时间，定位首个没有前进或丢失结果的环节。重点调查：

- 报价过期及来源年龄过大。
- 全市场刷新超时、队列等待和计算挤占。
- 输入批次不匹配，包括paired_input_epoch_mismatch。
- 输入已ready但评分或发布未完成。
- 服务已有新结果，而API、SSE、前端合并或当前策略选择未展示。
- 旧快照、加载状态或缓存覆盖新轮次。

这些是调查方向，不能把旧日志直接当成当前根因。

### ③ 修复实时性及展示行为

- 减少报价取得后到评分发布之间的重复计算、重复检查和阻塞写库。
- 防止慢任务、重复刷新和旧轮次排队持续占用当前轮次资源；取消、超时和迟到结果按现有身份合同处理。
- 盘中采集→评分荐股→Web服务端发布作为一个跨档位轮次；本轮启用档位全部完成或明确失败后才开始下一轮采集，不以持续采集并固定旧输入替代整轮串行。轮内复用公共输入，允许档位并行；15:00冻结优先，浏览器绘制不作为后端等待条件。
- 当前结果发布后，API与页面使用匹配身份及时更新，不跨轮拼接。
- 保留最近有效结果，清楚展示结果时间、来源年龄和降级原因。
- 合法业务筛选后为空时展示明确原因；输入待补、执行失败和业务淘汰分别计数。
- 不通过放宽报价时效、风险门、模型门或冻结规则制造“有荐股”。

### ④ 阶段281的完成条件

- 使用本批代码启动的新进程验证，不能沿用旧进程结果。
- 当前配置启用的档位都完成链路核对；具备对应模型和输入时覆盖V1/V2/V3/V5。
- 连续至少5个不同完整轮次，确认新结果或准确的空结果原因能到达Web。
- 核对页面与API的策略、轮次、结果、发布时间及来源年龄一致。
- 验证失败保留旧结果、SSE重连/轮询恢复以及正常关闭。
- 完成本阶段提交和推送后，再进入后续优化。

## 4. 后续未完成优化，逐项执行

### 荐股数据库与内存

⑤ 证明逐股计算阶段零业务数据库操作：启动完成后，历史、公司、资格、行业和日历从共享内存读取；新增资格事实交给独立批量写队列。分别统计逐股计算与整轮持久化的SQL成本。

⑥ 合并整轮持久化与只读查询：核对轨迹、序号、结果和历史查询中的重复连接、解码与逐条提交，按整轮或有界批次合并。正式冻结继续可靠提交，遵守15:00 first-wins。

⑦ 完成四档公共计算和内存复用核对：检查总体、研究派生量和模型基础输入的重复构建。同实际依赖共享不可变对象，不同窗口和模型身份独立；先测驱逐再决定是否扩大内存预算。扩大预算须同步配置、解析约束和权威文档，不以预算变更掩盖RSS回归。

### 训练

⑧ 取消正常样本复用时的整文件摘要扫描：样本完成时一次校验、封存，之后只读；正常复用检查来源、版本、特征、切分和封存元数据，同一命令只检查一次。完整文件复核保留为显式审计，实际读取错误明确处理。常规复用不承诺发现未被读取到的所有文件损坏。

⑨ 合并剩余双头及各档公共读取：复用289已有能力；同特征行一次读取公共特征及所需标签，按头投影有效样本。跨档仅共享一致的历史基础输入，避免可变矩阵相互污染，按行业释放资源。

⑩ 清理重复校验并闭合性能遗留：保留形状、标签对齐、切分、防泄漏和工件发布检查；减少已由下载发布或训练入口完成的重复内容扫描。定位V1读取回退，完成V5剩余质量、最大行业双头、总耗时及RSS对照。

### 下载

⑪ 优化事务、检查点和发布中的重复工作：复用现有批量流水线和连接，在批次内合并重复状态更新、计数及摘要计算。保持价格提交成功后推进检查点、分区完成后发布，继续验证raw/qfq、日期覆盖、缺口和复权身份。

⑫ 完成公司同步覆盖及提取验收：按受影响股票集合合并读取、派生和发布；分别核验目录、正文、事实及正式发布完成情况，完成持续风险、历史连续性和180日解禁范围检查。

⑬ 闭合阶段292的活动维护：活动history完成回执、market同步及两库只读审计仍缺证据，沿292原记录通过手动同步闭合，不接回荐股运行流程。

### 综合验收及其它遗留

⑭ 完成真实重建、训练和失败恢复验收：核对参考、raw/qfq、短窗、公司、样本和四档双头身份，验证中断续传、部分提交、重启复用及失败不覆盖旧模型。优先审计现有资料，不因旧台账记录而重新清空当前数据。

## 5. 接口、测试与交付

- HTTP/Web继续调用推荐只读用例；修复页面实时性不赋予它们抓行情、训练或写业务库的能力。
- 资源由bootstrap统一组装，公共输入使用有类型的不可变对象，避免第二套状态和隐藏fallback。
- 扩展既有诊断框架，区分启动读取、逐股计算、整轮持久化和Web交付成本。
- 每批运行最小充分定向验证；Web问题增加实际浏览器链路验收，不反复执行全仓回归。
- 当前先完整闭合281；之后每次“继续”完成一个阶段，提交、推送并打印下一批计划。
- 所有进度只记录到docs/3_工程实施.md；281、292、213沿用原阶段，其它独立工作在开工时登记新阶段。
