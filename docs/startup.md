定位完成：不是 company 数据加载慢，而是全市场历史投影在启动时超过了固定 300 秒期限。

关键原因：

- company 数据确实很小：数据库约 2.7 MiB，原始文件约 18 MiB。
- 但启动顺序是先加载历史行情，再加载 company：market_feature_service.py:109 (src/trader/recommendation/infra/market_data/market_feature_service.py:109)。
- v1,v2,v3 共用一次历史扫描，但 V1 的 251 个交易日决定扫描窗口，而 V2/V3 只有 61/62 日。
- 启动需要遍历全市场股票，进行历史对齐、停牌缺口扩展读取、V1 learned-rank 特征计算，并分别生成三个档位的投影。
- 历史目录约 4.6 GiB。虽然不会全部载入内存，但需要对全市场读取约 252 个交易日窗口。
- 投影发布前还会逐股票执行 JSON 序列化来计算内存占用，仍计入同一个 300 秒期限：shared_history_projection.py:124 (src/trader/recommendation/infra/market_data/shared_history_projection.py:124)、published_history_cache.py:221 (src/trader/recommendation/infra/market_data/published_history_cache.py:221)。
- 独立只读诊断运行超过 240 秒仍未完成，与启动失败表现一致。

日志的准确含义是：

history_preload_deadline boundary=require_projection:362

对应 published_history_cache.py:357 (src/trader/recommendation/infra/market_data/published_history_cache.py:357)。这时已经不是“仍在加载”，而是历史投影加载失败，close_quotes 每次刷新都被门禁拒绝。

还有一个重要问题：启动时在真正加载前就把 _initialized 设置成了 True，shared_history_projection.py:76 (src/trader/recommendation/infra/market_data/shared_history_projection.py:76)。因此超时后：

- close_quotes 会继续定时尝试；
- 但历史投影本身不会在当前进程自动重试；
- 重复日志不代表加载正在继续；
- 必须重启进程，而单纯重启仍可能再次撞到 300 秒期限。

Web 是异步启动的，所以页面先能打开，随后等待后台线程完成历史投影：published_input_preloader.py:36 (src/trader/recommendation/infra/market_data/published_input_preloader.py:36)。超时后前端正常情况下应显示“本地历史加载失败”；如果仍显示“正在加载”，说明页面没有取得最新状态，需要在进程运行时检查 /api/status 的轮询结果。

结论：真正需要修复的是历史启动投影的性能和失败后的状态/重试行为，不是 company 加载。当前只完成了定位，没有修改代码或用户现有文件。



核对后有两点需要纳入计划：已有阶段281正在处理同一个历史启动超时，应沿用它；现有预加载诊断却使用251/251/61日组合，并在290秒主动取消，不能直接代表当前251/61/62日的三档启动。修复先补齐准确测量，再按实测热点优化；300秒终止和单次加载是现有设计，不能直接当作缺陷取消。
修复应沿用现有阶段281，目标是让 ./run.sh v1,v2,v3 在原有300秒期限内完成历史及输入加载，并让页面准确区分“加载中”和“加载失败”。

先校正上一轮结论：日志已经证明历史预加载超时，但SQLite读取、逐行解码、停牌补长、V1特征计算、JSON容量核算各占多少时间，还需要测量，不能提前认定某一项是主要瓶颈。另外，失败后不自动重试是当前“一次性启动预读”的设计，不宜直接改成无限重试。

1. 补齐与真实启动一致的性能基线

   扩展现有统一诊断入口，不新增临时脚本。当前诊断存在三处偏差：
   - 使用251/251/61日组合，实际V1/V2/V3是251/61/62日。
   - 默认开启CPU剖析，会增加执行时间。
   - 290秒主动取消，且没有覆盖生产环境的容量预留和完整输入绑定。

   调整为读取当前配置构造所选档位，分别提供普通计时和CPU剖析模式。普通计时覆盖历史读取、投影发布、company加载和输入绑定；剖析单独运行，报告明确标注额外开销。

   记录同一份数据、模型、配置、源码和机器身份，输出：

   | 测量项 | 用途 |
   |---|---|
   | SQL次数、读取行数、解码耗时 | 区分磁盘与Python解码成本 |
   | 补长股票数、重复读取行数 | 判断停牌补长是否造成放大 |
   | 历史摘要、V1模型输入计算耗时 | 判断派生计算成本 |
   | 容量核算、发布、输入绑定耗时 | 定位扫描完成后的尾部耗时 |
   | 股票完成数、总数、RSS峰值 | 判断进度和资源上限 |

   完成条件：得到一份无剖析开销的失败或成功基线，能指出最耗时的具体阶段。首次运行和后续缓存预热运行分别标记，不把普通进程重启宣称为磁盘冷启动。
2. 优先处理历史读取与解码热点

   主要检查：
   - history_snapshot_reader.py
   - history_revision_codec.py
   - history_prices.py
   - published_history_snapshot.py

   根据基线落实以下优化：
   - 同一年度文件、同一发布序列的相邻月份尽量合并查询，避免逐股逐月反复建立连接和读取相同范围。
   - 已有分区校验缓存继续复用；核查是否仍存在重复校验，文件或WAL身份变化时必须失效。
   - 减少逐行重复日期转换、数值解析、中间对象及规范载荷构造。
   - 保留原有revision/content hash校验和快照身份检查；不能通过跳过校验换取速度。

   完成条件：相同快照下读取结果、缺失状态和身份与原实现一致，查询或解码成本确实下降；损坏数据仍能被拒绝。
3. 消除停牌补长的重复读取

   当前不足窗口会按63日递增，最多扩展到2000个交易日。如果每次重读整个扩展窗口，同一股票的旧数据会被反复读取和解码。

   改为保留已经读取的窗口，只补取更早的缺失区间，达到所需有效样本后立即停止；若现有读取接口无法表达区间，先在download读取边界增加明确的有界区间能力，再切换消费者。

   保持上市日期、真实停牌、未知缺失、价格异常和最大补长限制的原有语义。

   完成条件：长停牌、新上市、永久不足及正常股票的输出一致，补长过程不重复解码已读取的数据，取消和deadline检查仍有效。
4. 优化派生投影与容量核算

   保留现有“共享扫描一次、按档位派生”的结构：
   - 相同窗口摘要只计算一次。
   - 三档共享保留的最近20根日线。
   - V1模型输入所需日期、日历位置和公共中间结果按股复用，减少相邻日期输入的重复计算。
   - 原计算顺序和数值语义需要保持，避免排名或动作门因浮点变化而改变。

   容量核算目前通过规范JSON序列化计数。优化时优先复用已完成的编码或可精确组合的长度，维持现有规范JSON预算口径；不能直接改用 sys.getsizeof()，也不能取消容量门禁。
