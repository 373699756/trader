# 人工审查清单

本清单把用户问题整理成可执行检查，不定义第二套业务规则，也不记录完成状态。
规则分别引用评分、工程设计和下载训练；进度及验证证据只写[工程实施](3_工程实施.md)。

审查顺序：

1. 先找实际输入、配置和代码，确认问题是否仍存在。
2. 分开记录当前行为、目标差距和研究假设。
3. 用表中方法取得证据，不能用“看起来差不多”替代测量。
4. 代码、fixture、真实源、全市场及收益分别判断，不能互相代替。

## 1. 数据是否完整、稳定

| 审查问题 | 检查方法 | 判断依据 |
| --- | --- | --- |
| 评分究竟需要哪些字段 | 沿实际消费者核对[完整字段附录](1_评分逻辑.md#附录完整字段与因子表)、公式和模型manifest | 区分模型必需、本地必需、质量扣分、仅展示；旧候选30%缺失门不能机械保留或删除 |
| Tencent能提供什么，何时需要Sina | 统一来源诊断逐字段比较缺失、覆盖、耗时 | 主路成功不请求备路；不因辅助字段缺失重复采集 |
| 东方财富、BaoStock等是否还有用途 | 按报价、分钟、公司证据、行业和审计逐项查消费者 | 删除无消费者能力，不误删仍有业务用途的来源 |
| 慢数据是否还在盘中联网或读库 | 追踪公司缓存冷项、行业刷新、固定点及系统任务 | 按[手动维护边界](4_下载训练.md#72-手动维护边界)检查启动预读、线程退出和无周期扫描；已有宿主任务须另行核验，不能由服务内任务删除推定已卸载 |
| qfq和公司资料是否真正够用 | 检查截止、缺股日、模型字段及公告页/正文待补 | 下载完成、字段可用、风险完整覆盖不是同一件事 |
| 量比、成交量比、成交额比是否混用 | 逐个核对公式、单位、来源及缺失分支 | 同一字段保持同一统计含义，不能无标记替代；现有问题见评分逻辑第11.1节 |
| 前晚资料能否支持次日判断 | 分别核对财报披露/生效、公告覆盖截止、查询及读取时间 | 有效财报与新风险覆盖分开；未核实或过期时降级，必要时仅观察，不延长TTL冒充新鲜 |

来源实测沿用scripts/diagnose_runtime.py及现有market-factor-compare等profile，优先stdout，不临时造第二套脚本。
单源循环最长120秒、整组最长600秒；达到截止立即取消并报告本轮不可用，不把一次失败判为永久退役。
“qfq本地可读”仍要验证来源、复权和发布身份，不能忽略数据质量。

## 2. 流程与同轮一致性

| 审查问题 | 检查方法 | 判断依据 |
| --- | --- | --- |
| 能否先过滤再采集 | 对比静态事实与动态行情依赖 | 已知公司风险可前置，价格条件必须有当前行情 |
| 是否仍存在隐蔽候选截断 | 核对旧候选分第121但local_score全局靠前的例子，以及实际评分输入名单 | 保持已切换的完整总体选择链，无候选分、50分预选线或每板120只池，扣风险后选总前六 |
| 高原始分是否占住高风险名额 | 比较base_score与local_score排名反转，并区分V1模型排序 | V2/V3按扣风险后的local_score排名，V1沿独立模型排序且本地风险约束动作；风险只扣一次，同分按代码升序 |
| 模型门及评分输入是否覆盖完整范围 | 同数据对比当前与目标顺序，核对字段及总体身份 | 完整合格总体参与输入准备，保持参考总体口径；分批I/O不能变成分数截断 |
| 同一股票是否因请求人数变化而变分 | 固定总体及自身输入，比较99/100/120只和不同分批 | 按[固定总体规则](1_评分逻辑.md#51-板内总体)核对百分位、分数与参考身份；历史问题作为回归场景，不当作当前故障 |
| 缺模型时“降级”究竟允许什么 | 分开核对旧视图、常规新动作及收盘补建 | 常规模型门与[收盘恢复例外](1_评分逻辑.md#9-冻结恢复与不可变历史)分别验收；不把补建结果或旧视图解释为通过模型验证 |
| 名单、分数、流程诊断是否同轮 | 追踪输入身份到统一索引、SSE和Web | 整体切换，无新名单搭旧诊断；按[十一层展示合同](2_工程设计.md#111-同轮十一层执行观测)检查，旧冻结审计保留原身份 |
| 报价overlay是否改变评分 | 对照父决策、overlay版本及来源时间 | 按[当前刷新节奏](2_工程设计.md#62-当前刷新节奏)检查；只更新报价，不改变分数、六席或冻结 |
| 10秒是否能完成完整链 | 测来源→特征→评分→发布→浏览器 | 最短调度间隔与实际整轮耗时分开报告 |

## 3. 评分、模型与收益

| 审查问题 | 检查方法 | 判断依据 |
| --- | --- | --- |
| V2/V3或Tomorrow/D25为何名单相似 | 同日同股拆分预测、成本门、本地分和选择影响 | 归因清楚，不只看最终重合率 |
| 模型到底贡献什么 | 规则、规则+模型门、V1模型排序逐组比较；V5独立观察 | 预测覆盖、过滤贡献、排序贡献、净效用和成本后收益 |
| 生产权限是否混淆 | 核对决策execution_mode、production_authority及运行模式 | V1人工生产授权不升级旧Shadow记录或证明收益通过；V5保持Shadow，非交易日预览均不能正式持久化 |
| 成本是否随批次中的同伴改变 | 固定自身预测和流动性事实，更换批次同伴 | 固定参考人口、尺度与身份，成本及准入不能随请求分批翻转 |
| 权重、过热线、风险扣分是否合理 | 一次只改一族参数，固定独立确认和留出 | 当前值不是已证明最优；收益与尾部风险一起看 |
| 硬过滤后软风险是否仍可触达 | 核对质押、解禁、财务恶化的硬门、软扣分与动作矩阵 | 删除无效重复须有证据，不为使扣分生效而放宽已知硬风险 |
| 分数在不同时段和板块是否可比 | 分上午、午后、尾盘及板块比较累计量价、分数与后续净收益 | 时段归一化和跨板收益校准仍待研究，不因分数同为80就认定收益相同 |
| 历史评价是否使用未来信息 | 核对当时证券人口、ST、退市、财报披露、行业及特征可见时间 | 不用当前名单或事后标签重写历史人口；点时资格不足则停止收益评价 |
| 研究收益是否等于可实现收益 | 对照15:00锚点、可交易价格、滑点、交易限制及不可成交情景 | 冻结一致性不证明按收盘价成交，研究主口径和压力结果分别报告 |
| D25、六槽与资金收益是否混名 | 核对期限、空槽、空仓、分仓和重叠持仓 | 机会标签、固定槽位指标、入选均值及全资金收益分别解释；不直接据标签年化 |
| 风险单位和统计依赖是否一致 | 核对MAE、ATR倍数、百分比字段及各研究区块参数 | 依评分逻辑第12节核验；隔离期不等于bootstrap区块，旧研究保留注册参数 |
| 研究约束是否与目标生产一致 | 比较板块上限及ceil/floor取整、行业限制、动作与可行集合 | 不把不同约束的旧报告当成新目标收益证明，不改写已开启留出 |
| 推荐/关注/回避门槛在哪里 | 对照selection.json及额外阻断 | Tomorrow78/72、D25 76/70，比较local_score；V1模型排序分另列，高分仍可被风险限制 |
| LightGBM/Ridge是否应组合其它算法 | 固定数据、目标、成本及PC资源，对照独立Logistic门等方案 | 不预设复杂算法更好，不把回归分冒充概率 |
| 新股训练与板块属性是否正确 | 检查日期轴、特征窗、板块、行业暴露和样本 | 不补上市前数据，不统一要求每股1250日 |
| DeepSeek是否范围过大或误否决 | 核对固定六席单路径的实际对象，以及相同父决策有无复核 | 按[复核合同](1_评分逻辑.md#73-deepseek结构化风险复核)检查，不恢复旧challenger；漏报、误拒、机会成本、延迟和请求成本一起报告 |

收益判断唯一见[评分逻辑第12节](1_评分逻辑.md#12-收益验证与变更门禁)。
本清单只提出验证方法，不宣称算法、阈值或扩大内存已提高收益。

## 4. 工程、SQLite与速度

| 审查问题 | 检查方法 | 判断依据 |
| --- | --- | --- |
| 业务边界是否简单清楚 | 追踪owner、依赖方向和全部消费者 | 单一所有者，无兼容转发、重复状态或隐藏创建资源 |
| SQLite封装是否科学高效 | 检查连接释放、显式事务、建库失败恢复、批量读写 | 公共层只做primitive，业务持有SQL与编解码 |
| SQLite是否真的减少重复开销 | 同负载交替至少5轮，记录连接/事务/读写、延迟、RSS和WAL | 真实改善，不关FULL或弱化校验换数字 |
| 更大内存及多档共享是否提速 | 单档和显式所选组合分别测缓存命中、淘汰、读库、整轮P50/P95及换页 | 预算按[当前内存合同](2_工程设计.md#71-当前值与扩大目标)，所选各档共用进程预算；配置扩大不等于实测提速 |
| 全量评分是否把瓶颈转到分钟请求 | 核对完整合格总体的覆盖、队列、请求数、来源年龄及延迟 | 使用有界资源，不用旧120只fixture冒充全市场，不放宽新鲜度换速度 |
| 相同分钟内容是否重复触发评分 | 分开统计检查、内容变化、评分触发和完整轮次 | 观察时间不冒充内容变化；串行请求与有界并发分别实测 |
| 11层是否形成更多工程状态 | 跟踪一份流程事实到诊断、API及页面 | 业务层数不等于服务数；各投影不维护重复状态 |
| 调整阶段定义后旧冻结还能否读 | 使用旧规范字节核对历史解码、原字段、身份与摘要 | 隔离历史只读解码，不依赖新活动枚举重解释，也不恢复旧评分链 |
| 长时间运行是否稳定 | 连续多轮、失败、取消及关停后观察 | 无持续增长、无失控后台资源，失败保留合法结果 |

SQLite交付状态及隔离性能证据只查工程实施；合成库结果不能代替真实全市场验收。

## 5. Web与Long体验

| 审查问题 | 检查方法 | 判断依据 |
| --- | --- | --- |
| 页面为什么落到Long | 检查首次自动选择、当前ready/入选数和用户切换 | 当前按首个可用策略选择；目标默认Tomorrow，刷新不抢用户选择 |
| 评分链是否容易理解 | 从每层输入、输出、待补及原因逐点阅读 | 本层只说本层的事，中文解释先于变量名 |
| 固定六席是否被误称为六只推荐 | 核对分数、动作及复核后状态 | 六席可含关注/回避，veto不改分、不补第七名；取消行业限额后显示集中风险 |
| Long是否覆盖希望研究的前沿方向 | 核查固定名单分类、公司依据和更新日期 | 用户关注的海外前沿及国内增长赛道作为研究选题，不等于盈利保证 |
| 历史和报价是否混淆 | 核对日期、锚点、父身份与overlay | 正式历史不重算；当前报价独立标时点 |

旧冻结时点和退役流程退出活动设计；任何实际数据删除、模型替换或收益规则切换仍需独立任务，不随文档整理执行。
