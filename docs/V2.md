有。对当前 V2 最有价值的不是再找一个“东财包装器”，而是补充三类真正独立来源：交易所/巨潮、BaoStock、通达信公共行情。推荐优先级如下。

  ### 1. 交易所官方数据：最应该增加

  建议把上交所、深交所、北交所作为 V2 证券主数据的权威来源，用于：

  - 股票代码和交易所；
  - 主板、创业板、科创板、北交所身份；
  - 上市日期；
  - 暂停、终止上市状态；
  - 停复牌信息；
  - 交易日和休市安排；
  - 官方公告交叉校验。

  上交所提供股票列表、待上市和暂停/终止上市公司信息；北交所也有官方股票列表和公告页面。上交所股票列表
  (https://www.sse.com.cn/assortment/stock/home/)、北交所股票列表 (https://www.bse.cn/nq/listedcompany.html)、北交所公告
  (https://www.bse.cn/disclosure/announcement.html)

  价值非常大：即使 Eastmoney 当天连续失败，V2 仍然知道股票属于哪个板块、何时上市、是否正常上市，不会再出现数千只股票 missing_listing_date 和
  board_identity_degraded。

  注意：交易所网页数据适合低频同步，不应每几秒抓取。应每天盘前更新并本地持久化。

  ### 2. 巨潮资讯：解决公司风险历史缺失

  巨潮资讯是深交所法定信息披露平台，并覆盖沪深等市场公告，适合建立公司风险证据基线。巨潮资讯
  (https://www.cninfo.com.cn/new/index?islogin=false&language=cn)

  建议用于：

  - ST、退市风险和风险提示公告；
  - 立案、处罚、监管函；
  - 重大诉讼、破产重整；
  - 业绩预告和重大修正；
  - 股权质押、解禁、减持；
  - 停复牌和异常波动公告。

  实施方式：

  - 第一次分批回填历史公告；
  - 保存公告唯一标识、代码、日期、类别和证据链接；
  - 以后只拉增量；
  - 上交所、北交所公告作为对应市场的交叉验证；
  - 不在14:50前临时查询219只股票的全部公告。

  这比再增加一个行情源更能解决当前“评分高但全部只能观察”的问题。

  ### 3. BaoStock：历史行情的良好免费备用

  BaoStock 官方说明无需注册，提供免费证券数据，并有复权因子相关资料。BaoStock (https://www.baostock.com/)、BaoStock复权说明
  (https://www.baostock.com/helpdocs/pdf/BaoStock%E5%A4%8D%E6%9D%83%E5%9B%A0%E5%AD%90%E7%AE%80%E4%BB%8B.pdf)

  适合：

  - 日线历史回填；
  - 复权历史交叉验证；
  - 20/61日成交额和波动特征；
  - Eastmoney/Tencent历史失败时备用；
  - 收盘后更新本地历史特征仓库。

  不建议用于：

  - 秒级实时推荐；
  - 14:50最后阶段即时请求；
  - 未经校验直接替换当前复权历史。

  接入前必须统一：

  - 复权方式；
  - 成交量和成交额单位；
  - 停牌日表示；
  - 日期边界；
  - 除权除息前后的价格连续性。

  ### 4. 通达信公共行情：值得测试的实时备用

  mootdx 可以读取通达信线上多股票行情、K线和分钟数据，也能读取本地通达信数据文件。mootdx项目 (https://github.com/mootdx/mootdx)、mootdx标准行情文档
  (https://www.mootdx.com/zh-cn/latest/api/quote1/)

  适合尝试：

  - 候选池实时行情备用；
  - 分钟尾段行情；
  - Tencent 超时时的候选报价fallback；
  - 日线历史交叉检查。

  但存在限制：

  - 公共服务器不是正式 SLA；
  - 节点质量、连接稳定性和数据时标需要实测；
  - 项目声明主要用于学习交流；
  - 不能直接作为唯一实时源。

  建议先作为实验源：

  Tencent候选行情
      ↓ 失败或超时
  通达信/mootdx
      ↓ 再失败
  最近有效报价 + stale标记

  连续实测稳定后，才允许进入正式 fallback。

  ### 5. AKShare：可以用，但不要误认为新数据源

  AKShare 提供大量股票接口，包括交易所、东方财富等数据的统一封装；其定位是财经数据采集、清洗和落地工具。AKShare项目说明
  (https://akshare.akfamily.xyz/introduction.html)、AKShare股票接口 (https://akshare.akfamily.xyz/data/stock/stock.html)

  它的价值是降低接入成本，但很多接口底层仍然来自：

  - Eastmoney；
  - Sina；
  - 交易所网页；
  - 其他公开站点。

  因此：

  - 可以用 AKShare 快速实现官方数据同步；
  - 监控中必须记录真正的底层来源；
  - 两个底层都调用 Eastmoney 的 AKShare 接口不能算双源容灾；
  - 不宜整体引入为隐藏全能数据层，最好提取独立适配器。

  ## 接入顺序

  建议不要一次性增加所有源：

  1. 先接交易所证券主数据，解决板块和上市日期缺失。
  2. 接巨潮资讯持久化风险登记簿，解决全部候选只能观察。
  3. 接 BaoStock 历史备用，解决重启和历史预热偏差。
  4. 对通达信/mootdx 做影子实测，稳定后作为候选实时备用。
  5. AKShare只用于降低上述官方数据适配成本。

  每个新源先进行三组并行对比，验证代码覆盖、时间戳、价格、涨跌幅、成交额、停牌状态和延迟；未通过校验前不能直接进入评分。这样增加的才是真正的数据冗余，
  而不是把更多不稳定接口同时塞进关键链路。



新方案不再是“V1 切换到 V2”，而是把 V2 建成唯一产品链路：独立进程、独立数据、独立调度、独立决策、独立 Web。V1 最终从仓库活动代码中完全删除；回退依靠
  旧 release/wheel 和 Git 提交，不在新版本里保留 V1 兼容代码。

  ## 一、最终目标

  整改完成后的唯一运行链路：

  免费数据源
      ↓
  V2 采集器与字段标准化
      ↓
  V2 本地数据仓库
    ├─证券主数据
    ├─实时行情
    ├─历史特征
    ├─公司风险证据
    └─交易日历
      ↓
  V2 候选生成
      ↓
  V2 过滤、评分、融合、排名
      ↓
  唯一 DecisionTrace
    ├─Current 实时快照
    └─Freeze 正式快照
      ↓
  V2 API / SSE / Web

  必须达到以下结果：

  - V2 运行不导入、不调用、不读取 V1 的代码、线程、API、数据库或快照。
  - 单个免费源失败不会导致全市场股票身份、历史和评分同时丢失。
  - 重启后直接使用最近有效数据，不重新从零预热。
  - 缺失字段都有具体来源、状态和处理规则。
  - “没有合格股票”和“输入异常导致空结果”严格区分。
  - 14:50 冻结不依赖最后几秒完成全量抓取和评分。
  - V2 页面能够解释股票为什么未评分、被过滤、只能观察或可以执行。
  - 最终活动代码树不存在 V1 业务实现、旧测试和旧 Web 资源。

  ## 三、全新的分批实施计划

  ### 第一批：重写 V2 唯一产品契约

  先修改权威文档和测试契约，明确不再存在双版本运行关系。

  主要工作：

  - docs/software-business-design.md 改为 V2-only 架构。
  - 删除 V1/V2 影子一致率和双版本切换定义。
  - V2 Web 成为根页面，V2 API 成为唯一业务 API。
  - 明确 V2 独立数据库、缓存、运行目录和配置目录。
  - 明确回退方式是完整旧 release，而不是在新进程内切换 V1。
  - docs/recommendation-strategy.md 只定义唯一候选、过滤、评分和排名链。
  - pyproject.toml 最终只保留 V2 CLI、Web 和后台工作入口。
  - 建立 V1 删除清单、V2 替代清单和数据迁移清单。

  新的发布门禁不再依赖 V1 对比，改为：

  - 同一输入重复计算结果完全一致；
  - current、published、freeze 使用同一决策哈希；
  - 回放结果与实时结果一致；
  - 数据完整度、延迟和冻结指标达到要求；
  - 所有故障注入通过。

  ### 第二批：解除 V2 对 V1 的全部依赖

  逐项扫描并移除这些依赖：

  - V2 等待 V1 快照发布；
  - V2 从 V1 snapshot 构造输入；
  - V2 依赖 V1 的冻结状态；
  - V2 读取 V1 数据库或运行目录；
  - V2 复用 V1 worker、调度器、全局状态；
  - V2 Web 跳转或回退到 V1 页面；
  - run.sh 默认启动 V1；
  - V2 状态 API 从 V1 状态对象拼装信息。

  V2 应独立拥有：

  - MarketDiscoveryService
  - QuoteRefreshService
  - FeatureRefreshService
  - RecommendationPipeline
  - CurrentSnapshotPublisher
  - FreezeCoordinator
  - StatusReadModel
  - 可停止、可等待、可观察的后台调度器

  bootstrap.py 仍是唯一组合根，create_app() 不启动线程、不访问网络、不写文件。

  验收：

  - 停止或删除 V1 后，V2 仍能独立启动和更新。
  - V2 测试不能通过构造 V1 对象来工作。
  - V2 freeze 不读取 V1 frozen 状态。
  - HTTP 请求只读，不触发行情抓取、评分或 DeepSeek。

  ### 第三批：建立 V2 字段级质量模型

  把当前混在行情行里的数据拆成五个模型：

  1. 证券主数据

     代码、交易所、板块、上市日期、行业、ST/退市状态。

  2. 实时行情

     价格、涨跌幅、成交额、换手率、量比、源时间、接收时间。

  3. 历史特征

     20/61日成交额、趋势、波动、量价特征、复权状态。

  4. 公司风险证据

     公告、处罚、质押、解禁、财务风险及证据完整性。

  5. 盘中特征

     分钟尾段、价格速度、短时变化和相应覆盖范围。

  每个字段统一使用：

  valid / degraded / stale / missing / conflicting

  同时建立字段要求表：

  - 是否是核心评分字段；
  - 最大允许年龄；
  - 允许的来源；
  - 来源优先级；
  - 缺失时硬过滤、观察限制还是降级；
  - 是否允许使用最近有效值；
  - 是否允许参与正式冻结。

  这一批必须验证并修正稳定身份替换逻辑，防止降级行情覆盖完整证券主数据。

  ### 第四批：建立 V2 独立持久化数据底座

  当前只预热约360只且重启丢失，是历史指标结构性缺失的主要原因。

  V2 建立独立本地仓库：

  #### 1. 证券主数据仓库

  - 成功获取后持久化；
  - 每日增量更新；
  - 保留来源和版本；
  - Sina/Tencent 降级期间继续使用最近有效身份；
  - 冲突数据进入隔离状态，不直接覆盖。

  #### 2. 全市场紧凑历史特征仓库

  不对5500只股票每轮下载完整历史，而是：

  - 全市场持久化20/61日紧凑特征；
  - 每日收盘滚动更新；
  - 候选股票保存更完整的复权K线；
  - 初次基线分批回填；
  - 回填失败不阻塞 current 和 Web。

  #### 3. 实时行情缓存

  - 全市场行情与候选高频行情分层；
  - 保存最近有效 epoch；
  - 数据源失败时采用 stale-while-revalidate；
  - 明确显示陈旧时间，不能伪装成新行情。

  #### 4. 决策和冻结仓库

  - current 快照可覆盖更新；
  - freeze 正式记录不可覆盖；
  - 每个决策保存输入版本、配置版本和哈希；
  - 所有正式记录使用 V2 独立 schema。

  验收：

  - 重启后证券主数据和历史覆盖率不会重新归零。
  - 热启动与冷启动候选基线一致。
  - 潜在可执行候选的板块、上市日期覆盖率100%。
  - 候选核心历史指标覆盖率不低于99%。
  - V2 数据不会写入旧运行库。

  ### 第五批：重构公司风险证据链

  不能继续在14:50前用几秒时间临时检查全部候选历史风险。

  建立 V2 风险登记簿：

  known_clear / known_risk / unknown / stale

  公告、财务、处罚、质押、解禁分别保存，不再把多个接口当成一个全有或全无的结果。

  刷新顺序：

  1. 前一日推荐和TopK。
  2. 当日候选池。
  3. 理论最高分可能达到73分的股票。
  4. 可能达到78分执行阈值的股票。
  5. 其他股票在后台逐步覆盖。

  处理策略：

  - 历史公告先完成一次基线回填，以后只取增量。
  - 单个组件失败保留其他成功组件。
  - 已有有效证据在短暂故障期间不清空。
  - unknown/stale 只能观察，不能执行。
  - 不允许把未知风险当成零风险。
  - 风险刷新线程不能抢占行情、评分和冻结资源。

  验收：

  - 潜在可执行候选风险覆盖率100%。
  - 单个风险接口失败不会使整只股票风险历史变为不可用。
  - 页面能明确显示缺失的风险组件和最后成功时间。
  - 不再出现219只候选全部因同一个风险总状态而不可执行。

  ### 第六批：建立 V2 唯一候选、过滤和评分链

  新增唯一的 DecisionTrace，一次计算后同时用于 current、Web 和 freeze。

  完整漏斗固定为：

  全市场
  → 行情有效
  → 主数据有效
  → 历史就绪
  → 候选预选
  → 核心字段完整
  → 已评分
  → 达到观察阈值
  → 达到执行阈值
  → 风险证据完整
  → 最终观察/可执行

  过滤原因拆成四类：

  - 输入无效：当前数据不能形成合法决策。
  - 硬过滤：股票本身不满足策略。
  - 观察限制：可以展示，但不能作为执行项。
  - 排名淘汰：合格但因行业、数量或排名未入选。

  每只候选保留完整审计：

  - 候选预选分；
  - 各评分组件；
  - 缺失字段和缺失比例；
  - 板块身份可靠度；
  - 本地基础分；
  - 本地风险扣分；
  - local_score；
  - DeepSeek结构化结果；
  - 最终融合分；
  - 排名和淘汰原因；
  - 观察或不可执行原因。

  固定约束不变：

  - 融合公式不变；
  - local_score 不重复扣本地风险；
  - DeepSeek自由文本不能直接扣分；
  - 不降低73/78阈值；
  - 不通过取消风险限制增加荐股数量；
  - 无效空结果不能覆盖最近有效结果。

  ### 第七批：重构 V2 实时调度与14:50冻结

  固定任务优先级：

  Freeze/checkpoint
  > 候选实时报价
  > 增量评分
  > 全市场刷新
  > 历史回填
  > 公司风险后台更新

  冻结时间线：

  - 14:48前完成候选和主要风险覆盖。
  - 14:48—14:49持续增量评分。
  - 14:49:20进入checkpoint窗口并封存最新完整决策。
  - 14:49:50只刷新目标候选报价锚点。
  - 14:50使用已封存checkpoint创建正式记录。
  - 最后10秒不执行全市场抓取、全量历史请求或194只完整重算。

  V2 的 FreezeCoordinator 必须直接由 V2 时钟和调度器驱动：

  - 不等待 V1；
  - 封存尝试对象后再执行外部I/O；
  - 重试必须针对同一个不可变对象；
  - 迟到结果不能覆盖正式记录；
  - freeze 失败时 current 仍持续更新并明确显示“未冻结”；
  - tomorrow/d25 继续遵守15:00后的 close_fallback 契约。

  验收：

  - 覆盖14:49:20、14:49:50、14:50:00.001等边界。
  - 模拟调度延迟、网络超时、CPU繁忙和进程重启。
  - 正式记录的决策哈希、输入版本和报价锚点一致。
  - 本地发布延迟P95不超过5秒。
  - 决策年龄P95不超过10秒。
