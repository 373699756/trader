# V2 唯一产品迁移计划

> 状态：目标概览、非生产契约。产品与架构以 `docs/software-business-design.md` 为准，
> 候选、过滤、评分和排名以 `docs/recommendation-strategy.md` 为准。计划可靠性评审、
> 当前基线和可执行 P0-P13 拆解以 `docs/V2_plan.md` 为准。

新方案不再是“V1 切换到 V2”，而是把 V2 建成唯一产品链路：独立进程、独立数据、独立调度、独立决策、独立 Web。V1 最终从仓库活动代码中完全删除；回退依靠
  旧 release/wheel 和 Git 提交，不在新版本里保留 V1 兼容代码。

  ## 一、最终目标

  整改完成后的唯一运行链路：

  免费数据源
      ↓
  V2 采集器与字段标准化
      ↓
  V2 本地数据仓库
    ├─证券主数据
    ├─实时行情
    ├─历史特征
    ├─公司风险证据
    └─交易日历
      ↓
  V2 候选生成
      ↓
  V2 过滤、评分、融合、排名
      ↓
  唯一 DecisionTrace
    ├─Current 实时快照
    └─Freeze 正式快照
      ↓
  V2 API / SSE / Web

  必须达到以下结果：

  - V2 运行不导入、不调用、不读取 V1 的代码、线程、API、数据库或快照。
  - 单个免费源失败不会导致全市场股票身份、历史和评分同时丢失。
  - 重启后直接使用最近有效数据，不重新从零预热。
  - 缺失字段都有具体来源、状态和处理规则。
  - “没有合格股票”和“输入异常导致空结果”严格区分。
  - 14:50 冻结不依赖最后几秒完成全量抓取和评分。
  - V2 页面能够解释股票为什么未评分、被过滤、只能观察或可以执行。
  - 最终活动代码树不存在 V1 业务实现、旧测试和旧 Web 资源。

  ## 二、免费数据源的固定职责

  只使用免费数据源，不引入付费服务。以下是 V2 唯一的数据源职责定义；后续章节只引用本节，
  不再重复定义主备关系。

  | 数据源 | 固定职责与主备路由 | 执行方式 | 降级边界 |
  | --- | --- | --- | --- |
  | 交易所官方（上交所/深交所/北交所） | 证券主数据、停复牌、交易所属性和交易日历；交易所公告用于对应市场交叉校验，东财只做异常对账 | 每日盘前低频同步并持久化 | 失败不替换或清空字段，保留最近有效主数据 |
  | 巨潮资讯 CNInfo | 公司风险证据基线、历史回填、增量更新和风险事件归档；对应交易所公告交叉验证 | 首次分批回填，此后按公告唯一标识增量同步 | 空结果不能清零历史风险；不在冻结前临时全量查询候选公告 |
  | 东方财富 Eastmoney | 全市场发现和第一快照；前复权日线作为腾讯失败后的回退 | 实时全市场主路由，历史数据离线更新 | 失败不清空快照，允许 stale-while-revalidate；迟到结果不得覆盖更新数据 |
  | 新浪 Sina | 全市场价格延迟对冲、故障回退和时序连续性补齐 | 东方财富未及时成功时启动 | 只能补行情，不能覆盖证券主数据、公司风险或更完整记录 |
  | 腾讯 Tencent | 候选池和 TopK 高频报价；完整前复权日线历史主来源 | 候选定向刷新，历史数据离线更新 | 不承担证券主数据和公司风险；部分失败时回退全市场行情或最近有效报价 |
  | 通达信/mootdx | 候选分钟尾段和实验级实时行情备用；日线仅用于交叉检查 | 先影子实测，稳定后才能进入正式 fallback | 不能作为唯一实时源；失败后使用最近有效报价并标记 stale |
  | BaoStock | 历史日线交叉校验、历史回填和复权一致性审计 | 仅在离线、收盘后或重建流程使用 | 不进入秒级实时和冻结前即时请求；失败不阻塞当日评分 |
  | Tushare 120 积分 | 未复权原始日线能力审计和历史校验 | 仅保留来源健康与参考版本 | 不进入候选、评分和冻结关键路径 |
  | AKShare | 行业口径、公告入口和财务聚合的公共数据适配器 | 按底层来源拆分独立适配器并记录真实来源 | 不作为隐藏的全能数据层；相同底层来源不能算双源容灾 |

  参考入口：

  - [上交所股票](https://www.sse.com.cn/assortment/stock/home/)、
    [北交所股票](https://www.bse.cn/nq/listedcompany.html/)和
    [北交所公告](https://www.bse.cn/disclosure/announcement.html)；
  - [巨潮资讯](https://www.cninfo.com.cn/new/index?islogin=false&language=cn)；
  - [BaoStock](https://www.baostock.com/)及其
    [复权说明](https://www.baostock.com/helpdocs/pdf/BaoStock%E5%A4%8D%E6%9D%83%E5%9B%A0%E5%AD%90%E7%AE%80%E4%BB%8B.pdf)；
  - [mootdx 项目](https://github.com/mootdx/mootdx)及其
    [标准行情接口](https://www.mootdx.com/zh-cn/latest/api/quote1/)；
  - [AKShare 项目说明](https://akshare.akfamily.xyz/introduction.html)及其
    [股票接口](https://akshare.akfamily.xyz/data/stock/stock.html)。

  数据合并必须从“整行覆盖”改成“字段级合并”：

  - 新价格可以更新价格字段，但不能清空上市日期。
  - Sina fallback 不能把完整 Eastmoney 记录降级成只有价格的记录。
  - Tencent 报价不能改变股票板块身份。
  - 数据时间倒退、页数异常或数量骤降时，隔离异常结果。
  - 每个字段保留来源、源时间、接收时间、质量状态和版本。

  接入顺序固定为：

  1. 先接交易所证券主数据，解决板块和上市日期缺失。
  2. 接巨潮资讯持久化风险登记簿，解决公司风险证据缺失。
  3. 接 BaoStock 历史备用，解决重启和历史预热偏差。
  4. 对通达信/mootdx 做影子实测，稳定后作为候选实时备用。
  5. AKShare 只用于降低上述公共来源的适配成本。

  每个新源先进行三组并行对比，验证代码覆盖、时间戳、价格、涨跌幅、成交额、停牌状态和延迟；
  未通过校验前不能进入评分。

  ## 三、全新的分批实施计划

  本节保留目标能力分组，不再作为实际施工顺序。当前实现已经完成其中部分 tomorrow v2
  能力，且数据模型、持久化、来源接入和切换存在新的依赖关系；实际执行以
  `docs/V2_plan.md` 的现状续建顺序和逐批退出条件为准。

  ### 第一批：重写 V2 唯一产品契约

  先修改权威文档和测试契约，明确不再存在双版本运行关系。

  主要工作：

  - docs/software-business-design.md 改为 V2-only 架构。
  - 删除 V1/V2 影子一致率和双版本切换定义。
  - V2 Web 成为根页面，V2 API 成为唯一业务 API。
  - 明确 V2 独立数据库、缓存、运行目录和配置目录。
  - 明确回退方式是完整旧 release，而不是在新进程内切换 V1。
  - docs/recommendation-strategy.md 只定义唯一候选、过滤、评分和排名链。
  - pyproject.toml 最终只保留 V2 CLI、Web 和后台工作入口。
  - 建立 V1 删除清单、V2 替代清单和数据迁移清单。

  新的发布门禁不再依赖 V1 对比，改为：

  - 同一输入重复计算结果完全一致；
  - current、published、freeze 使用同一决策哈希；
  - 回放结果与实时结果一致；
  - 数据完整度、延迟和冻结指标达到要求；
  - 所有故障注入通过。

  ### 第二批：解除 V2 对 V1 的全部依赖

  逐项扫描并移除这些依赖：

  - V2 等待 V1 快照发布；
  - V2 从 V1 snapshot 构造输入；
  - V2 依赖 V1 的冻结状态；
  - V2 读取 V1 数据库或运行目录；
  - V2 复用 V1 worker、调度器、全局状态；
  - V2 Web 跳转或回退到 V1 页面；
  - run.sh 默认启动 V1；
  - V2 状态 API 从 V1 状态对象拼装信息。

  V2 应独立拥有：

  - MarketDiscoveryService
  - QuoteRefreshService
  - FeatureRefreshService
  - RecommendationPipeline
  - CurrentSnapshotPublisher
  - FreezeCoordinator
  - StatusReadModel
  - 可停止、可等待、可观察的后台调度器

  bootstrap.py 仍是唯一组合根，create_app() 不启动线程、不访问网络、不写文件。

  验收：

  - 停止或删除 V1 后，V2 仍能独立启动和更新。
  - V2 测试不能通过构造 V1 对象来工作。
  - V2 freeze 不读取 V1 frozen 状态。
  - HTTP 请求只读，不触发行情抓取、评分或 DeepSeek。

  ### 第三批：建立 V2 字段级质量模型

  把当前混在行情行里的数据拆成五个模型：

  1. 证券主数据

     代码、交易所、板块、上市日期、行业、ST/退市状态。

  2. 实时行情

     价格、涨跌幅、成交额、换手率、量比、源时间、接收时间。

  3. 历史特征

     20/61日成交额、趋势、波动、量价特征、复权状态。

  4. 公司风险证据

     公告、处罚、质押、解禁、财务风险及证据完整性。

  5. 盘中特征

     分钟尾段、价格速度、短时变化和相应覆盖范围。

  每个字段统一使用：

  valid / degraded / stale / missing / conflicting

  同时建立字段要求表：

  - 是否是核心评分字段；
  - 最大允许年龄；
  - 允许的来源；
  - 来源优先级；
  - 缺失时硬过滤、观察限制还是降级；
  - 是否允许使用最近有效值；
  - 是否允许参与正式冻结。

  这一批必须验证并修正稳定身份替换逻辑，防止降级行情覆盖完整证券主数据。

  ### 第四批：建立 V2 独立持久化数据底座

  当前只预热约360只且重启丢失，是历史指标结构性缺失的主要原因。

  V2 建立独立本地仓库：

  #### 1. 证券主数据仓库

  - 成功获取后持久化；
  - 每日增量更新；
  - 保留来源和版本；
  - Sina/Tencent 降级期间继续使用最近有效身份；
  - 冲突数据进入隔离状态，不直接覆盖。

  #### 2. 全市场紧凑历史特征仓库

  不对5500只股票每轮下载完整历史，而是：

  - 全市场持久化20/61日紧凑特征；
  - 每日收盘滚动更新；
  - 候选股票保存更完整的复权K线；
  - 初次基线分批回填；
  - 回填失败不阻塞 current 和 Web。

  #### 3. 实时行情缓存

  - 全市场行情与候选高频行情分层；
  - 保存最近有效 epoch；
  - 数据源失败时采用 stale-while-revalidate；
  - 明确显示陈旧时间，不能伪装成新行情。

  #### 4. 决策和冻结仓库

  - current 快照可覆盖更新；
  - freeze 正式记录不可覆盖；
  - 每个决策保存输入版本、配置版本和哈希；
  - 所有正式记录使用 V2 独立 schema。

  验收：

  - 重启后证券主数据和历史覆盖率不会重新归零。
  - 热启动与冷启动候选基线一致。
  - 潜在可执行候选的板块、上市日期覆盖率100%。
  - 候选核心历史指标覆盖率不低于99%。
  - V2 数据不会写入旧运行库。

  ### 第五批：重构公司风险证据链

  不能继续在14:50前用几秒时间临时检查全部候选历史风险。

  建立 V2 风险登记簿：

  known_clear / known_risk / unknown / stale

  公告、财务、处罚、质押、解禁分别保存，不再把多个接口当成一个全有或全无的结果。

  刷新顺序：

  1. 前一日推荐和TopK。
  2. 当日候选池。
  3. 理论最高分可能达到73分的股票。
  4. 可能达到78分执行阈值的股票。
  5. 其他股票在后台逐步覆盖。

  处理策略：

  - 历史公告先完成一次基线回填，以后只取增量。
  - 单个组件失败保留其他成功组件。
  - 已有有效证据在短暂故障期间不清空。
  - unknown/stale 只能观察，不能执行。
  - 不允许把未知风险当成零风险。
  - 风险刷新线程不能抢占行情、评分和冻结资源。

  验收：

  - 潜在可执行候选风险覆盖率100%。
  - 单个风险接口失败不会使整只股票风险历史变为不可用。
  - 页面能明确显示缺失的风险组件和最后成功时间。
  - 不再出现219只候选全部因同一个风险总状态而不可执行。

  ### 第六批：建立 V2 唯一候选、过滤和评分链

  新增唯一的 DecisionTrace，一次计算后同时用于 current、Web 和 freeze。

  完整漏斗固定为：

  全市场
  → 行情有效
  → 主数据有效
  → 历史就绪
  → 候选预选
  → 核心字段完整
  → 已评分
  → 达到观察阈值
  → 达到执行阈值
  → 风险证据完整
  → 最终观察/可执行

  过滤原因拆成四类：

  - 输入无效：当前数据不能形成合法决策。
  - 硬过滤：股票本身不满足策略。
  - 观察限制：可以展示，但不能作为执行项。
  - 排名淘汰：合格但因行业、数量或排名未入选。

  每只候选保留完整审计：

  - 候选预选分；
  - 各评分组件；
  - 缺失字段和缺失比例；
  - 板块身份可靠度；
  - 本地基础分；
  - 本地风险扣分；
  - local_score；
  - DeepSeek结构化结果；
  - 最终融合分；
  - 排名和淘汰原因；
  - 观察或不可执行原因。

  固定约束不变：

  - 融合公式不变；
  - local_score 不重复扣本地风险；
  - DeepSeek自由文本不能直接扣分；
  - 不降低73/78阈值；
  - 不通过取消风险限制增加荐股数量；
  - 无效空结果不能覆盖最近有效结果。

  ### 第七批：重构 V2 实时调度与14:50冻结

  固定任务优先级：

  Freeze/checkpoint
  > 候选实时报价
  > 增量评分
  > 全市场刷新
  > 历史回填
  > 公司风险后台更新

  冻结时间线：

  - 14:48前完成候选和主要风险覆盖。
  - 14:48—14:49持续增量评分。
  - 14:49:20进入checkpoint窗口并封存最新完整决策。
  - 14:49:50只刷新目标候选报价锚点。
  - 14:50使用已封存checkpoint创建正式记录。
  - 最后10秒不执行全市场抓取、全量历史请求或194只完整重算。

  V2 的 FreezeCoordinator 必须直接由 V2 时钟和调度器驱动：

  - 不等待 V1；
  - 封存尝试对象后再执行外部I/O；
  - 重试必须针对同一个不可变对象；
  - 迟到结果不能覆盖正式记录；
  - freeze 失败时 current 仍持续更新并明确显示“未冻结”；
  - tomorrow/d25 继续遵守15:00后的 close_fallback 契约。

  验收：

  - 覆盖14:49:20、14:49:50、14:50:00.001等边界。
  - 模拟调度延迟、网络超时、CPU繁忙和进程重启。
  - 正式记录的决策哈希、输入版本和报价锚点一致。
  - 本地发布延迟P95不超过5秒。
  - 决策年龄P95不超过10秒。

  ### 第八批：重建 V2 API、SSE 和 Web

  V2 页面成为唯一首页，至少展示：

  #### 数据源健康

  - Eastmoney、Sina、Tencent等最近成功时间；
  - 成功率、延迟、超时、断路状态；
  - 当前采用的主源和fallback；
  - DeepSeek真实预算使用量。

  #### 数据完整度

  - 全市场数量；
  - 证券主数据覆盖；
  - 历史特征覆盖；
  - 公司风险覆盖；
  - 盘中特征覆盖；
  - stale、missing、conflicting数量。

  #### 评分漏斗

  - 全市场、候选、已评分、阈值合格；
  - 观察项和可执行项；
  - 各过滤原因及明确分母；
  - 最高分和阈值附近股票。

  #### 单只股票诊断

  - 评分组件；
  - 数据来源；
  - 数据时间；
  - 缺失字段；
  - 风险证据；
  - 为什么未评分、被过滤或只能观察。

  #### 冻结状态

  - 最新current版本；
  - checkpoint版本；
  - 14:50冻结状态；
  - freeze失败原因；
  - 是否使用close fallback。

  所有原因码必须提供具体中文解释，禁止统一显示“运行条件暂不完整”。

  SSE 必须继续验证游标恢复、慢客户端、断线重连和版本单调性。

  ### 第九批：删除全部 V1 并切换唯一入口

  V2所有替代能力完成后，执行完整删除：

  - V1业务包；
  - V1服务和worker；
  - V1路由与API；
  - V1模板、CSS、JavaScript和图标；
  - V1配置；
  - V1测试；
  - V1数据库适配和迁移逻辑；
  - V1/V2影子比较器；
  - V1兼容层和别名；

  ## 四、最终发布门禁

  由于不再以V1作为对照，V2需要更严格的自验证。

  - 候选核心历史覆盖率不低于99%。

  ## 五、执行顺序

  每次“继续”只完成 `docs/V2_plan.md` 中下一个完整未完成的同级 P 批次，不再按本文九个
  高层能力组直接施工。每批都必须完成契约、测试、实现、Review、CHANGELOG、完整门禁、
  单一提交和推送后停止。最终结果不是双链长期共存，而是仓库和运行环境中只剩唯一 V2
  活动链；历史冻结所需的只读版本解码器不视为活动旧链。
