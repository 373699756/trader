  ## 二、文件应当怎样分层

  不建议一个大而全的 config.json，建议分成两层。

  ### 1. 仓库内稳定规则

  例如：

  config/reference_rules/
  ├── market_structure.json
  ├── trading_rules.json
  ├── industry_taxonomy.json
  └── reference_policy.json

  这里可以保存：

  - 板块识别规则；
  - 交易制度参数；
  - 行业体系名称和合法值；
  - 数据完整率门槛；
  - 软过期、硬过期时间；
  - 数据源优先级。

  这些文件可以随代码提交、审查和发布。

  ### 2. 本机慢变化参考快照

  例如：

  .runtime/reference/
  ├── active-manifest.json
  └── bundles/
      └── <content-hash>/
          ├── security-master.json
          ├── model-industry.json
          ├── trading-calendar.json
          └── index-membership.json

  这部分不提交 Git，也不属于历史行情或训练数据。

  每条行业记录至少包含：

  {
    "code": "600000",
    "industry_id": "J66货币金融服务",
    "classification": "证监会行业分类",
    "effective_date": "2026-09-01",
    "observed_at": "2026-09-14T08:40:00+08:00",
    "source": "baostock",
    "data_version": "baostock-industry:2026-09-14:...",
    "payload_hash": "..."
  }

  关键是不能只保存 code + industry，必须保留来源、生效日期、观测时间和完整性哈希。

  ## 三、更新机制

  建议采用“盘后生成、启动恢复、后台刷新、原子切换”。

  外部供应商
      ↓
  下载候选快照
      ↓
  标准化和类型校验
      ↓
  覆盖率、分类体系、日期、冲突检查
      ↓
  生成 manifest 和 SHA-256
      ↓
  写入新 bundle
      ↓
  原子切换 active-manifest
      ↓
  内存索引热更新

  具体规则：

  1. 每个交易日盘后约 18:30 更新证券主数据、行业和指数成分。
  2. 每年提前获取下一年度交易日历，运行中每周校验。
  3. 程序启动先加载本机最近有效快照，不等待网络。
  4. 快照过了软期限，后台刷新，但不阻塞荐股。
  5. 刷新失败继续使用最近有效版本，并显示降级状态。
  6. 超过硬期限时只过滤受影响股票，不能把整个策略漏斗清零。
  7. 新快照必须完整通过校验才允许替换旧快照。
  8. 保留最近几个有效 bundle，可快速回退，但不写入历史训练库。

  建议的有效期：

   数据                      软过期                硬过期
  ━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━
   证监会行业                   7天                  45天
  ──────────────────  ──────────────  ────────────────────
   证券主数据                   1天                   7天
  ──────────────────  ──────────────  ────────────────────
   交易日历            必须覆盖当日    不覆盖当日即不可用
  ──────────────────  ──────────────  ────────────────────
   指数成分                     7天                  45天
  ──────────────────  ──────────────  ────────────────────
   ST、停复牌等状态            当日      隔日不可继续使用

  ## 四、快照验收条件

  不能因为供应商返回了 HTTP 成功就替换旧文件，至少检查：

  - 行业记录数量达到合理下限；
  - 对当前可发行证券的覆盖率达到门槛；
  - 行业值属于模型支持的证监会行业集合；
  - 不存在相同股票、相同生效日对应两个行业；
  - 生效日期不得晚于评分日期；
  - 单日大规模行业变化超过阈值时进入隔离，不自动启用；
  - 文件哈希与 manifest 一致；
  - 加载失败时旧内存快照不被清空。

  推荐门槛：

  - 全市场行业覆盖率不低于 95%；
  - 进入三种策略模型输入前的行业覆盖率不低于 99%；
  - 单日行业变化超过 3%时要求人工复核；
  - 供应商返回数量明显低于上一有效版本时拒绝切换。

  ## 五、荐股链路怎样提速

  优化后的荐股阶段应当是：

  启动加载本地参考快照
          ↓
  建立 code → typed reference 内存索引
          ↓
  动态候选产生
          ↓
  一次内存关联行业、证券资料和规则
          ↓
  三种模型评分

  荐股运行时不再：

  - 临时请求全市场行业；
  - 每只股票单独查询证券资料；
  - 重复解析 JSON；
  - 从历史训练数据反查行业；
  - 因为一次供应商超时把全部模型输入清零。

  JSON 或本地数据库只在启动、后台更新时读取一次，评分时直接访问不可变内存索引。目标可以设为：

  - 5,000 多条参考数据启动加载低于 300ms；
  - 候选关联过程不产生网络调用；
  - 单一参考源失败不影响 Web；
  - 行业缺失只影响对应股票；
  - 漏斗明确显示“行业缺失、快照过期、模型不支持行业”的各自数量。

  ## 六、实施计划

  1. 建立参考数据分类契约
     明确哪些是固定规则、慢变化参考和实时数据，禁止跨层 fallback。

  2. 建立版本化参考 bundle
     定义 manifest、数据 schema、哈希、有效期和原子切换协议。

  3. 将证券主数据、证监会行业、交易日历接入统一内存索引
     启动先恢复，后台更新，不阻塞策略。

  4. 增加更新脚本
     提供检查、生成和激活三个独立动作；默认只检查，只有校验通过才能激活。

  5. 改造三种策略输入
     today-v3、tomorrow-v3、d25-v3 使用同一份模型行业参考；展示行业继续独立使用，禁止近似映射。

  6. 完善漏斗和诊断
     分别展示参考快照记录数、覆盖率、版本、年龄、拒绝原因和最后更新结果。

  7. 增加异常回归测试
     覆盖空响应、部分响应、旧快照、未来生效日期、冲突分类、供应商超时及原子回退。

  8. 最终运行真实 5000 服务验收
     验证程序重启后无需等待行业网络查询，三种策略能立即越过“模型输入”节点。

  这套优化不需要修改历史行情下载、历史归档、训练样本生成或模型训练逻辑。当前已经实现的 BaoStock 行业持久化可以作为参考快照的数据来源，下一步重点应是统一快照生命周期和冷启动恢复，而不是再增加一套手工股票行业映射。

  更新流程：

  1. 生成 .runtime/reference/reference_snapshot.next.json。
  2. 完整解析并检查覆盖率、日期、分类冲突和记录数量。
