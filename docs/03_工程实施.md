## 2. 评分模块化交付记录

原方案在局部拆文件与系统性收敛之间选择了后者：公共层只认识策略能力，不判断 V1/V2/V3 的算法差异；
档位差异集中在 `infra/scoring/profiles/`；训练与生产只共享纯特征计算、类型化合同、模型工件线格式和
内容 hash。该目标架构已经落地，当前主要边界为：

```text
domain/recommendation/model_scoring/         纯残差化、分位与档位身份
application/ports/model_scoring.py           类型化模型评分端口
application/recommendation/model_scoring_router.py
application/recommendation/tomorrow_model_scoring.py
infra/scoring/profile_factory.py             唯一 profile 组装入口
infra/scoring/profiles/{v1,v2,v3}/           各档位 codec、predictor 与证据
```

profile 只组装已经构造完成的能力；codec 只负责 JSON 到不可变类型对象及 schema/hash 校验；predictor
只接受类型化工件和输入并批量推理；locator 只定位工件；composition 只组合预风险模型信号。硬过滤、
DeepSeek、本地风险、固定融合、动作、TopK、冻结、持久化和 Web 投影不进入 profile 目录。

不得定时、在线或无人授权地自动训练/调参、自动晋级、自动激活或自动回退。

### 3.3 `tomorrow_v3_training_validation`

V3 是新的唯一 Tomorrow 模型，C3 只表示其离线训练阶段，不产生独立 profile，不做投票或 stacking，不读取 V1/V2/C3 运行时预测。训练切分使用下载数据库实际可用的共同完整交易日（只使用下载数据库中实际存在的记录），先保留最新 200 日；模型为 Ridge/LightGBM 50/50。
缺历史、行业或资格事实时返回 `historical_data_insufficient`，不生成伪模型。

它可以在用户显式 `--profile v3` 启动或性能门禁中参与评分，用于证明数据到评分/API 的工程接缝；不得解释为
