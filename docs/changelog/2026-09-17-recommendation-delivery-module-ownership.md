# Clarify Recommendation Delivery Module Ownership

## User Request

纠正重构蓝图把 `download/`、`training/`、`recommendation/`、`http_api/`、`web/` 全部表述为五个并列产品能力的错误：下载、训练和荐股才是三个独立业务；HTTP API 与 Web 只为荐股提供接口和展示，因功能模块独立而放在最外层。同时裁决蓝图中新增的 TODO：诊断状态是否落库、稳定资格是否需要联网刷新、缺失字段如何分级扣分，以及监控模态框与主页正式池/观察池的边界。

Regression-Key: `refactor-blueprint-single-architecture-truth`

## Cause

已确认目标目录的“物理并列”被误写成“业务所有权并列”。局部说明虽已把 HTTP 和 Web 称为只读边界，但第 1、2、3、6、10 和 11 章仍使用“五个顶层产品能力”、“五个独立能力块”等语句，导致实施者无法确定业务所有者。新增 TODO 还暴露出诊断状态与业务持久化混淆、稳定资格被误解为永不联网、质量扣分缺少字段级合同，以及监控模态框可能重复主页结果区等实施歧义。

## Added

- 增加顶层目录所有权表，分别标明目录分类、业务所有者和允许职责。
- 增加“物理目录层级不决定业务所有权”的强制解释规则。
- 增加一级稳定资格快照的恢复、有效期校验、后台增量刷新和失效处理合同。
- 增加缺失字段按用途、严重度、扣分上限和后续资格处理的显式矩阵。

## Changed

- 目标业务固定为 `download/`、`training/`、`recommendation/` 三个独立业务。
- `http_api/` 与 `web/` 固定为 `recommendation/` 的外置交付模块：它们保留顶层物理目录，但不拥有独立业务语义、运行状态或决策权。
- HTTP/API 只能调用 `recommendation/application/` 公开的只读用例，Web 只能消费荐股已发布结果和诊断投影；两者不定义下载或训练业务。
- 统一修订评审结论、重构目标、目录设计、能力边界、功能所有权索引、强制实施顺序和结论中的所有权口径。
- 流水线阶段、来源健康和近期错误保持为当前进程内的有类型状态，由 HTTP 边界投影；不新增诊断数据库、文件归档或流水线事件表。
- 监控入口固定为主页新增的只读模态框，仅展示候选、过滤、数据质量、评分、风险和融合的聚合状态；正式池、观察池和现有主页布局保持不变。
- 项目自有接口、类型、模块、函数和变量禁用 `Store`、`Repository`、`Archive`、`Registry` 等泛称，改用 `Index`、`Cache`、`Snapshot` 或直接表达业务职责的具体名称；目录树同步采用 `history_maintenance/`、`history_partitions/`、`decision_records.py` 和 `eligibility_ledger.py`。
