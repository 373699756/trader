# 荐股数据链路现状与实测计划

本文记录荐股数据链路的工程现状、可观测性要求、运行证据和后续执行顺序。产品/API/架构合同以 `docs/项目重构详细.md` 为准，评分合同以 `docs/01_评分逻辑.md` 为准；阶段进度只登记在 `docs/03_工程实施.md`，本文不另建第二份进度台账。

## 目标与不可变边界

1. 静态参考数据在进程内按不可变快照复用；只有参考版本变化或明确刷新时才生成新的 `reference_epoch`，行情轮询不能重复获取静态基线。
2. 动态行情按配置周期采集。一次采集形成新的 `market_epoch`，与对应 `reference_epoch`、交易日和观察时间组合成输入批次；数据新鲜度与参考数据新鲜度分别判断。
3. 每个阶段只消费紧邻上游的不可变输出，产生自己的新列表/tuple 和批次身份。阶段之间校验 `previous.output_batch_id == current.input_batch_id` 及人口连续性；不得原地修改上游或通过前端差值制造人口。
4. Web/API/SSE 只读取后端已形成的状态和已发布决策，不发起行情、评分、历史恢复或 DeepSeek 工作。
5. 推荐展示只在完整不可变发布节点替换。短线决策以 `decision_version` 作为 `publication_id`；报价 overlay 单独发布并校验父决策身份。阶段快照只更新诊断状态，不能逐股改写推荐内容。SSE 发布 `decision`/`overlay`；游标过期、事件缺口或慢订阅者移除时通过 `resync_required` 回到完整 GET。仅在 SSE 不可用时使用有界轮询。
6. 展示链固定为 14 层。第 14 层必须保留为“TopK、集中度、冻结与发布”，不得拆成多个展示/业务阶段。`RecommendationPipelineStatus` 的 16 个评分子阶段 key 是另一种类型化决策/评分状态投影，不是第二套业务流水线，不能拼入 14 层漏斗。
7. 每层记录真实的 input/output、业务拒绝、待补充、失败、原因聚合、耗时、批次身份和来源健康。只有业务过滤阶段可以计算业务拒绝率；数据缺失、来源失败、待刷新、质量待补充、评分未选中、风险否决和发布阻止都不得伪装成过滤拒绝。

展示顺序固定为：数据源 → 静态采集 → 静态标准化 → 一级稳定过滤 → 动态采集 → 动态标准化 → 二级动态过滤 → 候选生成 → 质量评估 → 评分 → 风险复核 → 固定 68/32 融合 → 下行保护与动作门 → TopK、集中度、冻结与发布。第 14 层不能再拆。

## 当前工程事实

- 阶段快照和业务输出已有类型化实现：`PipelineStageOutput` 是冻结 dataclass，阶段记录转换为 tuple；`PipelineStageSnapshot` 携带阶段顺序、输入/输出批次身份、人口计数、原因、来源健康和耗时。`stage_output()` 只为静态过滤和动态过滤构造 `BusinessRejectionSummary`。
- 行情特征缓存以 `reference_epoch` 校验静态参考版本，版本变化时不能复用旧全市场特征缓存；市场状态还区分 `market_epoch` 与 `reference_epoch`。这是静态/动态身份隔离的现有基础，不等于全部阶段已由一条生产编排逐层执行。
- 运行时状态能投影完整 14 层快照，Web 读取后端快照中的拒绝数，不应自行用 input-output 计算“淘汰”。冻结/发布仍是第 14 层单一边界。
- 静态/动态阶段模块已有独立 builder，但截至阶段 41 台账，它们仍待接入统一应用编排。`build_first_nine_stage_snapshots()` 在有完整 `stage_facts` 时投影逐阶段事实；没有事实时仍有基于聚合计数补齐前九层的路径，部分阶段的耗时/来源健康也是合成值。不能仅凭“接口存在”或“快照有 14 层”声称这些字段均来自实际逐层执行。
- 配置的全市场采集周期在常见盘中 phase 为 10 秒；候选行情和 TopK 行情另有独立 cadence（phase 配置分别为 1–10 秒和 1–10 秒），分钟尾部数据为 3–5 秒。它们是当前 `config/runtime.json` 配置，不是实测吞吐或供应商保证。实际频率、重复静态读取、完整行情覆盖和各阶段耗时需从真实运行批次验证。
- 不使用固定“5221 只”“1120 只”或旧 TTL 作为当前运行结论。预期人口应绑定当次证券主数据版本；实际数量、缺失代码、来源年龄和失败原因只能来自同一运行批次的后端状态。

## 可执行计划

按顺序执行，每一步保存脱敏诊断摘要和同一 `run_id`/批次的阶段快照。未满足前置条件时停在该步，不用合成值填空。

1. **建立真实运行基线**：在服务所在主机/网络上下文执行 `./.venv/bin/python3 scripts/diagnose_runtime.py --profile runtime --output -`，记录 `runtime_version`、运行 phase、策略/交易日、当前发布身份、状态样本数和结果。若默认端口不可达，先查明服务地址和进程归属；不要将沙箱 `connection_failed` 认作产品故障，也不要擅自重启用户服务。
2. **验证静态基线复用**：对同一运行连续采集至少两个全市场周期，记录 `reference_epoch`、静态证券主数据版本/人口、刷新次数、缓存命中和静态读取耗时；行情 epoch 应变化而静态 epoch 保持不变。显式刷新参考数据后，验证新 `reference_epoch` 产生且相关特征缓存失效。期望证据由现有健康状态提供；若没有计数，先补 owner 侧观测，不从 Web/日志文本猜测。
3. **验证动态输入批次**：记录每轮 `market_epoch`、采集时间、预期/收到/有效/待补充/失败人口、来源及来源年龄；核对不同全市场轮次身份不同，候选/TopK 刷新不伪装成新的全市场 epoch。至少覆盖一次完整行情和一次受控部分覆盖/失败降级；失败试验只在隔离进程或可丢弃环境执行。
4. **验证真实 14 层串联**：使用同一 `run_id` 检查 1–14 层顺序、前后 `batch_id` 与人口连续性、每层真实 duration/source health/reason aggregates，以及过滤层之外 `rejected_count`/拒绝率为零或不适用。对静态/动态采集与标准化若耗时固定为 0、健康/时间与运行观察点完全相同或人口由聚合差值补齐，记为 instrumentation gap，而不是通过验收。
5. **验证 API/Web/SSE 只读发布**：对照后端 14 层快照与 `/api/status`/观察页面逐字段核对；确认 Web 无业务计数推导和供应商副作用。先 GET 完整决策，再通过 SSE 收到阶段诊断及 `decision`/`overlay` 事件；验证 publication identity、游标恢复/`resync_required` 和受控有界轮询。不得把 16-key 评分状态混为 14 层展示。
6. **覆盖时序和故障场景**：在隔离环境分别验证常规热运行、冷启动、15:00 first-wins 冻结边界、15:00 后正式记录命中及合法 `close_fallback`。记录适用/不适用项；供应商失败保留最近有效快照但明确 stale、年龄、失败类别。DeepSeek 预算、正式冻结记录与运行数据库不得由故障注入污染。
7. **形成实现切片与回归证据**：按首个缺失 owner 修复阶段事实生产或统一编排，确保每一阶段只消费上游不可变输出；API/SSE/Web 只读消费端到端改为使用这些快照。仅当荐股核心行为或公开合同变化时补最小充分测试；文档-only 批次运行完整 diff review 与 `git diff --check`。
8. **真实复测并收口**：在获准的隔离运行目录启动修改后的服务，等待一次完整刷新并做多轮 `runtime` 诊断；浏览器/Web 改动再跑三档桌面门禁。供应商探测使用 `sources`/`live` 会产生真实外部请求并消耗配额，须在执行前确认来源凭据、额度和运行窗口。不得读写活动历史/冻结数据来完成验证。
