## 1. 适用与优先级

1. 遵守用户明确要求和仓库强制规范。
2. 沿用仓库 formatter、linter、type checker 和测试框架。
3. 新增和实际修改的语句遵守既有 formatter；保留未涉及代码的布局，不主动进行纯格式整理。
4. 不为了满足本规范而扩大无关 diff。

## 2. 模块与导入

必须：

- 使用绝对、明确的导入；包内相对导入仅在仓库已有清晰约定时使用。
- 禁止 `from module import *`。
- 导入位于文件顶部，按标准库、第三方、本地包分组；仅为解决可证明的可选依赖、平台差异或循环问题使用局部导入。
- 不通过修改 `sys.path` 让测试或运行“碰巧可用”。正确安装包或配置受支持的入口。
- 模块导入不得启动网络、创建线程、修改外部状态或执行昂贵工作。

应该：

- 导入模块还是对象，以调用处最容易识别来源为准。
- 把仅供类型检查的昂贵或循环导入放入 `TYPE_CHECKING`，但确保运行时注解策略正确。
- 保持 `__init__.py` 轻量；只在仓库允许的明确公共边界导出对象。Trader 禁止为旧路径或旧名称保留兼容导出、转发模块。

## 3. 命名、格式与可读性

本节是Trader命名规范的唯一维护位置；AGENTS.md、业务文档和其它skill只保留引用。新增或本次实际修改的Python命名使用以下分类，不能用“所有函数都按PEP 8小写”覆盖公开接口规则：

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 跨模块公开的顶层函数，包括异步函数 | 大驼峰 `PascalCase`，无前导下划线 | `LoadPrices`、`ParseTradingDate`、`IsEligible` |
| 公开类、异常、Protocol、类型别名 | 大驼峰 `PascalCase` | `PriceWindow`、`PriceSourceError`、`PriceSourcePort` |
| 模块内部顶层函数 | 单前导下划线 + `snake_case` | `_parse_row`、`_validate_window` |
| 模块内部类或类型 | 单前导下划线 + `PascalCase` | `_ParsedRow` |
| 公开方法、属性 | `snake_case` | `load_prices`、`is_ready` |
| 非公开方法、属性、实例成员 | 单前导下划线 + `snake_case` | `_load_prices`、`_session` |
| 模块、参数、局部变量 | `snake_case`，参数和局部变量默认无前导下划线 | `price_source.py`、`timeout_seconds` |
| 常量 | `UPPER_SNAKE_CASE`；模块私有常量加单前导下划线 | `MAX_ATTEMPTS`、`_MAX_ATTEMPTS` |

公开边界由承诺的接口和真实消费者确定：跨模块导入、入口注册、回调导出与文档声明都要检查。使用明确接口或 `__all__` 暴露；`__all__` 只列真实公开符号，不能把 `_helper` 列入其中来掩盖越界，也不能遗漏实际跨模块调用来声称它是私有函数。

`PascalCase` 指每个单词首字母大写，不是全大写；函数名通常以动作或谓词开头。局部变量只有明确丢弃或因接口约束未使用时才用 `_` 或 `_name`。Python 双下划线协议方法、第三方要求的回调/覆盖方法及 pytest 发现名称（如 `__enter__`、`model_post_init`、`test_*`）按固定合同保留；外部 JSON/SQL/HTTP 字段不随 Python 符号改名。

公开符号迁移必须：

1. 确认定义 owner、实际可见性和全部消费者；只有公开边界变化或已授权命名迁移才改既有名称。
2. 同批更新定义、导入、调用、类型引用、`__all__`、入口字符串、mock/patch 目标和有关文档。
3. 删除旧定义、旧名别名和转发路径；搜索旧标识并区分活动引用、外部固定字面量和不可改历史文本。
4. 按风险验证导入、入口和消费者；不通过把公开函数改为私有或扩大 lint 豁免来规避规则。

未改变职责、可见性和消费者的既有符号，不得仅为风格增删下划线，也不得在后续批次无新证据改回。现有命名不一致本身不是发起整理或扩大任务范围的理由；确需改变公开边界时，说明合同变化并与全部消费者原子改名。

Trader 新增或迁移的项目模块、类、函数、类型和其它符号还须遵守以下职责命名约束：

- 禁用 `store`、`stored`、`*Store`、`Repository`、`Archive`、`Registry`，包括大小写和 `snake_case` 变体。现有禁用名称随所属业务和全部消费者一次切换，不保留兼容别名或转发路径；外部协议、SQL/HTTP 标准字面量和不可变历史文本保持原样。
- 按真实职责选择 `Index`、`Cache`、`Snapshot` 或直接表达业务行为的具体名称，不把禁用词机械替换为 `Manager` 等泛称。`Artifacts` 不是全局禁词，但对象实际只是一组模型、样本或快照时，应直接写明 `Models`、`Samples` 或 `Snapshots`；不要用笼统的 `Artifacts` 掩盖内容和 owner，例如缺模型异常用 `ScoringModelsMissingError`。
- 一个职责只设一个活动 owner；模块和目录名称应反映该 owner。顶层业务只用 `download/`、`training/`、`recommendation/`；`http_api/` 与 `web/` 是只读交付边界，顶层 `infra/` 只放跨业务技术 primitive。不得为旧路径造转发模块、兼容导出或重复实现。
- 项目版本命名使用当前生产档位V2/V3，以及用户已授权的全新V1算法档位；不得新增其它 `vN` 项目版本命名。全新V1与退役旧V1身份分离，不按同名重解释旧实现、数据或冻结记录；业务准入与启用仍遵守AGENTS.md和评分权威。供应商模型名、Python/包版本、日期和随机种子不属于项目版本身份。

- 命名要专业且通俗：使用领域内公认、含义准确的词，让同事不查注释也能看懂职责；在不损失含义时选最短的清晰名称，避免生造术语、堆砌词语和非通用缩写。需要单位时写明，例如 `timeout_seconds`；避免 `data`、`obj`、`tmp`、`manager` 等无边界名称。
- 布尔值和方法使用可读谓词，如 `is_ready`、`has_access`；公开顶层谓词函数相应写作 `IsReady`、`HasAccess`。
- 不覆盖内置名称，不使用难辨认的单字符名称；短循环索引和明确数学符号可例外。
- 禁止无意义的纯格式改动：不得仅为整齐、统一风格或个人偏好，把一行参数、容器或表达式机械拆成多行，也不得反向合并、重排空行或更换引号。功能修复和测试补充不得顺带重排周边代码。
- 新增代码一次按仓库 formatter 要求书写。已有代码只有在用户明确要求格式整理，或本批实际修改的语句无法通过既有格式门禁时，才调整必要的最小范围；不得借 formatter 扩大到未涉及语句、整文件、目录或全仓。提交前剔除与任务无关的纯格式 diff。
- 一行一个逻辑语句，不使用分号拼接。
- 比较 `None` 使用 `is`/`is not`；比较布尔值通常直接使用真值，不写 `== True`。
- 对序列使用真值判断空/非空；当 `0`、空容器和 `None` 语义不同，显式判断。

## 4. 函数与控制流

必须：

- 避免可变默认参数。使用 `None` 或工厂创建新对象。
- 入口处校验前置条件，核心流程使用早返回减少嵌套。
- 函数的副作用、错误和返回约定必须可推断；不要有时返回值、有时隐式返回 `None`。
- 不使用 `assert` 校验用户输入、权限或运行时业务条件，因为优化模式可移除断言。
- 不在 `finally` 中用 `return`、`break` 或 `continue` 吞掉异常。

应该：

- 一个函数负责一个层级的决策。参数过多时先检查职责是否混合，再考虑参数对象。
- 把纯计算与数据库、网络、时钟和随机数等副作用分开，并显式传入依赖。
- 推导式只表达简单映射/筛选；出现多层循环、复杂条件、副作用或异常处理时改用普通循环。
- `lambda` 只用于局部、短小且无需文档的一次性表达式；有领域含义时使用命名函数。
- 生成器用于流式处理，但要明确资源生命周期和只能消费一次的语义。

## 5. 类、数据与状态

- 只有当状态与行为确实共同维护不变量时才引入类；不要用只有静态方法的类模拟模块。
- 简单记录优先使用合适的数据对象，例如 dataclass、NamedTuple 或项目既有模型；不要为每个字段手写无价值 getter/setter。
- 使用属性维护轻量、无惊讶的访问语义；昂贵 I/O、可能失败或具有副作用的操作应是显式方法。
- 组合通常优先于深继承。继承必须满足可替换性，并保持基类契约。
- 禁止无保护的可变模块全局状态。常量应不可变或视为不可变。
- 复制可变输入或清楚声明所有权，不要让调用者和被调用者意外共享可变容器。
- `__repr__`、异常文本和调试输出不得泄露机密。

## 6. 类型标注

必须：

- 遵守项目支持的最低 Python 版本和类型检查器语法。
- 公共 API、跨模块边界和复杂返回结构应标注类型。
- 不用宽泛 `Any` 隐藏不确定性；在不可信边界使用 `object`/未知输入，验证后缩窄。
- `# type: ignore` 必须尽可能带错误码并解释不可消除的原因。
- 类型不能与运行时行为矛盾；可选值、异常和可变性要真实表达。

应该：

- 接收抽象能力足够的小类型，返回能表达保证的具体类型。
- 用 `Protocol` 表达结构化依赖，用类型别名表达重复且有领域意义的组合。
- 避免只为复用类型而建立运行时循环依赖。
- 不在每个局部变量上重复显而易见的类型；类型标注服务于边界和推理。

## 7. 异常与错误

必须：

- 捕获能够处理的最窄异常；禁止裸 `except:`，谨慎捕获 `Exception`。
- 不吞异常。恢复、重试、转换、记录后继续都必须是明确策略。
- 转换异常时使用 `raise DomainError(...) from exc` 保留因果链；刻意隐藏低层细节时明确使用 `from None`。
- 异常消息包含安全且可操作的上下文，不包含密码、令牌或完整敏感载荷。
- 清理资源使用上下文管理器或 `finally`，不能依赖正常路径。

应该：

- 在协议/应用边界把低层异常转换为稳定错误；核心层不要依赖供应商异常类型。
- 自定义异常形成小而有意义的层次，便于调用者按恢复策略捕获。
- 错误日志通常只在最终处理边界记录一次，避免每层重复打印同一堆栈。

## 8. 资源、I/O 与并发

- 文件、socket、连接、事务、锁和临时资源必须显式关闭；优先 `with`/`async with`。
- 文件读写明确编码；文本协议不要依赖平台默认编码。
- 外部 I/O 必须考虑超时。重试只用于可恢复错误，并包含上限、退避、抖动和幂等性判断。
- 异步函数不得直接执行阻塞 I/O 或长时间 CPU 工作；使用合适的异步客户端或显式转移执行环境。
- 正确传播取消；不要用宽泛异常处理意外吞掉取消信号。
- 共享状态要有同步和所有权；不要假设某个内置操作在所有解释器或复合流程中天然原子。
- 后台任务必须可观测、可停止，并处理其异常；不要创建无人持有的“fire-and-forget”任务。

## 9. 字符串、日志与文档

- 普通格式化优先使用 f-string；日志调用沿用日志框架的惰性参数格式，避免无用格式化开销。
- 用户可见错误、协议响应和日志事件分开设计，不直接把内部异常文本返回给用户。
- 公共模块、类和函数应有与项目风格一致的 docstring，说明契约、重要副作用、异常和非显然约束；不要复述签名。
- 注释解释“为什么”和约束来源，不逐行翻译代码。过期注释是缺陷。
- TODO 必须可追踪，包含 issue/负责人或清晰完成条件；不要留下无上下文的永久 TODO。
- 日志使用模块级 logger；选择正确级别，包含关联标识，禁止记录机密和不必要的个人信息。

## 10. 测试代码

必须：

- 测试可观察行为、边界和失败路径，不只覆盖正常路径。
- 测试相互隔离、顺序无关且可重复；控制时间、随机数、环境、网络和文件系统。
- 关键业务、公开合同或重要回归风险变化时，保留原失败证据，在完整实现切片后集中补最小充分回归。普通文档、低风险整理不为形式新增测试；依仓库规则选择门禁。
- mock 应 patch 被测模块实际查找名称的位置，并验证有意义的结果，而不是复制实现调用序列。

应该：

- 测试名表达场景和结果。
- fixture 小而明确；避免一个全能 fixture 隐藏大量状态。
- 优先使用真实轻量值对象；只在慢、不稳定、昂贵或边界隔离需要时 mock。
- 对不变量、解析器和组合输入考虑参数化或基于属性的测试。
- 不用固定 sleep 等待异步结果；使用事件、轮询上限或可控调度器。

## 11. 安全规则

必须：

- SQL 和命令参数化；默认 `shell=False`，不可拼接不可信命令。
- 规范化并限制文件路径，防止 `..`、符号链接或绝对路径逃逸预期根目录。
- 不对不可信数据使用 `pickle`、不安全 YAML loader、动态 `eval`/`exec`。
- 机密来自受控配置，永不硬编码、提交或记录。
- 对输入大小、分页、压缩、正则、并发、重试和队列设置边界。
- 身份认证和授权分别检查；对象级权限不能只依赖前端隐藏。

涉及密码学、认证、支付、隐私或反序列化时，查阅当前官方安全指南和仓库安全策略，不凭记忆发明方案。

## 12. 自动化与审查清单

沿用仓库统一命令。没有既有工具链时，选择能覆盖以下能力且互不冲突的最小集合：格式化、lint、类型检查、测试、覆盖率和构建。把同一检查放入本地开发入口与 CI，避免两套配置漂移。

审查每个变更时依次确认：

1. 行为是否满足需求，边界/错误/并发场景是否正确？
2. 公共 API、数据、配置和持久化是否兼容？
3. 依赖方向、状态所有权和资源生命周期是否清晰？
4. 输入、权限、机密、注入和拒绝服务风险是否处理？
5. 类型、测试和日志是否验证关键契约？
6. 是否存在无关重构、重复抽象、死代码或隐藏副作用？
7. 公开函数/类型、内部实现与方法是否按各自规则命名，全部导出和消费者是否同步？
8. 所选门禁是否实际运行，未运行项和既有失败是否如实区分？

Trader 的公开顶层函数由 `scripts/check_refactor_quality.py` 中的 AST 门禁检查；`N802/N813` 不用于强制公开函数改回小写。复用现有门禁，不新增第二套命名检查或调整无关基线。纯 skill 文档修改不要求运行全仓代码门禁。
