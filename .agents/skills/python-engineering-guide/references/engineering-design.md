# Python 工程设计指南

本指南用于新建、扩展、拆分或审查 Python 工程。它是现代化归纳，不是某个上游仓库的逐字翻译。

## 1. 决策顺序

按以下顺序做决策：

1. 用户目标、外部契约和合规要求。
2. 仓库已有约定、支持版本和运维现实。
3. 能通过测试或指标验证的工程需求。
4. 本指南默认值。
5. 个人偏好。

不要为采用某个“最佳实践”而破坏稳定行为。任何结构调整都要指出它解决的具体故障模式，例如循环依赖、不可替换的外部服务、导入副作用或无法隔离的测试。

## 2. 项目分类

先判断交付物，因为不同交付物需要不同边界：

| 类型 | 主要契约 | 重点 |
| --- | --- | --- |
| 单文件脚本 | 参数、输入输出、退出码 | 简单、可重复执行、错误清晰 |
| 可复用库 | 导入路径、公共对象、版本 | API 稳定、依赖克制、构建可用 |
| CLI | 命令、选项、stdout/stderr、退出码 | 解析与业务逻辑分离、可测试 |
| 服务 | HTTP/RPC/消息契约、SLO | 边界验证、资源生命周期、可观测性 |
| 数据/批处理 | 数据模式、幂等性、检查点 | 可恢复、数据质量、重跑安全 |
| 插件/框架扩展 | 宿主接口、加载生命周期 | 兼容矩阵、隔离可选依赖 |

确认它是应用还是库。应用可以锁定完整依赖以获得可重复部署；库通常声明兼容范围，不应把所有传递依赖钉死。

## 3. 仓库与包结构

对新的可发布包，优先考虑以下基线：

```text
project/
├── pyproject.toml
├── README.md
├── LICENSE
├── src/
│   └── package_name/
│       ├── __init__.py
│       └── ...
├── tests/
├── docs/                  # 确有长期文档时
└── .github/workflows/     # 使用 GitHub Actions 时
```

`src` 布局可避免测试意外从仓库根目录导入未安装代码，并更接近用户安装后的行为。现有工程采用稳定的 flat layout 时，不要只为形式一致而迁移；若迁移，应同时验证构建、editable install、测试发现和入口点。

保持根目录可扫描。根目录只放工程级元数据、自动化入口和少量说明。不要使用含义模糊的 `utils.py`、`common.py` 或层层重复的包名承载无边界代码；根据业务能力或技术职责命名。

`__init__.py` 应轻量。只暴露有意维护的公共 API，避免执行网络、文件、线程或昂贵计算。把命令入口保持为薄适配层，使导入模块不会启动应用。

## 4. 模块边界与依赖方向

每个模块都要能回答：它拥有哪类决策、暴露什么契约、依赖谁、谁可以依赖它。

推荐的依赖方向是从易变边界指向稳定核心：

```text
entrypoints/adapters -> application/use-cases -> domain/core
infrastructure ------^  implements ports owned by inner layers
```

- 核心逻辑不要导入 Web 框架、ORM、消息客户端或 CLI 解析器。
- 在需要替换或测试外部系统时，由内层定义小接口，由外层实现。
- 在组合根创建具体对象并注入；不要在业务函数内部隐藏构造数据库或网络客户端。
- 允许直接依赖简单稳定的库。不要为每个三方函数机械包装一层。
- 循环导入通常表示职责或所有权不清。先重画依赖，再考虑局部延迟导入。

优先按业务能力形成垂直模块；只有跨能力的基础设施才按技术层共享。共享模块必须有清晰所有者和稳定契约。

## 5. 按复杂度选择架构

使用满足当前约束的最小结构：

### 级别 A：函数与模块

适用于脚本、小型库和简单服务。分离纯计算与 I/O，显式传入依赖，用普通函数和数据类型表达流程。

### 级别 B：用例/服务层

当同一业务流程有多个入口，或事务、授权、重试等编排逻辑开始重复时，引入薄用例层。入口负责协议转换，用例负责流程，领域对象负责业务不变量。

### 级别 C：端口与适配器

当数据库、消息系统、支付或其他外部边界确实需要替换、模拟或独立演进时，由应用核心定义最小端口，由基础设施适配器实现。避免暴露供应商对象穿透核心。

### 级别 D：事件、工作单元等模式

仅在事务一致性、跨聚合协作或异步解耦有明确需求时使用。定义事务边界、投递语义、幂等键、失败恢复和可观测性。不要仅为“解耦”加入不可追踪的全局事件总线。

每升一级都要用当前故障模式证明复杂度值得，并保留简化路径。

## 6. 接口、数据与兼容性

- 先定义边界契约：输入、输出、错误、超时、副作用和版本策略。
- 在入口处解析并验证不可信数据；进入核心后使用明确的领域值或类型。
- 区分缺失、空值和默认值。不要用一个 `None` 表达多个语义。
- 公共 API 要小而稳定；内部对象默认不承诺兼容。
- 序列化模型与内部领域模型分离，避免数据库或协议字段控制所有内部设计。
- 破坏性修改要提供迁移说明、弃用期或版本边界。
- 数据库迁移采用向后兼容的 expand/migrate/contract 顺序，避免代码与模式只能同时瞬时切换。

## 7. 配置、状态、资源与并发

配置应在应用边界读取、解析和校验，再作为显式对象传入。不要在任意模块导入时读取环境变量。机密不进入源码、日志、异常消息或测试快照。

尽量使核心逻辑无状态。必须共享的可变状态要明确所有权、生命周期和同步策略。缓存必须定义键、失效、容量、并发和一致性容忍度。

文件、socket、数据库连接、事务、锁和线程池都必须有可见生命周期。使用上下文管理器或应用生命周期钩子保证释放。不要依赖垃圾回收完成关键清理。

并发设计要写明：

- 哪些工作是 CPU-bound，哪些是 I/O-bound。
- 顺序、一致性和重复执行要求。
- 超时、取消、重试和背压策略。
- 线程/进程/事件循环之间传递的数据是否安全。
- 异步代码是否调用阻塞 I/O。

## 8. 错误、日志与可观测性

把错误分为领域拒绝、无效输入、外部依赖失败和内部缺陷。只在有能力恢复、转换或增加上下文的边界捕获异常；保持原始因果链。

日志记录事件，不记录散乱句子。至少考虑时间、级别、事件名、请求/任务关联标识、关键对象标识和结果。禁止记录密码、令牌、完整敏感载荷或不必要的个人信息。

服务和任务应同时设计指标与追踪：吞吐、延迟、错误、重试、队列深度、资源饱和度和业务结果。告警绑定用户可见症状或明确操作，不绑定每个异常堆栈。

## 9. 依赖、构建与发布

- 使用 `pyproject.toml` 声明构建系统和项目元数据；不要为新工程默认生成遗留 `setup.py`。
- 选择一个符合仓库环境的构建后端和依赖工作流，不混用多个锁定真相源。
- 运行时、测试、文档和开发依赖分组，避免把工具链带入运行镜像。
- 库声明兼容版本范围并测试最低/最高支持组合；应用使用锁文件和可重复构建。
- 删除未使用依赖，审查依赖许可证、维护状态、漏洞和供应链风险。
- 版本只保留一个权威来源。发布前构建 sdist/wheel，并在干净环境验证安装、导入、入口和包数据。
- CI 发布使用最小权限、受保护环境和短期凭证；不要把长期令牌写入配置。

具体工具和字段会变化。新增或升级配置前查阅当前工具的官方文档，不把本指南中的示例当作版本锁定模板。

## 10. 测试与质量门禁

测试按风险分层：

| 层次 | 覆盖对象 | 目标 |
| --- | --- | --- |
| 单元 | 纯函数、领域规则、不变量 | 快、定位清晰 |
| 组件 | 数据库适配器、客户端、序列化 | 验证真实边界行为 |
| 契约 | 自有/第三方接口约定 | 发现协议漂移 |
| 集成 | 完整用例和资源协作 | 验证装配与事务 |
| 端到端 | 少量关键用户路径 | 验证部署形态 |

优先测试可观察行为，不与内部调用顺序过度绑定。对金额、时间、重试、并发、权限、迁移和错误路径加入边界测试。随机、时间和外部服务要可控制，失败测试要可重复。

典型 CI 门禁包括 formatter 检查、lint、类型检查、测试和构建。沿用仓库既有工具；新工程可以从一套小而一致的门禁开始，再根据缺陷数据增加规则。

## 11. 安全与性能

安全基线：校验外部输入；使用参数化查询；限制路径遍历和上传；避免 `shell=True`；不要反序列化不可信 pickle；限制请求体、并发、重试和解压规模；依赖最小权限；默认不泄露内部异常。

性能优化必须先有代表性测量。先检查算法、I/O 次数、批处理、序列化和缓存，再做微优化。记录基准输入、环境、延迟分位数、内存和正确性约束。不要以牺牲清晰度换取未测量的速度。

## 12. 演进与迁移

采用可回退的小步迁移：

1. 用测试固定当前外部行为。
2. 引入新边界或兼容适配器。
3. 逐个迁移调用者并监测结果。
4. 删除旧路径、临时开关和重复数据。
5. 更新文档、运维手册和质量门禁。

长迁移要定义完成条件和最后期限，避免永久双写、双读或两套 API。数据迁移先评估容量、锁、重跑和中断恢复。

## 13. 设计审查清单

- 目标、非目标和外部契约是否明确？
- 模块职责和依赖方向是否能用一句话解释？
- 是否存在不必要的层、抽象或全局注册表？
- 配置、状态、资源、事务和并发由谁拥有？
- 超时、取消、重试、幂等和部分失败如何处理？
- 公共 API、数据和部署如何兼容迁移？
- 单元、组件、契约、集成和端到端测试各覆盖什么风险？
- 构建、安装、运行、回滚和发布能否自动验证？
- 日志、指标和追踪能否回答“发生了什么、影响谁、如何恢复”？
- 是否处理机密、注入、路径、权限、依赖和拒绝服务风险？
- 性能假设是否有测量，容量边界是否明确？
- 新复杂度解决了哪个可复现问题，未来能否移除？
